## 0.1 — Repository and solution skeleton

- **The dependency rule:** Clean Architecture is enforced by which project may reference which, so `Gym.Domain` has zero references and every arrow points inward — this is why an entity can never call EF Core.
- **`Directory.Build.props`:** MSBuild walks up from each `.csproj` and imports the nearest one, so `Nullable`, `ImplicitUsings` and `TreatWarningsAsErrors` are declared once and cannot drift per project.
- **Layered props files:** MSBuild imports only the *nearest* `Directory.Build.props`, so `tests/Directory.Build.props` must import the root one explicitly with `GetPathOfFileAbove` before adding its test-only settings.
- **Central Package Management:** `Directory.Packages.props` holds every version and `.csproj` files reference packages by name only, so two projects can never disagree on a version.
- **`global.json`:** pins the SDK band (`10.0.401` + `rollForward: latestPatch`) so this machine and CI compile with the same compiler instead of silently diverging.
- **Warnings as errors:** cheap on day one and expensive later, because a codebase with 200 tolerated warnings is one where nobody reads warnings at all.
- **Analyzer rules vs project conventions:** CA1707 forbids underscores in member names, which contradicts the mandated `Method_Scenario_ExpectedResult` test naming; the fix is to scope the rule off for `tests/**` in `.editorconfig`, not to rename the tests or silence the rule globally.
- **Architecture tests:** `Assembly.GetReferencedAssemblies()` turns the dependency rule into an executable assertion, so a forbidden reference fails the test run instead of surviving code review.
- **Trade-off behind those tests:** they read *compiled* references, so they are weak while assemblies are near-empty and get stronger as code lands; the airtight alternative (parsing `.csproj` files) is more brittle, and a dedicated library such as NetArchTest is not on the approved list.
- **Microsoft Testing Platform:** the .NET 10 SDK dropped the VSTest bridge, so xunit.v3 test projects are executables hosting their own runner and `global.json` opts `dotnet test` in with `"test": { "runner": "Microsoft.Testing.Platform" }`.
- **`.gitattributes` and `.editorconfig` must agree:** git on Windows converts to CRLF by default, which would silently contradict `end_of_line = lf`; `* text=auto eol=lf` settles it for both the repo and the working tree.

## 0.2 — Local infrastructure

- **Environment as code:** `docker-compose.yml` turns "install Postgres and Seq" into a file under version control, so a new machine, a teammate and CI all get byte-identical infrastructure instead of following a wiki page that drifted.
- **Running is not ready:** Postgres accepts TCP connections seconds before it will accept queries, so `healthcheck` exists to distinguish *started* from *usable*. Task 0.6 depends on this: Testcontainers waits for a readiness signal rather than sleeping a guessed number of seconds.
- **A health check can only use tools the image actually ships.** The Seq image has neither `curl` nor `wget`, and its bundled `seqcli` is broken, so the probe is a hand-written HTTP request through one of bash's `/dev/tcp` sockets. The trade-off against the simpler "is the port open" check: an open port only proves something bound it, while a `200 OK` on `/health` proves Seq is actually serving.
- **Named volumes outlive containers:** the container is disposable and the volume is not, which is what makes `docker compose down` safe and `down -v` the deliberate destructive one.
- **The `postgres:18` mount point:** this image keeps `PGDATA` in a versioned subdirectory, so the volume mounts at `/var/lib/postgresql`. Mounting `/var/lib/postgresql/data` — correct for older tags, and what most tutorials still show — leaves the real data directory inside the container's writable layer, so the data silently disappears on every recreate.
- **Splitting a connection string:** everything non-secret is committed in `appsettings.Development.json` and only the password lives in user-secrets, under a separate `Postgres:Password` key. A configuration *value* cannot have child keys, which is why the password gets its own key instead of being layered onto the connection string; `AddInfrastructure()` recombines them with `NpgsqlConnectionStringBuilder` in task 0.3.
- **User-secrets are a `UserSecretsId` plus a file outside the repository** (`%APPDATA%\Microsoft\UserSecrets\<id>\secrets.json`). They are a development convenience and nothing more — production reads environment variables, because a developer's home directory is not a secret store.
- **Fail loudly on missing configuration:** compose's `${VAR:?message}` stops with that message instead of starting a database with an empty password. The trade-off is one extra setup step (`cp .env.example .env`) against never having a working credential committed by default — and defaults have a way of surviving into staging.
- **Guard tests for configuration:** the same value written in two files will eventually disagree, so `DevelopmentSettingsTests` reads the repository's own files and fails if `.env.example` and the connection string drift apart, or if a password ever appears in a committed file. It is a cheap executable version of a code-review rule nobody remembers to apply.
- **`dotnet test` forwards unknown arguments to the test application.** Under Microsoft Testing Platform there is no VSTest wrapper to absorb MSBuild-style flags, so `dotnet test --nologo` hands `--nologo` to the test app, which rejects it and reports "Zero tests ran" with exit code 5 — a build-succeeded, no-tests-found result that looks exactly like a discovery failure. Plain `dotnet test` works. The lesson generalises: when a runner reports zero tests but the test executable run directly passes, suspect the arguments before suspecting the packages.

## 0.3 — Persistence foundation

- **`IAppDbContext` is the seam, not a repository:** Application declares the contract and Infrastructure implements it, so the dependency arrow still points inward even though EF Core is doing the work. The trade-off for dropping `IRepository<T>`: Application references the EF Core *abstractions* (`DbSet<T>`, `SaveChangesAsync`) and gains full LINQ, but never references a provider — a wrapper around something that is already a repository and a unit of work would only have to re-expose LINQ to stay useful, and would cost a layer of indirection for nothing.
- **Why version 7 GUIDs:** a v4 GUID is random, so every insert lands at a random point in the primary key's B-tree and fragments it. `Guid.CreateVersion7()` puts a millisecond timestamp in the high bits, so ids sort by creation time and inserts append to the end of the index — the write pattern of an `int` identity, but generated in C# before the row is saved, which matters for assigning ids to related objects in one unit of work.
- **A `SaveChangesInterceptor` turns a convention into a guarantee:** forty use cases each remembering to set `UpdatedAt` is forty chances to forget. One interceptor underneath `SaveChanges` is zero. The general lesson: when a rule must hold for *every* write, put it below the write, not beside it.
- **Writing through the change tracker preserves encapsulation:** `entry.Property(e => e.CreatedAt).CurrentValue = now` reaches a **private** setter, because EF Core writes properties through its own accessors rather than through C# visibility. So the audit fields did not have to be made public for the interceptor's benefit, and CLAUDE.md's "entities have private setters" stays literally true.
- **Insert is not update:** `CreatedAt` is stamped only for `Added` entries and `UpdatedAt` only for `Modified` ones. Re-stamping `CreatedAt` on every save is the classic bug here — it passes a naive one-save test and silently destroys history in production, which is why there is a dedicated test for it.
- **One timestamp per save, not per row:** `GetUtcNow()` is called once and shared, so everything written in the same transaction agrees about when it happened.
- **snake_case as a convention, not a per-property attribute:** Postgres folds unquoted identifiers to lower case, so a `CreatedAt` column would have to be quoted forever. `UseSnakeCaseNamingConvention()` renames the whole model at once. Watch out: it also renames EF's own `__EFMigrationsHistory` columns.
- **An empty first migration is still worth having:** there are no entities yet, so `InitialCreate` creates only `__EFMigrationsHistory` — but it also fixes `AppDbContextModelSnapshot` as the baseline every later migration is diffed against, so task 1.1's Identity tables become a clean delta instead of one enormous first migration.
- **A health check should answer "can I do my job", not "am I running":** `AddDbContextCheck<AppDbContext>()` makes `/health` return `503 Unhealthy` when Postgres is unreachable. A process-only probe would let an orchestrator route traffic to an API that cannot serve a single request. Verified by stopping the container and watching the endpoint flip to 503 and back.
- **Design-time is a separate execution context:** `dotnet ef` builds and runs the startup project's host to find `AppDbContext`, and it reads `Properties/launchSettings.json` for environment variables. Without an `ASPNETCORE_ENVIRONMENT=Development` profile there, the migration commands run as Production and never see `appsettings.Development.json` or user-secrets. The global `dotnet-ef` tool also carries its own version and must be at least as new as the EF Core packages.
- **Fail loudly at startup, not at the first query:** `AddInfrastructure` throws with the exact `dotnet user-secrets set` command when no password is configured, instead of letting the first request die with a bare authentication error — the same reasoning as `${VAR:?message}` in `docker-compose.yml`.
- **You can test EF Core without a database:** building a model and tracking changes happen entirely in memory; a connection is opened only when a query or `SaveChanges` actually runs. So column naming, type mappings and the interceptor's behaviour are all testable with the *real Npgsql provider* and no Docker — which is not the same thing as the banned InMemory provider, whose whole problem is that it is a *different* provider with different semantics. Real database behaviour (constraints, concurrency, transactions) still needs Testcontainers, which arrives in task 0.6.
- **`FakeTimeProvider` is why `DateTime.UtcNow` is banned:** the interceptor's clock is injected, so a test can pin "created on 21 March" and "updated on 22 March" and assert exact values instead of asserting that something is "roughly now".

## 0.4 — API plumbing

- **Structured logging is not string logging:** `logger.LogInformation("Member {MemberId} checked in", id)` sends Seq a *property* called `MemberId`, not a sentence. That is why the request log line arrives with `RequestPath`, `StatusCode` and `CorrelationId` as queryable fields — and why Seq is in `docker-compose.yml` instead of a text file. Grep can find a string; only properties can answer "every 5xx for this member last week".
- **A correlation id reassembles a story from scattered lines:** one request produces log events from several layers, and without a shared id they are unrelated rows. ASP.NET Core already starts a W3C `Activity` per request and adopts an inbound `traceparent`, so the middleware *returns* that id rather than inventing one — verified by sending `traceparent: 00-4bf92f…-…-01` and getting `X-Correlation-Id: 4bf92f…` back. Inventing a second id would mean carrying two names for one thing.
- **Deferred header writes:** headers cannot be set once the response has started, and the request you most want to look up is the one that threw. So the id is registered in an `OnStarting` callback *before* calling the next middleware, not assigned after it returns.
- **A bootstrap logger covers the gap before the host exists:** anything thrown while the host is being built — including task 0.3's missing-password check — would otherwise die with no log line at all, which is exactly when a log line is worth most. `CreateBootstrapLogger()` writes to the console until the configured logger replaces it, and `try/catch/finally` around `app.Run()` with `Log.CloseAndFlush()` stops the buffered Seq events from being dropped on an abrupt exit.
- **Logging has a budget:** `/health` polled every ten seconds is 8,640 events a day that say nothing. `GetLevel` drops health probes to `Debug` while keeping 5xx at `Error`. Deciding what *not* to log is part of setting logging up — otherwise the signal drowns and people stop reading Seq at all.
- **Configuration over code for levels and sinks:** they live in `appsettings.json`, so turning production up to Debug for an hour is a config change, not a rebuild and a redeploy. Only what configuration cannot express stays in C#.
- **Config files merge by key, arrays merge by index:** so Serilog sinks are written as a keyed object (`"WriteTo": { "Console": … }`) and `appsettings.Development.json` adds `"Seq"` by name. With an array, Development could only add a sink by counting the entries in the base file — and would silently overwrite one if the count ever changed.
- **Culture leaks into logs:** the analyser refused `WriteTo.Console()` without an `IFormatProvider` (CA1305), and it was right in a way that matters here — this project sets `InvariantGlobalization=false` so the app can format Persian dates, so a machine set to `fa-IR` would write log timestamps and numbers in Persian digits that no query would match. Persian formatting is the frontend's job; logs are for engineers. A warning-as-error caught a real bug rather than being noise.
- **Environment-gated middleware:** Scalar and a credentialed CORS policy are development conveniences that would be a hole in production, so they are behind `IsDevelopment()`. That turns "do not ship the API explorer" into a property of the code rather than a deployment checklist item somebody has to remember.
- **`AllowAnyOrigin` and `AllowCredentials` are illegal together,** and for good reason: that pair would let any website on the internet call this API as the logged-in user. Origins are therefore listed explicitly, which is also why `AddVitePolicy` throws when the list is empty rather than starting with CORS quietly broken.
- **`TryAddSingleton` lets two layers declare the same dependency:** Application needs a clock for business dates and Infrastructure needs one for the audit interceptor, so both register `TimeProvider.System` and neither breaks when used alone or together. A plain `AddSingleton` twice would leave two registrations; a test asserts one instance comes back.
- **`ValidateOnBuild` and `ValidateScopes` move DI failures to the build:** registering a service and resolving it are separate events, so a missing registration normally surfaces on the first request that needs it, in production. Building the provider in a test with validation on finds it now — and `ValidateScopes` catches a singleton capturing a scoped `DbContext`, the bug that becomes a cross-request data leak rather than an exception.
- **Test doubles must actually do the thing:** `HttpResponseFeature.OnStarting` on a plain `DefaultHttpContext` is a no-op, because nothing is ever written to a socket. A test using it would have asserted on a header that was never going to be set either way — passing regardless of whether the middleware worked. `RecordingResponseFeature` records the callbacks and fires them where a real server would. The general lesson: a test that cannot fail is worse than no test, because it buys false confidence.

## 0.5 — Errors and validation

- **Expected failures are return values; exceptions are for the unexpected.** A signature of `Task<Result<MemberResponse>>` tells the caller this can fail and makes the compiler carry the failure along the same path as the success. An exception says nothing in the signature, costs a stack unwind, and — worse — makes "this phone already exists" indistinguishable from "the database is down". The trade-off: every caller must now unwrap a `Result`, which is exactly the point.
- **`Error` separates a code from a message.** `Code` (`Members.PhoneAlreadyExists`) is a published contract the Persian frontend maps in `lib/errors.ts`; `Description` is English prose for developers and logs. Because they are separate fields, rewording a message can never change what a member reads, and the API never has to speak Persian.
- **No `Error.None` sentinel.** The common tutorial design gives a success a blank error object; this one gives it none at all, and asking a success for its `Error` throws — the mirror of asking a failure for its `Value`. A blank error would otherwise travel on and be reported to the caller as a real failure with an empty code, which is a bug that surfaces far from where it was made.
- **One mapping table, in one place.** `ToHttpResult()` is the only code in the solution that picks a status code. If each endpoint chose for itself, "member not found" would be a 404 here and a 400 there and the frontend would need a special case per endpoint. This is also why `ErrorType` lives in the Domain but the status codes do not: a handler called from a Hangfire job in Phase 5 has no HTTP to speak of.
- **400 vs 422.** A 400 means the request is malformed — the form can point at the field that is wrong. A 422 means the request was fine and a rule in BUSINESS_RULES.md said no ("this subscription is expired"). The frontend reacts differently to each, so the distinction has to survive the trip.
- **An enum switch still needs a default arm.** Covering every declared `ErrorType` silences CS8509, but C# allows an enum to hold any underlying value, so CS8524 then demands a default — and with warnings-as-errors there is no way to have the compiler guard exhaustiveness here. The guard moved to a test that walks `Enum.GetValues<ErrorType>()`. General lesson: when the compiler cannot hold a rule, a test has to, and it is worth writing down which one does.
- **A 500 must leak nothing.** `GlobalExceptionHandler` returns a fixed sentence and a correlation id — never the exception message, type or stack. Messages carry connection strings, file paths and member names, and they help the reader with nothing; the id is the way back to the full exception in Seq. It also deliberately logs nothing, because ASP.NET Core's exception middleware and Serilog's request log already record it, and three copies of one event is how a log stops being read.
- **Validation is a filter, not the first fifteen lines of every handler.** `ValidationFilter<T>` short-circuits before the endpoint, so handlers can assume well-formed input and are left with the rules that actually need the database. It also means nothing was written on the way to a 400.
- **Where the filter lives is the dependency rule doing its job.** ARCHITECTURE.md originally put `ValidationFilter` in Application, but `IEndpointFilter` is an ASP.NET Core type and the layer test from task 0.1 fails the build on that reference. So the *validators* stay in Application (a command must be valid whoever sends it, including a background job) and only the HTTP shape of the answer moved to Gym.Api. An executable architecture rule caught a documentation error, which is the whole reason for writing those tests.
- **Field errors carry codes, not just sentences.** `Results.ValidationProblem` produces `errors: { field: ["message"] }` — English strings the Persian UI cannot use. This API returns `errors: { "phoneNumber": [ { code, description } ] }` instead, keyed by the JSON property name, so the frontend can attach a Persian message to the right input. The price is a non-standard `errors` shape, which is documented in ARCHITECTURE.md as part of the contract.
- **An assembly scan beats a registration list.** `AddValidatorsFromAssembly` picks up a new validator by its simply being there. A forgotten line in a manual list would not fail the build — it would silently disable validation for one endpoint, which is the worst way to find out.
- **Test the bytes, not the intent.** Asserting `result.ShouldBeOfType<ProblemHttpResult>()` tests what the code meant; `ExecutedResult.RunAsync` executes the `IResult` against a real `HttpContext` and asserts on the JSON that comes out — the casing, the field names, the extensions added by configuration. The frontend only ever sees the bytes.
- **A passing test can still be testing nothing.** The first "two rules on one field" test passed while only one rule was actually failing, so the grouping it claimed to check was never exercised. Worth re-reading a green test once and asking what would have to break for it to go red.
- **`InternalsVisibleTo` instead of widening the API.** The mapping tables are internal because no endpoint should call them; the test project gets access through the csproj rather than by making them public. Letting a test dictate the public surface is a small decision that compounds.

## 0.6 — Test harness

- **Two kinds of test, two kinds of bug.** A unit test asks whether a class is correct; an integration test asks whether the parts were plugged together. `WebApplicationFactory<Program>` starts the real `Program.cs` in process — real DI container, real middleware order, real routing — so it catches the bug a unit test structurally cannot see: a service registered with the wrong lifetime, a middleware nobody wired up, an endpoint that was never mapped. `CorrelationIdMiddlewareTests` proves the middleware works; only the `/health` test proves it is actually in the pipeline.
- **One assertion can cover a lot of seams.** For `/health` to return `Healthy`, the host must start, `AddInfrastructure` must build a working connection string, the migrations must apply, the endpoint must be mapped, and the health check must reach Postgres. Every item on that list is a seam between two things rather than a thing, which is exactly what unit tests cannot reach.
- **Why the InMemory provider is banned, concretely.** It is a *different* provider, not a fast Postgres: it ignores unique indexes, check constraints and concurrency tokens, so a green test there says nothing about the database that will actually reject the write. Testcontainers runs the same `postgres:18` image as production instead, on a random port, and deletes it afterwards.
- **Tests must not touch the development database.** The container is Testcontainers' own, never `gym-postgres` from docker-compose.yml — otherwise `dotnet test` would truncate the data you are looking at in the app. Worth checking explicitly for any harness: which database does this actually connect to?
- **Respawn instead of a fresh database.** Recreating a container or re-running migrations between tests would cost seconds each; truncating rows costs milliseconds. The price is one sharp edge: Respawn deletes *rows*, not tables, so `__EFMigrationsHistory` has to be ignored or the next run finds a fully migrated database that believes it has never been migrated. That is the failure `DatabaseHarnessTests` guards.
- **Collection fixture vs assembly fixture is a cost decision.** An assembly fixture would start Postgres for every run, including the ones that only exercise `Result` mapping in milliseconds. A collection fixture starts the container when the first database test asks for it and tears it down when the collection ends. The serial execution it forces is not a cost here — it is required, since a parallel test would have its rows deleted by another test's reset.
- **`WebApplicationFactory` cannot override configuration that was read before `Build()`.** This cost a debugging round: with minimal hosting, `Program.cs` calls `AddInfrastructure(builder.Configuration)` *before* `builder.Build()`, so the factory's `ConfigureAppConfiguration` delta arrives after the registrations have already read config — the app started with no connection string at all. Environment variables (`ConnectionStrings__Postgres`) are set before the host exists, and they are how production supplies the value too, so the test now travels the real path rather than a test-only hook. General lesson: to override configuration, you have to get in *earlier* than the code that reads it.
- **Environment `Testing`, not `Development`.** Scalar and the permissive CORS policy are development conveniences; a suite running with them on would not be testing the pipeline that gets deployed.
- **Warnings-as-errors keeps reaching into test code too.** CA1711 rejected `DatabaseCollection` (the `Collection` suffix is reserved for real collections) and CA1816 wanted `GC.SuppressFinalize` in an `IAsyncDisposable`. Renaming to `DatabaseCollectionDefinition` costs nothing — only the attribute name matters to xUnit.
- **A harness has to be testable itself.** If `DatabaseHarnessTests` breaks, every test built on the fixture is suspect, so the migration-applied check and the Respawn-configuration check are worth their weight. The probe table is created *before* its Respawner, because Respawn builds its delete plan from the schema it finds at creation time — asserting on the options object alone would have proved nothing.
- **Admitting what cannot be tested yet.** The ideal isolation test — test A inserts a member, test B sees an empty table — needs an entity, and the model has none until task 1.1. Writing a reassuring substitute would have been worse than leaving a note to add the real one then.

## 0.7 — Frontend skeleton

- **Generated API types are a compile-time contract.** `npm run gen:api` turns the API's OpenAPI document into `schema.d.ts`, and `openapi-fetch` only accepts paths and bodies that exist in it. When a backend field is renamed, `npm run build` fails instead of a screen quietly showing `undefined`. The trade-off is one more step after every endpoint change (regenerate and commit), which is why CLAUDE.md lists it as a command.
- **A dev proxy means one origin, like production.** The browser only talks to `localhost:5173`, and Vite forwards `/api` and `/health` to the API. Behind Caddy in production it is the same shape, so cookies and relative URLs behave identically in both places and CORS is never something the app relies on.
- **Server state belongs in TanStack Query, not in `useState`.** `useQuery` owns loading, error, retry, caching and refetching. A component only describes *what* it needs (`["health"]`, `fetchHealth`) and renders the three states. There is no hand-written `useEffect` + `fetch` + flags that could get out of sync.
- **"Unhealthy" is an answer, not a failure.** `/health` returns 503 with the body `Unhealthy` when the database is down. Treating every non-2xx as an error would show "server unreachable" exactly when the server is reachable and trying to tell you something. The test for this was checked by temporarily adding the tempting `if (!response.ok) throw` and watching it go red.
- **RTL works in three layers.** `<html dir="rtl">` is set before JavaScript runs, so there is no flash. Radix `DirectionProvider` exists because Radix computes placement and keyboard direction in JavaScript and does not read the `dir` attribute. And logical utilities (`border-e`, `ps-`) are enforced by an ESLint rule: the navigation is on the right because it comes first in a right-to-left row, not because anything says "right".
- **A business date is a day, not a moment.** `"2026-09-17"` is formatted in UTC so the day it names can never shift. A timestamp is formatted in `Asia/Tehran` so 21:00 UTC shows as 00:30 on the *next* Jalali day. Mixing these two up is the classic off-by-one-day bug.
- **Honest tests, again.** A "never shifts the day" test for dates passed with both the old and the new code, because Tehran is ahead of UTC and can't show the bug. It was renamed to what it actually checks instead of being kept as reassurance.
- **Invisible characters belong in escapes.** ZWNJ, Arabic ي and Persian ی look identical or invisible in an editor, so source code and tests write them as `\u200C`, `\u064A` and `\u06CC`. ESLint rejects literal ones, and the reviewer can see which code point is meant.
- **Normalization is a business rule, not a helper detail.** Treating half-space and space as the same, and stripping harakat and tatweel, decide which members a search finds. That is why these rules were written into BUSINESS_RULES §13 before the code was changed to match.
- **Generators need checking too.** The shadcn CLI read the wrong tsconfig, wrote into a literal `@/` folder and installed an unrelated npm package called `cn`. Reading `package.json` after running any generator is cheap insurance.

## 0.8 — CI and first decision record

- **CI is a clean machine that doesn't trust yours.** Locally, a test can pass because of something only your laptop has: `.env`, user-secrets, a `node_modules` built by an older install. The runner starts from an empty checkout, so anything the repository doesn't contain fails there first. The check that mattered before the first push was what the tests read from disk: `.env.example` (committed) and not `.env` (ignored).
- **The pipeline encodes the project's rules.** "Warnings are errors" and "every task ends with passing tests" were habits. Now `dotnet build -c Release` with `TreatWarningsAsErrors` and the two test jobs make them a gate on every push. A rule a machine enforces doesn't depend on anyone remembering it.
- **Build what you ship.** CI builds `Release`, not `Debug`. Some analyzers and trimming behave differently between them, and production runs Release.
- **Lock files make installs repeatable.** `npm ci` installs exactly what `package-lock.json` records and fails if `package.json` disagrees. `npm install` may quietly pick newer versions. The lock generated on Windows already listed the Linux native bindings (Rolldown, Tailwind oxide, lightningcss), which is why it installs on Ubuntu.
- **Testcontainers needs no CI setup.** GitHub's Ubuntu runners have Docker, so the integration tests start `postgres:18` exactly as they do locally. There's no service container to declare and no second database definition that could drift.
- **A gate you have never seen fail proves nothing.** After the first green run, a throwaway branch with a physical `ml-2` class was pushed to confirm the pipeline goes red on the Lint step. The same idea as the mutation check in 0.7, applied to the pipeline.
- **An ADR records the trade-off, not just the answer.** ADR 0001 lists what the modular monolith costs (more files per use case; module boundaries inside one database are only a convention) next to what it buys. Accepted records are never edited. A changed mind gets a new record that supersedes the old one, so the reasoning at each point stays readable.

## 1.1 — Identity and Owner seeding

- **Questions before code.** Four behaviors this task needed (what "Owner already exists" means, what happens when `Seed:*` is missing, the password policy, the FullName default) were not in BUSINESS_RULES.md. They were asked and answered before writing `IdentitySeeder`, then written back into BUSINESS_RULES.md §1 — so the next task reads the decision, not a comment buried in code.
- **`AddIdentityCore`, not `AddIdentity`.** `AddIdentity` also wires up cookie authentication and `SignInManager`, neither of which task 1.1 needs — there's no login endpoint yet. `AddIdentityCore<User>().AddRoles<IdentityRole<Guid>>().AddEntityFrameworkStores<AppDbContext>()` registers exactly `UserManager` and `RoleManager`, and task 1.2 adds `.AddSignInManager()` only if it turns out to need it.
- **`OnModelCreating` order is load-bearing once Identity joins.** `IdentityDbContext.OnModelCreating` (the `base` call) is what names the six Identity tables `AspNetUsers`, `AspNetRoles`, etc. `UserConfiguration.ToTable("users")` has to run *after* that base call or it gets silently overwritten back to `AspNetUsers` — the opposite of the order `AppDbContext` used before this task, when there were no entities for the order to matter to.
- **A Guid primary key can be client-generated or database-generated, and EF Core decides per-value.** `User`'s constructor sets `Id = Guid.CreateVersion7()` before the row is ever tracked, so EF Core sees a non-default value and inserts it as-is. `new IdentityRole<Guid>(roleName)` leaves `Id` at `Guid.Empty`, so the same convention detects "unset" and generates one instead. Same primary key type, two different paths, chosen by what the constructor already put there.
- **A validator that ignores its own parameters is still worth a real interface.** `LetterAndDigitPasswordValidator.ValidateAsync(manager, user, password)` only reads `password` — case-agnostic letter+digit isn't something `RequireLowercase`/`RequireUppercase` can express without also demanding a specific case. Because it doesn't touch `manager`/`user`, its tests call it directly with `null!` for both rather than standing up a real `UserManager`, which needs a full `IUserStore` to even construct.
- **`[LoggerMessage]` instead of `logger.LogWarning(...)`.** This is the first `ILogger` call in the codebase, and CA1848 (warnings-as-errors) rejected the extension-method form on grounds of allocation cost. The fix is a source-generated `partial` logging method (`[LoggerMessage(Level = LogLevel.Warning, Message = "...")]`) — no new package, since the generator ships with `Microsoft.Extensions.Logging.Abstractions`.
- **The pre-migration startup ordering from task 0.6 became a real design constraint, not just a fixture detail.** `WebApplicationFactory` runs `Program.cs` up to `app.Run()` while building the host, before `DatabaseFixture` calls `Database.MigrateAsync()`. That's exactly the moment `IdentitySeeder.SeedOwnerAsync` runs from `Program.cs`, so it has to decide whether `Seed:*` is configured *before* touching `RoleManager`/`UserManager` — if it queried first, every integration test in the suite would fail at boot, not just the Identity ones.
- **`IdentityResult` is a result, not an exception.** An unchecked `await roleManager.CreateAsync(...)` fails silently. Every Identity call in the seeder now checks `Succeeded`. A bad configured password is an expected mistake and gets a warning. Anything else is unexpected and throws, which is the same line CLAUDE.md draws between `Result` and exceptions.
- **Two saves that must both happen belong in one transaction.** `CreateAsync` and `AddToRoleAsync` each call `SaveChanges`. A crash between them would leave a user with no role, and the seeder would then be stuck forever on `DuplicateUserName`. `UserManager` shares the scoped `AppDbContext`, so `Database.BeginTransactionAsync()` covers both calls.
- **Prove a database invariant with raw SQL.** `UserManager` checks for duplicate names in C# before inserting, so a test through it proves only the C# check. `UserTableConstraintTests` inserts with plain SQL and expects SQLSTATE 23505 (unique) and 23514 (check). `ck_users_full_name_not_blank` exists because `IsRequired()` stops NULL but not `'   '`.
- **An ADR for a rule you bend.** `User` can't live in Domain because `IdentityUser<Guid>` is a framework type. ADR 0002 records that and the rejected "two user classes" option, so the next person doesn't have to rediscover the trade-off.

## 1.2 — Login and access tokens

- **A JWT is a signed claim, not a session.** The server writes "user X, role Owner, valid until 10:15" and signs it with a secret key. On every request it checks the signature and the expiry, with no database lookup. The price is that a token can't be taken back before it expires, which is why it lives only 15 minutes and task 1.3 adds refresh tokens that *can* be revoked.
- **Clock skew is a hidden extension of token lifetime.** The bearer handler accepts tokens up to five minutes past `exp` by default, to tolerate clocks on different machines. One machine issues and checks these tokens, so skew is zero. A mutation check proved the expiry test fails with the default.
- **Lockout and rate limiting guard different things.** Lockout guards one account: after 5 wrong passwords it is locked for 15 minutes, even for the right password. Rate limiting guards the endpoint: 10 attempts per minute per IP, however many accounts are tried. Without it, trying one password against every user name would never trigger a lockout.
- **The order of checks is a security property.** `UserAuthenticator` checks: unknown user → the same error as a wrong password. Locked → refuse before checking the password. Wrong password → count it. Inactive → only reveal it after the correct password. Each step leaks as little as possible to someone who doesn't know the password.
- **Interfaces at the layer boundary, again.** `LoginHandler` in Application can't see the Identity `User` (ADR 0002). It depends on `IUserAuthenticator` and `IAccessTokenIssuer`, which Infrastructure implements with `UserManager` and `JsonWebTokenHandler`. The handler is left with the use case itself: no token without a successful authentication.
- **Fail closed by default.** A fallback authorization policy makes every endpoint require a logged-in user unless it explicitly says `.AllowAnonymous()`. Forgetting a policy now causes a 401 instead of an open endpoint.
- **Validate configuration at startup.** `JwtOptionsValidator` with `ValidateOnStart()` stops the API when the signing key is missing or too short, with a message that says how to fix it. Otherwise the first sign of trouble would be a failed login in front of a user.
- **Options bound lazily see the final configuration.** `Bind(configuration.GetSection(...))` reads the section when the options are first used, not at registration. That's why a test host's `UseSetting` can change the rate limit, where a value read in `Program.cs` before `Build()` would be too late (the gotcha from task 0.6).
- **My notes:**

## 1.3 — Refresh tokens and logout

- **Two tokens, two jobs.** The access token is short (15 minutes) and can't be revoked. The refresh token is long (7 days, renewed on use) and *can* be revoked, because every refresh checks it against the database. Short-lived and stateless for every request, long-lived and checked for the rare refresh: each gets the property it's good at.
- **HttpOnly cookie instead of JavaScript storage.** A token in `localStorage` can be read by any script that ends up on the page. An HttpOnly cookie can't be read by JavaScript at all; the browser just sends it. `SameSite=Strict` stops other sites from making the browser send it, and `Path=/api/auth` keeps it off every other request.
- **Store a hash, like a password, but a fast one.** The database keeps only SHA-256 of the token, so a leaked backup contains nothing that logs anyone in. Passwords need slow hashes because people choose guessable ones. A 256-bit random value has nothing to guess, so a fast hash is enough and lets each refresh look the token up directly.
- **Rotation turns theft into a detectable event.** Each token works once. If a used-up token comes back, one of the two holders is a thief, and the server can't tell which, so it revokes the whole family (every token from that login). The thief loses access, and the real user re-enters a password the thief doesn't have. A mutation check proved the reuse test fails without the detection.
- **Optimistic concurrency with `xmin`.** Two requests can read the same active token at once. Postgres's `xmin` row version makes the second save fail with `DbUpdateConcurrencyException` instead of giving one parent two children. The handler then treats it as reuse, which is the "strict, no grace period" rule. A unique index on `replaced_by_token_id` is a second guard at the database level.
- **Rules in the entity, orchestration in the handler.** `RefreshToken.Rotate` and `Revoke` hold the rules (only active tokens rotate, a revoked token keeps its first reason) and are unit-tested without a database. `RefreshHandler` decides what to do with the results: look up, detect reuse, reload the user, save.
- **Say less when you refuse.** Missing, unknown, expired, revoked and reused tokens all return the same `Auth.RefreshTokenInvalid`, and logout always answers 204. Whoever holds a stolen or guessed token learns nothing about which ones are still worth trying.

## 1.4 — Current user, policies, change password

- **Authentication vs. authorization.** Authentication (1.2, 1.3) proves *who* you are. Authorization decides *what you may do*. They fail differently: 401 means "I don't know who you are, log in"; 403 means "I know who you are, and the answer is no." The frontend reacts to each differently, so the difference is worth keeping sharp.
- **Policies name a permission once.** `OwnerOnly` and `StaffOrOwner` are the permissions table in BUSINESS_RULES.md, written as code. An endpoint says which one it needs, instead of each handler checking roles itself, and a single test checks every combination of role and flag.
- **A requirement is a reusable rule inside policies.** The forced password change gate is `PasswordChangedRequirement`, added to every policy but one. Because it's a named requirement, the failure result says *which* rule failed, and the API can answer `Auth.PasswordChangeRequired` instead of a vague "forbidden".
- **Secure by default.** The fallback policy covers endpoints that forget their policy, `EndpointAuthorizationTests` covers endpoints that forget to *decide*, and the gate is part of both. Forgetting something now makes an endpoint closed, never open.
- **`ICurrentUser` hides HTTP from the inner layers.** Application and Infrastructure ask "who is this?" through an interface. Only Gym.Api knows the answer comes from a JWT claim, so the same handler works from a background job, where the answer is "nobody". The audit interceptor is its first user: `CreatedBy` and `UpdatedBy` now fill themselves.
- **A singleton can depend on per-request data through an accessor.** `IHttpContextAccessor` returns the current request each time it's asked, so `HttpContextCurrentUser` can be a singleton without capturing one request's user forever. Capturing a scoped value in a singleton is the classic DI bug that leaks one user's data into another's request.
- **Transactions have edges; choose what goes inside.** Changing a password saves the hash, clears the flag and revokes tokens in one transaction. The failed-attempt count is saved *before* the transaction, on purpose, so a rollback can't erase evidence of password guessing.
- **Old tokens don't learn about changes.** After a password change, the old access token still says `must_change_password=true` until it expires. The endpoint returns a fresh session, so the user moves on at once instead of hitting the gate for 15 more minutes.

## 1.5 — Staff management API

- **A policy on the group, not on each endpoint.** `MapGroup("/api/staff").RequireAuthorization(Policies.OwnerOnly)` makes "Owner only" a property of the whole URL space. A sixth endpoint added next month is protected without anyone remembering to protect it.
- **"Not found" as a safety rail.** The staff endpoints only see Staff accounts. Asking them to deactivate the Owner's id answers 404, as if the account weren't there, so the Owner can't lock themselves out through the staff screen.
- **Idempotent actions.** Deactivating an inactive account succeeds and changes nothing. A double-clicked button or a retried request can't turn into an error, and the result is the same however many times it arrives.
- **A test that passes for the wrong reason proves nothing.** The first deactivate test checked that refresh fails. But refresh rejects inactive users anyway, so it would have passed without the token revocation. The test now checks the tokens right after deactivation, and a mutation check confirms it fails without the revocation.
- **One rule, two enforcers.** `UserNamePolicy` and `PasswordPolicy` are read by both the FluentValidation rules (a friendly field error before anything is saved) and Identity's options (a guarantee on every path that stores a user). Neither can drift from the other because neither holds a copy.
- **Paging from the start.** Even a list of five staff returns `PagedResponse<T>`. Changing a response shape later breaks the frontend. Paging from day one costs almost nothing.

## 1.6 — Audit log

- **An interceptor sees every change, so no handler has to remember.** The audit rule is "every insert, update and delete". Forty handlers each writing their own audit row would be forty chances to forget. One `SaveChangesInterceptor` reads the change tracker and writes the rows for all of them.
- **Same save, same transaction.** The audit rows are added to the context *inside* `SavingChanges`, so they commit or roll back together with the change they describe. A test proves a failed save leaves no audit row behind.
- **The change tracker knows the old values.** `PropertyEntry.OriginalValue` and `CurrentValue` give "before" and "after" for free, and `IsModified` says which properties changed. EF marks a property modified when it's *assigned*, so the interceptor also compares the values.
- **Exclude secrets by name, and prove it with the real values.** The test doesn't only check that no row has a `PasswordHash` key. It loads every real hash and stamp from the database and checks that none appears anywhere in the log. A mutation check confirmed the test fails if the exclusion is removed.
- **Append-only belongs in the database.** The entity has no update methods, but code isn't the only thing that talks to a database. A trigger rejects UPDATE and DELETE from any connection. Triggers aren't part of EF's model, so the migration creates it with raw SQL and `ARCHITECTURE.md` records that the snapshot doesn't know about it.
- **Know how your tools touch the database.** A DELETE-blocking trigger could have broken every test reset. It doesn't, because Respawn uses TRUNCATE, which row-level triggers ignore. A test now pins that, so a Respawn upgrade that changes it fails loudly in one place.

## 1.7 — UI: login and staff

- **Where a token lives decides who can steal it.** The access token is a variable inside a module, and the refresh token is an HttpOnly cookie. Script on the page can read neither from storage, because there's no storage. The cost is a page reload forgets the access token, so `restoreSession()` asks for a new one with the cookie before the first screen decides anything.
- **One place for "my token expired".** `authFetch` wraps `fetch`: it adds the bearer header, and on a 401 it refreshes and retries once. No screen handles expiry, so no screen can get it wrong.
- **Single-flight refresh.** Three requests failing at once must cause *one* refresh. Refresh tokens rotate strictly, and a second refresh with the same cookie looks like theft and logs the user out. A shared promise makes later callers wait for the first refresh. A test fires three requests at once and counts the refreshes.
- **A request body can be read once.** Retrying a POST needs the body again, so the first attempt sends a `clone()` and the retry sends the original. A test checks that the retried body arrives intact.
- **Guards are for users, the API is for security.** `RequireAuth` and `RequireRole` keep people away from screens that would fail. The API still refuses the request if someone gets past them. The two protect different things.
- **Mock at the boundary, run everything else for real.** Tests replace only `fetch`, with a small router. openapi-fetch, `authFetch`, TanStack Query and React Router all run for real, so a test like "login with a temporary password lands on change-password" exercises the actual wiring.
- **A contract that spans two languages needs its own test.** Nothing links C# error codes to the TypeScript messages. `ErrorCatalogTests` collects every code the API defines, by reflection over errors and validators, and fails when `errors.ts` lacks one. A mutation check confirmed it.
- **Verify the Done-when for real, and doubt surprising results.** The live run through the Vite proxy showed a staff name as `??????`. Instead of assuming an app bug or ignoring it, the same request sent from a UTF-8 file came back intact: the Windows shell had mangled the argument. The dev data was repaired, and the gotcha is in `ARCHITECTURE.md`.

## Phase 1 review

A `code-reviewer` agent read all of Phase 1. It found no auth bypass, but it did find races and gaps that the task-by-task tests had missed.

- **"Read, change, save" is a race.** Identity's failed-login counter loads the count, adds one in C#, and saves. Eight parallel wrong passwords all read the same count: one save won, seven answered 500, and lockout counted one attempt instead of eight. The fix lets Postgres do the arithmetic in one `UPDATE ... SET count = count + 1`, on a row it locks. A test fires eight wrong passwords at once, and it failed on the old code with seven 500s.
- **Concurrency failures are expected, not exceptional.** Two people changing the same account at once is normal, so the answer is a 409 the Owner can retry (or, for token families, a retry loop), never a 500.
- **The same error message isn't enough; it must take the same time.** An unknown user name returned instantly while a known one ran the slow password hash, so timing leaked which names exist. Unknown names now run a dummy hash.
- **"Only one refresh at a time" must hold across tabs.** A module-level promise protects one tab. The refresh cookie is shared by every tab, so tabs coordinate with the browser's Web Locks API.
- **The cookie belongs to the browser, not the tab.** If someone else logs in from another tab, this tab's next refresh would quietly become them. The frontend now compares the token's `sub` and signs out instead.
- **A 401 isn't always an expired token.** Only `Auth.Unauthenticated` is worth a refresh. A handler's own 401 (locked out, deactivated) came with a valid token, and retrying would only resend the request.
- **A rule enforced only by the client is a suggestion.** Password digit conversion lived only in the browser, so a Persian-digit seed password could never log in. The API now converts too.
- **Why a review after the tasks.** Each task tested its own feature. The review looked across them: parallel requests, several tabs, two people at once. That's where these bugs were.

## 2.1 — Member creation and update

- **Canonical form before comparison.** `0912…`, `۰۹۱۲…`, `+98 912…` and `0098-912-…` are one phone number but five strings. A unique index compares strings, so every number is turned into E.164 (`+989121234567`) before it's saved or searched. The index is only as good as the normalization in front of it, which is why a check constraint also refuses anything that isn't E.164.
- **Use the library that knows the data.** Which Iranian ranges are mobiles, and how every country writes its numbers, is data that changes. libphonenumber (Google's, the one Android uses) carries it, behind `IPhoneNormalizer` so only Infrastructure knows it exists.
- **Store as entered, search on the normalized form.** `FullName` keeps what the receptionist typed. `NormalizedFullName` (ي→ی, ك→ک, half-space→space, lower case) is what task 2.2's search reads. Only the `Member` entity writes either, and always both, so they can't drift apart.
- **The first real domain entity.** `Member.Create` and `Update` return `Result` for rule failures (blank name, too long) and throw only for a caller's bug (a phone that wasn't normalized). Ten unit tests run without a database.
- **Check first, then let the index decide.** The handler asks "does this phone exist?" for a friendly 409. Six parallel creates can all pass that check, so the database's unique index decides, and `AppDbContext` turns its error into `UniqueConstraintException` so the losers get the same 409. A mutation check showed they got 500s without that translation.
- **Optimistic concurrency across a whole form.** `xmin` alone protects only the milliseconds between a request's read and write. Returning `Version` with the member, and requiring it back on update, protects the minutes a receptionist spends editing: if someone saved in between, the edit is refused instead of silently erasing their change.
- **Invisible characters need visible source.** A literal Arabic ي looks exactly like Persian ی, and editing tools quietly turned `\u064A` escapes into the character itself. Domain code and tests now write them as code points, `(char)0x064A`, which no tool rewrites and every reviewer can read.

## 2.2 — Member queries and lifecycle

- **Read side vs. write side.** Queries use `AsNoTracking()` and `Select(MemberResponse.Projection)`. The projection is an `Expression`, so EF Core turns it into SQL that reads only those columns and builds no tracked entities. Writes still load the entity and call its methods.
- **One search box, two searches.** The handler decides from the input: only digits, `+`, spaces and dashes means a phone search, anything else a name search. Both sides are normalized the same way before comparing, so "علي" finds "علی" and `۰۹۱۲…` finds `+98912…`.
- **Trigram indexes.** A B-tree index can't help `LIKE '%احم%'`, because the match can start anywhere. `pg_trgm` splits text into three-character pieces, and a GIN index over those pieces can find a match in the middle of a name or a phone number.
- **Escape user input inside patterns.** In `LIKE`, `%` and `_` are wildcards. Without escaping, a search for `%%` would list every member. It's the same idea as SQL injection, one level down.
- **Stable paging.** Sorting only by name lets two "علی"s swap places between two page requests, so one shows twice and the other never. Adding `Id` as a tie-breaker gives every row a fixed position.
- **An action that repeats safely.** Deactivating an already inactive member just succeeds. EF Core sees nothing changed, so it writes nothing, not even an audit row. A double-click or a retry after a network error can't do harm.
- **Where tests found real details.** `timestamptz` keeps microseconds while .NET keeps 100 ns, and the snake-case convention quietly renamed an index. Both are now in the Gotchas in ARCHITECTURE.md.

## 2.3 — UI: members

- **State in the URL.** The search text, page and filter live in the query string, not only in React state. Refresh, back from a profile, and a copied link all show the same results. Typing uses `replace` so the back button doesn't step through every pause; paging and filters push, so back undoes them.
- **Debouncing a call, not a value.** `useDebouncedCallback` waits until typing pauses for 300 ms, then writes the URL once. An effect watching a debounced value would also re-run whenever its other dependencies changed, like `setSearchParams`, which changes on every navigation.
- **Adjusting state during render.** When the URL changes from outside (back button), the search box follows it with `if (q !== shownQ) { … }` in the render itself, React's documented pattern. An effect would first paint the stale text.
- **Two layers of validation.** Zod catches blanks and lengths instantly, with the same Persian messages as the API's codes. Only the server knows whether a phone is a real Iranian mobile or already taken, so those codes are routed to the phone field (`codeFields`).
- **Optimistic concurrency, visible.** The edit form sends back the `version` it was filled from. On `Members.ChangedConcurrently` the page explains and offers to load the colleague's version. The form is keyed by `version`, so React rebuilds it with the fresh values.
- **Cache after a change.** A mutation puts the server's answer straight into the profile's cache entry and invalidates the lists, so a renamed member never keeps the old name in search results.
- **Bidi in practice.** In a right-to-left paragraph, `۰۹۱۲ ۱۲۳ ۴۵۶۷` is laid out as `۴۵۶۷ ۱۲۳ ۰۹۱۲`. Wrapping it in `dir="ltr"` keeps the groups in order.

## 3.1 — Plans API

- **Two groups, one prefix, two policies.** `/api/plans` is mapped twice: a read group with `StaffOrOwner` and a write group with `OwnerOnly`. Every endpoint gets its policy from the group it lives in, so a new write endpoint can't be added without the Owner check. Staff still see plans, because they sell them.
- **Null that means something.** `SessionCount` is `int?`: null is "unlimited". A magic value like 0 or -1 would be a number every caller has to remember isn't a number; `null` makes the compiler remind them. `IsUnlimited` names the meaning and is ignored by EF Core.
- **Money is exact.** `decimal` in C#, `numeric(18,2)` in Postgres. A price with three decimals is refused, not rounded, because silently changing an amount nobody typed is the kind of bug you find in an audit.
- **A rule with one home, used later.** "Inactive plans cannot be sold" is `plan.EnsureCanBeSold()`. There is nothing to sell yet; task 4.2 will call it instead of checking `IsActive` itself, so the rule can't be implemented twice slightly differently.
- **Validator and entity share one source.** The limits are constants on `Plan`, and `PlanRules` uses the same constants and error codes (even `Plan.CheckPrice`). The form gets field-level messages, and the entity still refuses bad values if a caller skips validation.
- **The database repeats the rules.** Check constraints (`BETWEEN 1 AND 365`, `price >= 0`, `session_count IS NULL OR …`) and a unique index on the normalized name. Tests insert bad rows with raw SQL to prove the database refuses them by itself.
- **Unique in normalized form.** Uniqueness is checked on `NormalizedName`, not `Name`, so "ویژه" typed with an Arabic ي is the same plan. Check first for a friendly 409, and let the unique index settle the race (the parallel-create test).

## 3.2 — UI: plans

- **Guards are UX, the API is security.** The three plan routes are wrapped in `RequireRole role="Owner"` (now through a small `ownerOnly()` helper, also used for staff) and the menu item has `role: "Owner"`. A staff user who types `/plans` sees "no access" and no request is sent. The API's `OwnerOnly` group would refuse them anyway.

The form keeps the price as text and sends it as a JSON string (`"price": "1500000.50"`). ASP.NET reads a string straight into `decimal`, and a new integration test proves it (`CreatePlan_PriceAsJsonString_IsStoredExactly`).

## 4.1 — Subscription domain model

- **Snapshot at the sale.** A subscription copies `PlanName`, `Price`, `DurationDays` and `TotalSessions` from the plan when it is sold. Editing or deactivating the plan afterwards changes nothing, like a receipt that keeps the price it was printed with. A test edits the plan after the sale to prove it.
- **Calculated, never stored.** `GetStatus(today)` works the status out from the dates, the sessions, the freeze and the cancel. A stored status would be wrong the morning after a subscription expires, until some job rewrote it.
- **Precedence as code.** When two statuses apply at once (frozen *and* past the end date), a fixed order decides: Cancelled, Frozen, Upcoming, Expired, Exhausted, Active. The `if` chain in `GetStatus` is that order. A test per pair pins it, and breaking the order on purpose showed the tests catch it.
- **"Today" is a parameter.** The entity never reads a clock. It receives a `DateOnly` in the gym's time zone, so a test can place it on any day. The tests use `FakeTimeProvider` to show why the time zone matters: at 20:30 UTC on 30 September it is already 1 October in Tehran (UTC+03:30), so the subscription has expired.
- **An inclusive end date.** `EndDate = StartDate + DurationDays - 1`. A one-day plan starts and ends on the same day. Off-by-one bugs in dates hide exactly here, so both edges (the end date itself and the day after) are tested.
- **Errors that say why.** Using a subscription fails with a different code per status (`NotStarted`, `Expired`, `NoSessionsLeft`, `Frozen`, `Cancelled`), because at the front desk each one is a different conversation with the member.
- **A limit that never traps anyone.** A freeze longer than the remaining allowance still ends. `Unfreeze` just caps the extension at the days left and returns how many days it added, so task 4.3 can move queued subscriptions by exactly that amount.
- **Bugs throw, users get `Result`.** A blank cancel reason is a user mistake, so it returns an error. Unfreezing on a date before the freeze began can only be a bug in the caller, so it throws.

## 4.2 — Assign and renew

- **A rule the database guarantees.** "A member never has two subscriptions covering the same date" is an **exclusion constraint**: `EXCLUDE USING gist (member_id WITH =, daterange(start_date, end_date, '[]') WITH &&) WHERE (cancelled_at IS NULL)`. A unique index can only compare equal values; an exclusion constraint compares with any operator, here "same member *and* overlapping dates". `btree_gist` lets a GiST index handle the plain `member_id` column. EF Core can't express this, so it's hand-written SQL in the migration.
- **What the race test found.** Six parallel sales for one member failed with 500. With the constraint deferred, each transaction waited at commit for another's uncommitted row, in a circle: a **deadlock** (40P01). Running the test ten times caught it 2 times out of 10. A race test that passes once proves little.
- **Take turns, don't fight.** The fix is a row lock: the sale opens a transaction and runs `SELECT … FOR UPDATE` on the member first. A second sale for the same member waits, then reads the first one's subscription and queues after it, so all six succeed. The constraint stays as a safety net. Removing the lock made the test fail 3 out of 3 times, which proves the lock is what fixes it.
- **Deferred vs immediate.** A deferred constraint is checked at `COMMIT`, and its error arrives from the commit itself, not wrapped in `DbUpdateException` like other save errors. It's now `DEFERRABLE INITIALLY IMMEDIATE`: checked on every write, but task 4.3 can defer it inside its own transaction when unfreezing moves several subscriptions at once.
- **"Today" has one owner.** `IGymCalendar.Today()` turns `TimeProvider` plus `Gym:TimeZone` into a Tehran date. A misspelled time zone stops the app at startup (`ValidateOnStart`) instead of quietly expiring subscriptions 3.5 hours late.
- **Shared logic without a framework.** Assign and renew differ only in *which* plan. `SubscriptionSeller` is a plain injected class holding the common part (lock, schedule, create, save), and the two handlers stay small.
- **The foreign key is the last word.** `ON DELETE RESTRICT` means a member or plan with sales can never be deleted, even by hand. It reports SQLSTATE 23001, not 23503, which the test found.
- **My notes:**

## 4.3 — Freeze, unfreeze, cancel endpoints

- **One row vs. several rows.** Freeze and cancel each change one field on one subscription, so the `xmin` token from task 4.2 is enough: a concurrent second write just fails with `DbUpdateConcurrencyException`. Unfreeze can change *several* subscriptions' dates at once (the one unfrozen, plus everything queued behind it), so it needs the member lock too — the same reason `SubscriptionSeller` takes it.
- **Deferring a constraint on purpose.** Moving a chain of date ranges later has to pass through a moment where the old, not-yet-shifted ranges overlap the new ones — if row A is updated before row B, A's stretched range briefly overlaps B's old one. `SET CONSTRAINTS ex_subscriptions_no_overlap DEFERRED` tells Postgres to check the exclusion constraint once, at `COMMIT`, after every row in the transaction is consistent, instead of after each `UPDATE`. This is exactly what the `AddSubscriptions` migration's comment (written in task 4.2) was waiting for.
- **Commit can fail too.** A deferred constraint's violation surfaces from `transaction.CommitAsync()`, not from `SaveChangesAsync()`, and it isn't wrapped in `DbUpdateException` the way an immediate one is. `IAppDbContext.CommitTransactionAsync` exists just to catch that raw `PostgresException` in Infrastructure (the only project allowed to know about Npgsql) and re-throw the same `ExclusionConstraintException` the immediate path already throws, so the handler's `catch` doesn't care which path it came from.
- **A second `IOptions<T>` on the same section.** `Gym:MaxFreezeDaysPerSubscription` sits in the same `"Gym"` configuration section as `Gym:TimeZone`, but it's bound by its own `SubscriptionPolicyOptions`, not added to `GymCalendarOptions`. Two small, single-purpose Options types reading the same section beat one growing type that answers unrelated questions.
- **The entity still only knows how to move.** `Subscription.ShiftQueued(days)` moves `StartDate` and `EndDate` together; it has no opinion on *which* subscriptions should be shifted or why. `UnfreezeSubscriptionHandler` decides that (same member, not cancelled, starts after the original end date) — the same split as `SubscriptionSchedule.NextStartDate` in task 4.2: the entity enforces the rule, the Application layer decides who it applies to.

## 5.1 — Lockers API

- **A fact the entity can't look up, so it's a parameter.** `Locker.MarkOutOfService(isOccupied)` needs to know whether the locker is occupied, but Domain has no EF Core reference and cannot query Attendance itself. The caller (the handler, which *can* query) works it out and passes it in — the same shape as `Subscription.ConsumeSession(today)` taking today's date instead of reading a clock.
- **Derived, not stored, and not fakeable either.** BUSINESS_RULES.md §6 says occupancy is derived from an open attendance, never stored. Task 5.2 hasn't added Attendance yet, so today there is no way for any locker to be occupied — `IsOccupied` is hardcoded `false` in `LockerResponse`, with a comment explaining that's the *correct* answer right now, not a placeholder being left broken.
- **One mapping, two shapes.** `LockerResponse.From(Locker)` builds the response from a tracked entity (used after a write); `LockerResponse.Projection` is the same mapping as a `LINQ` expression tree, which EF Core translates straight to SQL for reads (`GetLocker`, `ListLockers`) so the database returns only the columns needed instead of whole rows.
- **The same two race guards, a third time.** Duplicate locker numbers and concurrent edits reuse exactly the patterns from Members and Plans: check first for a friendly error, then catch the unique-index violation (`UniqueConstraintException`) for the race the check can't close; `xmin` (exposed as `Version`) catches a concurrent status change (`DbUpdateConcurrencyException` → `Lockers.ChangedConcurrently`). Writing it a third time is what turns a solution into a habit.
- **A check constraint the entity already enforces.** `Locker.CheckNumber` rejects non-positive numbers before anything touches the database; the migration adds `ck_lockers_number_positive` as well, so a hand-written `INSERT` can't sneak one past application code. A test inserts one directly with raw SQL to prove the database, not just the app, refuses it.
- **The frontend error catalogue is a real test, not a suggestion.** Adding `Lockers.*` error codes without a matching Persian entry in `web/src/lib/errors.ts` fails `ErrorCatalogTests` on the .NET side — a reflection-based test that lists every `Error` in Domain/Application plus every FluentValidation code and checks the frontend file mentions each one. It caught the omission here.

## 5.2 — Check-in

- **A placeholder from last task became real, not a new decision.** Task 5.1 hardcoded `LockerResponse.IsOccupied` to `false` because Attendance didn't exist yet. Adding Attendance here means that hardcoding was no longer the accurate answer — `LockerResponse.Projection` changed from a static field to a method that takes the open attendances as an `IQueryable<Attendance>` and closes over it in the expression tree, so EF Core still translates the whole thing to one SQL query with a correlated `EXISTS` subquery. `SetLockerOutOfServiceHandler` got the same fix: the `isOccupied` it feeds to `Locker.MarkOutOfService` is now a real query, not a hardcoded value. A pattern from 5.1's own learning note repeated: a column or field can exist a task before the feature that fully uses it, as long as the note says why.
- **A filtered index instead of an exclusion constraint.** Subscriptions needed a hand-written exclusion constraint (task 4.1/4.2) because "no two date ranges overlap" isn't expressible in EF Core's fluent API. "At most one *open* row per member" is simpler: `checked_out_at IS NULL` is an ordinary filter condition, so `HasIndex(...).IsUnique().HasFilter("checked_out_at IS NULL")` is enough, and Postgres enforces it exactly like any other unique index — no raw SQL in the migration, no deferred-constraint machinery.
- **A column before the feature that mutates it.** `Attendance.CheckedOutAt` exists from this task and is never set by any code in it — check-out and cancel are task 5.3. It has to exist now because both partial unique indexes filter on it; without the column there's nothing to filter on. Same reasoning as `Locker.IsOutOfService` existing before task 5.1 had a UI for it, just one layer earlier (schema before behavior, instead of behavior before UI).
- **Reusing a lock for a reason that wasn't originally about check-in.** `IAppDbContext.LockMemberAsync` was built in task 4.2 so two subscription sales for the same member can't both read the same calendar. Check-in needs the identical guarantee for a different reason — two check-ins can't both consume the last session — so `CheckInHandler` opens a transaction and takes the same lock before touching the member's subscriptions. The lock is about "changes to this member happen one at a time," not about subscriptions specifically, so it was already the right tool.
- **Reusing `ConsumeSession`'s errors instead of inventing new ones.** Check-in's precondition is "has an Active subscription," but the roadmap's own test list names specific reasons a subscription might not qualify: expired, frozen, exhausted. Rather than re-deriving those as new `Attendance.*` codes, the handler picks the member's latest non-cancelled subscription and calls `subscription.ConsumeSession(today)` — the same method `Subscription` already exposes — and returns whatever `Result` it produces. One rule, enforced in one place, told to two different call sites (selling a subscription and using one).
- **No `Result` on `Attendance.CheckIn`.** Every other `Create`-style factory in this codebase (`Locker.Create`, `Subscription.Create`) returns `Result<T>` because it checks a field-level invariant. `Attendance.CheckIn` has none — every precondition it depends on (member active, subscription active, no open attendance) is a fact about *other* entities that Domain cannot look up, so it's checked in the handler before `CheckIn` is ever called. The entity just records what already passed.

## 5.3 — Check-out, cancel, lists

- **One field closes two different stories.** `Attendance.Cancel` sets both `CancelledAt` *and* `CheckedOutAt` to the same moment. `CheckedOutAt` is what the partial unique indexes and every occupancy query (`LockerResponse.Projection`, the "currently inside" list) actually filter on, so a cancelled visit has to look closed to all of them without teaching each query a second condition. `CancelledAt` alone answers a narrower question — *why* it closed — for the one place that cares (the member's own history).
- **Resource address depends on whether the resource exists yet.** Check-in stays posted under the member (`POST /api/members/{id}/attendance/check-in`) because there's nothing to address until it returns one. Check-out and cancel address the attendance directly (`POST /api/attendance/{id}/check-out`) once it exists, the same split `SubscriptionsEndpoints` already made between selling (posted under the member) and freeze/unfreeze/cancel (addressed by the subscription's own id).
- **"Who and when" doesn't always need its own column.** BUSINESS_RULES.md says cancelling "marks the attendance cancelled (who and when)." *When* is `CancelledAt`, a real column, because the domain rule (the cancel window) needs it. *Who* is already on every entity for free — `Entity.UpdatedBy`, stamped by `AuditableEntityInterceptor` from `ICurrentUser` — so no `CancelledByUserId` was added. `Subscription.Cancel` made the identical call in task 4.1; this is the second time it came up, which is what makes it a pattern rather than a coincidence.
- **A second method on an interface that only had one.** `IGymCalendar` existed to answer "what day is it" (`Today()`). Filtering `Attendance.CheckedInAt` — a UTC moment — by a `DateOnly` range needed the inverse operation, turning a business day back into a UTC moment (`StartOfDayUtc`). It belongs on the same interface because it's the same responsibility (the one place that knows `Gym:TimeZone`), not a new concern bolted on.
- **Deliberately not adding concurrency protection here.** Every other mutable entity (`Member`, `Plan`, `Subscription`, `Locker`) carries an `xmin`-backed `Version`. `Attendance` still doesn't, even though `CheckOut` and `Cancel` are its first mutations. The roadmap gives concurrency races for this exact feature their own task (5.4: "two parallel check-ins... fix any issues found"), so adding a guard now would be solving a problem before the task whose job is to go looking for it. Task 5.2's member lock was different: double-consuming a session was 5.2's own correctness requirement, not a race deferred to later.
- **Two aggregates, one `SaveChangesAsync`.** Cancelling loads and mutates both an `Attendance` and its `Subscription` in one handler, then calls `SaveChangesAsync` once. No explicit `BeginTransactionAsync`: EF Core already wraps a single `SaveChangesAsync` in one database transaction, so both writes commit together or neither does, without reaching for the heavier transaction+lock pattern `CheckInHandler` needed for a different reason (serializing two *concurrent requests*, not two writes in the same request).
- **An ambiguous business rule, asked rather than guessed.** BUSINESS_RULES.md excludes cancelled attendances from "attendance reports" (§7, §12), but 5.3's own member-history endpoint isn't the Phase 9 report the rule was written for. Rather than write another "decided by Claude, pending review" note, this one was asked directly: history includes cancelled visits, marked by `CancelledAt`, because it's an operational audit view of one member, not a statistic. The difference from the standing "decided while away" notes elsewhere in BUSINESS_RULES.md is that the developer was here to ask.
- **A cross-field FluentValidation rule.** `From <= To` isn't a per-property rule, so it's `RuleFor(query => query)` with a `.Must(...)` over the whole record, plus `.OverridePropertyName(nameof(To))` so the 400 response still points at a sensible field — the same trick `CreateStaffValidator` already used for a full-name check that depends on more than one input.

## 5.4 — Concurrency tests

- **A lock can turn a race into an ordinary business rule.** The roadmap expected "two parallel check-ins for the same member... one gets 409," but tracing `LockMemberAsync` shows the second request physically blocks at `SELECT ... FOR UPDATE` until the first commits — by the time it wakes up, it just sees an already-open attendance and returns the same `Attendance.AlreadyCheckedIn` (422) as two *sequential* calls would. The database's unique index (which would answer 409) never gets a chance to fire, because the lock already resolved the conflict one layer up. Two different-looking outcomes — "prevented" and "detected" — are really the same safety net working at two different points, and a concurrency test has to trace which one a given precondition actually reaches.
- **No lock at all is sometimes the right call, if something else catches the miss.** The free-locker query in `CheckInHandler` takes no lock — two different members' check-ins never serialize against each other — so two transactions can both see the same locker as free before either commits. That is the genuine race: whichever `INSERT` loses hits the partial unique index on `locker_id` and the handler's existing `catch (UniqueConstraintException ...)` turns it into `Attendance.ChangedConcurrently` (409). Locking every locker row would remove the race but serialize unrelated members' check-ins for no reason; catching the constraint violation costs nothing until two people actually grab for the same locker at once.
- **A concurrency test can pass for the wrong reason.** `ShouldAllBe(status == Created || status == Conflict)` is true even if the race never actually happens in a given run — every response could just come back `Created` because the six requests happened to interleave without ever colliding. Before trusting the test, it was run several times with the status codes captured to a file: every run produced exactly one `Created` and five `Conflict`s, confirming real parallel HTTP requests against the Testcontainers Postgres instance genuinely overlap enough to hit the index, not just that the assertion is loose enough to always pass.
- **This task's "fix any issues found" had nothing to fix.** Both races were already handled correctly by code written in 5.2 (the member lock, and the `UniqueConstraintException` catch block) — 5.3's own learning note even predicted this task by name when it explained why `Attendance` deliberately has no `xmin` column yet. Writing the tests here didn't change behavior; it turned an implicit design decision into an explicit, regression-proof guarantee. A concurrency task doesn't have to find a bug to be worth doing.

## 5.5 — Background jobs

- **A job persisted in the database survives what an in-process timer doesn't.** A `Timer` or `IHostedService` loop forgets everything the moment the process restarts — if the API redeploys at 22:58, a 23:00 in-memory schedule never fires. Hangfire writes the job's *definition* to Postgres (`RecurringJob.AddOrUpdate`) and a separate polling loop reads it back, so the schedule survives restarts and deploys. This is the same reasoning refresh tokens are rows instead of server memory (task 1.3): anything that must outlive one process belongs in the database.
- **Cron needs a time zone, not just a time.** `Gym:ClosingTime = 23:00` alone is ambiguous — 23:00 in what frame? `RecurringJobOptions.TimeZone` (built from the same `IGymCalendar.TimeZone` that already computes "today") is what makes Hangfire fire at 23:00 *Tehran* time regardless of the server's own clock, the identical problem `GymCalendar.Today()` solved for business dates in task 0's very first ADR-adjacent decision.
- **A second interface gains a member for a caller nobody expected yet.** `IGymCalendar` had `Today()` and `StartOfDayUtc()`, both consumed by request handlers. Nothing in Application needed the raw `TimeZoneInfo` until the job *scheduler* — infrastructure code that runs once at startup, not a use case — needed to hand it to Hangfire. Same interface, same responsibility ("the one place that knows `Gym:TimeZone`"), a caller in a different layer.
- **A background job goes through the same audit path as everything else, on purpose.** `AutoCheckoutHandler` loads open attendances as tracked entities and calls `SaveChangesAsync`, instead of a faster set-based `ExecuteUpdateAsync`. The set-based version would silently skip `AuditableEntityInterceptor` (which stamps `UpdatedBy`) entirely, because it issues raw SQL outside the change tracker. The interceptor's own doc comment already anticipated this: "`ICurrentUser` is null for rows written by... background jobs, which act on nobody's behalf" — so `UpdatedBy = null` is the *correct*, already-designed-for answer, not a gap to work around.
- **One database, two schemas.** Hangfire's own job-queue tables live in a `hangfire` schema instead of the app's `public` one. Not a style preference: the integration test harness's Respawn reset is scoped to `SchemasToInclude = ["public"]` specifically so a per-test cleanup can never touch infrastructure bookkeeping it doesn't own — the schema split is what makes that scoping safe to add here without either tool needing to know about the other.
- **A design decision walked back within the same session.** The Hangfire dashboard was first mapped alongside Scalar with `.AllowAnonymous()` reasoning applied only in a code comment, not in code — `UseHangfireDashboard` is old-style branch middleware (matches on `HttpContext.Request.Path` directly), not a routed endpoint, so there is no `IEndpointConventionBuilder` to call `.AllowAnonymous()` on. It still got routed through `UseAuthorization()`'s fallback policy and answered 401. A quick manual smoke test (`curl -i /hangfire`) caught it before calling the task done; the fix was to move the mapping *before* `UseAuthentication`/`UseAuthorization` in the pipeline, so it never reaches the fallback policy at all. Lesson: a conditional environment gate and an authorization bypass are two different things, and only one of them was actually written at first.
- **A real business-rule gap, not a hypothetical one.** BUSINESS_RULES.md §0 listed `Gym:ClosingTime` as "still to decide" before this task started — the roadmap needed it and the docs said to ask, so the developer picked 23:00 Asia/Tehran before any code was written, and the decision was recorded back in BUSINESS_RULES.md's "Decided values" list the same way `MaxFreezeDaysPerSubscription` was in task 4.1.
- **"Restricted to Owner" was scoped down, deliberately and visibly.** The JWT-bearer-only auth model has no way to authenticate a plain browser navigation to `/hangfire` (no session cookie, no ambient credential) — solving that properly (a query-string token bridge, or a second cookie-auth scheme just for this one route) was judged bigger than this task's actual size. The dashboard is Development-only for now, the same gate Scalar and OpenAPI already use, and the roadmap checkbox says so explicitly rather than silently claiming full compliance.

## 5.6 — UI: front desk

- **Generated types are a snapshot, not a live view.** `web/src/lib/api/schema.d.ts` still described check-in-only Attendance from task 5.2 — three tasks and a dozen fields out of date, because nothing had re-run `npm run gen:api` since. The generator needs the API actually *running*; it's easy to finish a backend task, commit, and forget the frontend has no way to know the contract changed until someone tries to use it. The type system caught it immediately once this task started (`AttendanceResponse` had no `checkedOutAt` to read), which is the whole point of generating types from the OpenAPI document instead of hand-declaring them — a stale contract is a compile error, not a runtime surprise.
- **A shared presentational table takes a callback, not a hook.** `MembersTable` grew an optional check-in column (`onCheckIn`/`checkingInId`) rather than calling `useCheckIn()` itself, the exact shape `PlansTable` already used for `onToggleActive`/`busy`. The table stays a pure function of props either way; the host page (`HomePage`) owns the mutation and decides what "one-click check-in" even means on that screen, while `MembersPage` — the full directory, not the front desk — passes nothing and gets no check-in column at all, for free.
- **A cache invalidation that crosses a feature boundary, done explicitly.** Checking in doesn't just change attendance — it changes locker occupancy too, a different feature's cache. `features/attendance/api.ts` imports `lockerKeys` from `features/lockers/api.ts` and invalidates both after every mutation. The alternative (a generic "refetch everything" or a shared event bus) would hide *why* two features are coupled; the import makes the coupling a fact the compiler enforces, not a comment hoping someone remembers.
- **The same field read twice for two different questions.** "Is this member currently inside?" has no dedicated endpoint — it's answered by reading the *first* row of the member's own attendance history (already sorted newest-first by the API) and checking whether `checkedOutAt` is still null. One `GET .../attendance` call serves both the profile's "currently inside" banner and its history table below it, instead of two requests asking almost the same question.
- **Scope trimmed twice, both times on purpose and both times written down.** Attendance history became a second stacked `Card`, not a real `<Tabs>` component — that pulls in `@radix-ui/react-tabs`, off the approved list, for one screen that doesn't need real tab-panel semantics. Locker creation became one inline number field on `LockersPage`, not a separate `/lockers/new` route with React Hook Form and Zod, because Members and Plans need that machinery for multi-field forms with cross-field rules and this one doesn't. Neither shortcut was silent: both are named in the plan and in this note, the same way `AttendancePolicy`'s Development-only dashboard was named in task 5.5.
- **"Attempt, then explain" beats duplicating a business rule in the client.** The cancel-check-in window (30 minutes) and a locker's occupied-while-out-of-service rule are both enforced only server-side; every button that could hit either one is always shown, always clickable, and a rejection just surfaces the server's own Persian message through the same notice pattern every other mutation on this page uses. Teaching a form to also know `Gym:CancelCheckInWindowMinutes` would be a second copy of a rule that already lives in `Attendance.Cancel`, guaranteed to drift the day someone changes one without the other.
- **A test suite can prove a feature works without a browser.** This session's Chrome extension wasn't connected, so there was no literal click-through — but 23 new Testing Library tests render the *actual* `CurrentlyInsidePage`, `MemberProfilePage` and `LockersPage` components into real jsdom, fire real clicks, and assert on what a person would actually see, against a mocked network boundary. That is meaningfully different from a type-check passing: it is proof the UI text, the button labels and the state transitions are correct, just not proof of pixels. The dev server and Vite's `/api` proxy were confirmed serving and forwarding correctly against the real backend; what wasn't done was an authenticated interactive walkthrough, and the roadmap says so rather than implying more coverage than there is.
- **A button label collided with one that already existed.** The check-out button was first named "خروج" — identical to `AppShell`'s sign-out button — and `getByRole("button", { name: "خروج" })` matched both, failing a test with "multiple elements found" the moment it ran. Renamed to "ثبت خروج" ("record check-out"). A small reminder that accessible names are a shared namespace across the whole rendered page, not just within one component.

## 6.0 — Deployment decisions (planning session, no production code)

The question that started this was whether a gym that is entirely internal — Iranian server, Iranian SMS panel, members who never log in — breaks anything in the design. The answer was no: the application needed no change, but Phase 6 of the roadmap had been written against assumptions that turned out to be wrong, so this session rewrote Phase 6 and recorded the deployment shape as `docs/adr/0003-deployment-topology.md`.

- **"Does this break the architecture?" is answered by looking for external dependencies, not by reading the architecture.** The check was concrete: does any layer call a foreign service, does the frontend load anything from a CDN, does business logic read a clock the deployment controls? All three were already no — `client.ts` uses `window.location.origin`, fonts are self-hosted by rule, "today" comes from `IGymCalendar`. Decisions made for other reasons (same-origin so cookies behave identically in dev and prod; self-hosted fonts so the build is reproducible) turned out to be exactly what a locally-hosted deployment needs. That is the usual shape of portability: it is the accumulated absence of ambient dependencies, not a feature someone adds later.
- **Capacity planning means finding the one number that binds.** The first version of this plan treated 5 GB of disk as the constraint and built the whole phase around slimming things down. The real figure was 50 GB, and the binding constraint turned out to be 2 GB of RAM instead. The plan changed shape completely — not because the conclusion "don't run Seq in production" changed, but because its *reason* did, and a reason recorded wrongly is a decision nobody can revisit correctly later. ADR 0003 says "rejected on memory" specifically so that adding RAM is recognisable as the thing that reopens it.
- **A reverse proxy is what makes "one origin" true in production.** Caddy serving the React build and proxying `/api` to the API is the production twin of the Vite dev proxy, and `vite.config.ts` says so in a comment written back in task 0.7. The payoff is that CORS stays a development-only safety net instead of something the application depends on, and the `SameSite=Strict` refresh cookie works in both places for the same reason rather than by coincidence.
- **A `Secure` cookie is a deployment requirement, not just a flag.** `RefreshTokenCookie` sets `Secure`, so a browser will not store or send it over plain HTTP to anything but `localhost`. That single line decides that production must be HTTPS — there is no "we'll add TLS later" path that does not also mean weakening authentication. Constraints that propagate outward from a security choice like this are worth noticing early, because they are cheap to satisfy when planning and expensive to discover during a go-live.
- **Automatic certificates need a name, not an address.** Let's Encrypt issues for domains through a challenge that proves you control the name; a bare IP has nothing to prove control of in the ordinary flow. This is why the plan spends a domain registration rather than deploying to `https://<ip>`, and why the earlier on-premise plan had reached for Caddy's `tls internal` instead — on a LAN with no public name, a private CA whose root you install on a handful of machines is the honest answer. Different topology, different correct answer.
- **Build where the RAM is.** `dotnet publish` and `npm run build` each comfortably exceed a gigabyte, and running one beside a live Postgres on a 2 GB host invites the OOM killer to pick a victim mid-deploy — possibly the database. Building on the development machine and shipping the image with `docker save`/`docker load` costs one extra step and removes an entire class of deploy-day failure. Note the reason is memory, not disk: with 50 GB the *space* was never the problem.
- **An EF migration bundle is a self-contained executable, so the server needs no SDK.** `dotnet ef migrations bundle --self-contained` produces one binary that applies the migrations and exits. The alternative — migrating at application startup — is convenient and already ruled out in ARCHITECTURE.md, because two API containers starting at once would race each other through the same migration, and a failed migration would leave you with an application that boot-loops instead of one that simply has not been upgraded yet.
- **Containers do not automatically have a time zone database or ICU.** `InvariantGlobalization=false` needs ICU to format Persian dates; `Gym:TimeZone = Asia/Tehran` needs tzdata to resolve at all. Debian-based .NET images carry both, Alpine does not. The good news is that the startup validation of `Gym:TimeZone`, added long before there was a container, makes this fail loudly: the app refuses to start rather than quietly computing "today" in UTC and expiring subscriptions a few hours early.
- **A proxy makes every client look like one client.** ASP.NET reads `RemoteIpAddress`, which behind Caddy is always Caddy. The login rate limiter would then put every user in one bucket, and `UseForwardedHeaders` is what restores the real address from `X-Forwarded-For`. This was already written down as a task 11.2 item; it moved to 6.2 because the severity depended on the topology — sharing a bucket among three staff on a LAN is a nuisance, but doing it on a publicly reachable login endpoint is a defect.
- **A dump is not a replica, and a backup is not a backup until it has been restored.** What the gym's flash drive will hold is a `pg_dump` file: bytes that *can* become a database, after a deliberate manual step nobody has practised. Calling it "a second database" would be comfortable and wrong, which is why task 6.3 has "restore rehearsed" as its own checkbox and its own "Done when". The failure mode being defended against is not losing the file; it is discovering on the worst possible day that the restore command was never run.
- **Direction of connection is decided by NAT, not by preference.** The server cannot open a connection to the gym's computer, because that machine sits behind a router with no inbound route to it. So the backup copy is *pulled* from the gym side on a schedule, not pushed from the server. Whenever one side of a link is publicly addressable and the other is not, the addressable side is the one that gets connected *to*.
- **Design an interface against the provider's real constraint, not the one you wish it had.** Iranian SMS panels generally require a pre-approved template for service messages: you send a template id and named parameters, not a sentence. An `ISmsSender` shaped as "send this string" would have to be rewritten the day the real provider was wired up in task 10.3. A template-first interface still works if the panel happens to allow free text, but the reverse is not true — so when two shapes are not symmetric in cost, pick the one that survives being wrong.
- **Log rotation without a new package.** Dropping Seq in production could have meant adding `Serilog.Sinks.File`, which CLAUDE.md would require asking about. It did not: Serilog already writes to the console, and Docker's `json-file` driver rotates that with `max-size` and `max-file`. Reaching for a dependency to solve a problem the platform underneath already solves is a habit worth catching.
- **My notes:**
