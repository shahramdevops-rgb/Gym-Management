## 0.1 — Repository and solution skeleton

- **The dependency rule:** Clean Architecture is enforced by which project may reference which, so `Gym.Domain` has zero references and every arrow points inward — this is why an entity can never call EF Core.
- **`Directory.Build.props`:** MSBuild walks up from each `.csproj` and imports the nearest one, so `Nullable`, `ImplicitUsings` and `TreatWarningsAsErrors` are declared once and cannot drift per project.
- **Layered props files:** MSBuild imports only the *nearest* `Directory.Build.props`, so `tests/Directory.Build.props` must import the root one explicitly with `GetPathOfFileAbove` before adding its test-only settings.
- **Central Package Management:** `Directory.Packages.props` holds every version and `.csproj` files reference packages by name only, so two projects can never disagree on a version.
- **`global.json`:** pins the SDK band (`10.0.401` + `rollForward: latestPatch`) so this machine and CI compile with the same compiler instead of silently diverging.
- **Warnings as errors:** cheap on day one and expensive later, because a codebase with 200 tolerated warnings is one where nobody reads warnings at all.
- **Analyzer rules vs project conventions:** CA1707 forbids underscores in member names, which contradicts the mandated `Method_Scenario_ExpectedResult` test naming; the fix is to scope the rule off for `tests/**` in `.editorconfig`, not to rename the tests or silence the rule globally.
- **Architecture tests:** `Assembly.GetReferencedAssemblies()` turns the dependency rule into an executable assertion, so a forbidden reference fails the test run instead of surviving code review.
- **Trade-off behind those tests:** they read *compiled* references, so they are weak while assemblies are near-empty and get stronger as code lands; the airtight alternative (parsing `.csproj` files) is more brittle, and a dedicated library such as NetArchTest is not on the approved list.
- **Microsoft Testing Platform:** the .NET 10 SDK dropped the VSTest bridge, so xunit.v3 test projects are executables hosting their own runner and `global.json` opts `dotnet test` in with `"test": { "runner": "Microsoft.Testing.Platform" }`.
- **`.gitattributes` and `.editorconfig` must agree:** git on Windows converts to CRLF by default, which would silently contradict `end_of_line = lf`; `* text=auto eol=lf` settles it for both the repo and the working tree.

## 0.2 — Local infrastructure

- **Environment as code:** `docker-compose.yml` turns "install Postgres and Seq" into a file under version control, so a new machine, a teammate and CI all get byte-identical infrastructure instead of following a wiki page that drifted.
- **Running is not ready:** Postgres accepts TCP connections seconds before it will accept queries, so `healthcheck` exists to distinguish *started* from *usable*. Task 0.6 depends on this: Testcontainers waits for a readiness signal rather than sleeping a guessed number of seconds.
- **A health check can only use tools the image actually ships.** The Seq image has neither `curl` nor `wget`, and its bundled `seqcli` is broken, so the probe is a hand-written HTTP request through one of bash's `/dev/tcp` sockets. The trade-off against the simpler "is the port open" check: an open port only proves something bound it, while a `200 OK` on `/health` proves Seq is actually serving.
- **Named volumes outlive containers:** the container is disposable and the volume is not, which is what makes `docker compose down` safe and `down -v` the deliberate destructive one.
- **The `postgres:18` mount point:** this image keeps `PGDATA` in a versioned subdirectory, so the volume mounts at `/var/lib/postgresql`. Mounting `/var/lib/postgresql/data` — correct for older tags, and what most tutorials still show — leaves the real data directory inside the container's writable layer, so the data silently disappears on every recreate.
- **Splitting a connection string:** everything non-secret is committed in `appsettings.Development.json` and only the password lives in user-secrets, under a separate `Postgres:Password` key. A configuration *value* cannot have child keys, which is why the password gets its own key instead of being layered onto the connection string; `AddInfrastructure()` recombines them with `NpgsqlConnectionStringBuilder` in task 0.3.
- **User-secrets are a `UserSecretsId` plus a file outside the repository** (`%APPDATA%\Microsoft\UserSecrets\<id>\secrets.json`). They are a development convenience and nothing more — production reads environment variables, because a developer's home directory is not a secret store.
- **Fail loudly on missing configuration:** compose's `${VAR:?message}` stops with that message instead of starting a database with an empty password. The trade-off is one extra setup step (`cp .env.example .env`) against never having a working credential committed by default — and defaults have a way of surviving into staging.
- **Guard tests for configuration:** the same value written in two files will eventually disagree, so `DevelopmentSettingsTests` reads the repository's own files and fails if `.env.example` and the connection string drift apart, or if a password ever appears in a committed file. It is a cheap executable version of a code-review rule nobody remembers to apply.
- **`dotnet test` forwards unknown arguments to the test application.** Under Microsoft Testing Platform there is no VSTest wrapper to absorb MSBuild-style flags, so `dotnet test --nologo` hands `--nologo` to the test app, which rejects it and reports "Zero tests ran" with exit code 5 — a build-succeeded, no-tests-found result that looks exactly like a discovery failure. Plain `dotnet test` works. The lesson generalises: when a runner reports zero tests but the test executable run directly passes, suspect the arguments before suspecting the packages.

## 0.3 — Persistence foundation

- **`IAppDbContext` is the seam, not a repository:** Application declares the contract and Infrastructure implements it, so the dependency arrow still points inward even though EF Core is doing the work. The trade-off for dropping `IRepository<T>`: Application references the EF Core *abstractions* (`DbSet<T>`, `SaveChangesAsync`) and gains full LINQ, but never references a provider — a wrapper around something that is already a repository and a unit of work would only have to re-expose LINQ to stay useful, and would cost a layer of indirection for nothing.
- **Why version 7 GUIDs:** a v4 GUID is random, so every insert lands at a random point in the primary key's B-tree and fragments it. `Guid.CreateVersion7()` puts a millisecond timestamp in the high bits, so ids sort by creation time and inserts append to the end of the index — the write pattern of an `int` identity, but generated in C# before the row is saved, which matters for assigning ids to related objects in one unit of work.
- **A `SaveChangesInterceptor` turns a convention into a guarantee:** forty use cases each remembering to set `UpdatedAt` is forty chances to forget. One interceptor underneath `SaveChanges` is zero. The general lesson: when a rule must hold for *every* write, put it below the write, not beside it.
- **Writing through the change tracker preserves encapsulation:** `entry.Property(e => e.CreatedAt).CurrentValue = now` reaches a **private** setter, because EF Core writes properties through its own accessors rather than through C# visibility. So the audit fields did not have to be made public for the interceptor's benefit, and CLAUDE.md's "entities have private setters" stays literally true.
- **Insert is not update:** `CreatedAt` is stamped only for `Added` entries and `UpdatedAt` only for `Modified` ones. Re-stamping `CreatedAt` on every save is the classic bug here — it passes a naive one-save test and silently destroys history in production, which is why there is a dedicated test for it.
- **One timestamp per save, not per row:** `GetUtcNow()` is called once and shared, so everything written in the same transaction agrees about when it happened.
- **snake_case as a convention, not a per-property attribute:** Postgres folds unquoted identifiers to lower case, so a `CreatedAt` column would have to be quoted forever. `UseSnakeCaseNamingConvention()` renames the whole model at once. Watch out: it also renames EF's own `__EFMigrationsHistory` columns.
- **An empty first migration is still worth having:** there are no entities yet, so `InitialCreate` creates only `__EFMigrationsHistory` — but it also fixes `AppDbContextModelSnapshot` as the baseline every later migration is diffed against, so task 1.1's Identity tables become a clean delta instead of one enormous first migration.
- **A health check should answer "can I do my job", not "am I running":** `AddDbContextCheck<AppDbContext>()` makes `/health` return `503 Unhealthy` when Postgres is unreachable. A process-only probe would let an orchestrator route traffic to an API that cannot serve a single request. Verified by stopping the container and watching the endpoint flip to 503 and back.
- **Design-time is a separate execution context:** `dotnet ef` builds and runs the startup project's host to find `AppDbContext`, and it reads `Properties/launchSettings.json` for environment variables. Without an `ASPNETCORE_ENVIRONMENT=Development` profile there, the migration commands run as Production and never see `appsettings.Development.json` or user-secrets. The global `dotnet-ef` tool also carries its own version and must be at least as new as the EF Core packages.
- **Fail loudly at startup, not at the first query:** `AddInfrastructure` throws with the exact `dotnet user-secrets set` command when no password is configured, instead of letting the first request die with a bare authentication error — the same reasoning as `${VAR:?message}` in `docker-compose.yml`.
- **You can test EF Core without a database:** building a model and tracking changes happen entirely in memory; a connection is opened only when a query or `SaveChanges` actually runs. So column naming, type mappings and the interceptor's behaviour are all testable with the *real Npgsql provider* and no Docker — which is not the same thing as the banned InMemory provider, whose whole problem is that it is a *different* provider with different semantics. Real database behaviour (constraints, concurrency, transactions) still needs Testcontainers, which arrives in task 0.6.
- **`FakeTimeProvider` is why `DateTime.UtcNow` is banned:** the interceptor's clock is injected, so a test can pin "created on 21 March" and "updated on 22 March" and assert exact values instead of asserting that something is "roughly now".

## 0.4 — API plumbing

- **Structured logging is not string logging:** `logger.LogInformation("Member {MemberId} checked in", id)` sends Seq a *property* called `MemberId`, not a sentence. That is why the request log line arrives with `RequestPath`, `StatusCode` and `CorrelationId` as queryable fields — and why Seq is in `docker-compose.yml` instead of a text file. Grep can find a string; only properties can answer "every 5xx for this member last week".
- **A correlation id reassembles a story from scattered lines:** one request produces log events from several layers, and without a shared id they are unrelated rows. ASP.NET Core already starts a W3C `Activity` per request and adopts an inbound `traceparent`, so the middleware *returns* that id rather than inventing one — verified by sending `traceparent: 00-4bf92f…-…-01` and getting `X-Correlation-Id: 4bf92f…` back. Inventing a second id would mean carrying two names for one thing.
- **Deferred header writes:** headers cannot be set once the response has started, and the request you most want to look up is the one that threw. So the id is registered in an `OnStarting` callback *before* calling the next middleware, not assigned after it returns.
- **A bootstrap logger covers the gap before the host exists:** anything thrown while the host is being built — including task 0.3's missing-password check — would otherwise die with no log line at all, which is exactly when a log line is worth most. `CreateBootstrapLogger()` writes to the console until the configured logger replaces it, and `try/catch/finally` around `app.Run()` with `Log.CloseAndFlush()` stops the buffered Seq events from being dropped on an abrupt exit.
- **Logging has a budget:** `/health` polled every ten seconds is 8,640 events a day that say nothing. `GetLevel` drops health probes to `Debug` while keeping 5xx at `Error`. Deciding what *not* to log is part of setting logging up — otherwise the signal drowns and people stop reading Seq at all.
- **Configuration over code for levels and sinks:** they live in `appsettings.json`, so turning production up to Debug for an hour is a config change, not a rebuild and a redeploy. Only what configuration cannot express stays in C#.
- **Config files merge by key, arrays merge by index:** so Serilog sinks are written as a keyed object (`"WriteTo": { "Console": … }`) and `appsettings.Development.json` adds `"Seq"` by name. With an array, Development could only add a sink by counting the entries in the base file — and would silently overwrite one if the count ever changed.
- **Culture leaks into logs:** the analyser refused `WriteTo.Console()` without an `IFormatProvider` (CA1305), and it was right in a way that matters here — this project sets `InvariantGlobalization=false` so the app can format Persian dates, so a machine set to `fa-IR` would write log timestamps and numbers in Persian digits that no query would match. Persian formatting is the frontend's job; logs are for engineers. A warning-as-error caught a real bug rather than being noise.
- **Environment-gated middleware:** Scalar and a credentialed CORS policy are development conveniences that would be a hole in production, so they are behind `IsDevelopment()`. That turns "do not ship the API explorer" into a property of the code rather than a deployment checklist item somebody has to remember.
- **`AllowAnyOrigin` and `AllowCredentials` are illegal together,** and for good reason: that pair would let any website on the internet call this API as the logged-in user. Origins are therefore listed explicitly, which is also why `AddVitePolicy` throws when the list is empty rather than starting with CORS quietly broken.
- **`TryAddSingleton` lets two layers declare the same dependency:** Application needs a clock for business dates and Infrastructure needs one for the audit interceptor, so both register `TimeProvider.System` and neither breaks when used alone or together. A plain `AddSingleton` twice would leave two registrations; a test asserts one instance comes back.
- **`ValidateOnBuild` and `ValidateScopes` move DI failures to the build:** registering a service and resolving it are separate events, so a missing registration normally surfaces on the first request that needs it, in production. Building the provider in a test with validation on finds it now — and `ValidateScopes` catches a singleton capturing a scoped `DbContext`, the bug that becomes a cross-request data leak rather than an exception.
- **Test doubles must actually do the thing:** `HttpResponseFeature.OnStarting` on a plain `DefaultHttpContext` is a no-op, because nothing is ever written to a socket. A test using it would have asserted on a header that was never going to be set either way — passing regardless of whether the middleware worked. `RecordingResponseFeature` records the callbacks and fires them where a real server would. The general lesson: a test that cannot fail is worse than no test, because it buys false confidence.

## 0.5 — Errors and validation

- **Expected failures are return values; exceptions are for the unexpected.** A signature of `Task<Result<MemberResponse>>` tells the caller this can fail and makes the compiler carry the failure along the same path as the success. An exception says nothing in the signature, costs a stack unwind, and — worse — makes "this phone already exists" indistinguishable from "the database is down". The trade-off: every caller must now unwrap a `Result`, which is exactly the point.
- **`Error` separates a code from a message.** `Code` (`Members.PhoneAlreadyExists`) is a published contract the Persian frontend maps in `lib/errors.ts`; `Description` is English prose for developers and logs. Because they are separate fields, rewording a message can never change what a member reads, and the API never has to speak Persian.
- **No `Error.None` sentinel.** The common tutorial design gives a success a blank error object; this one gives it none at all, and asking a success for its `Error` throws — the mirror of asking a failure for its `Value`. A blank error would otherwise travel on and be reported to the caller as a real failure with an empty code, which is a bug that surfaces far from where it was made.
- **One mapping table, in one place.** `ToHttpResult()` is the only code in the solution that picks a status code. If each endpoint chose for itself, "member not found" would be a 404 here and a 400 there and the frontend would need a special case per endpoint. This is also why `ErrorType` lives in the Domain but the status codes do not: a handler called from a Hangfire job in Phase 5 has no HTTP to speak of.
- **400 vs 422.** A 400 means the request is malformed — the form can point at the field that is wrong. A 422 means the request was fine and a rule in BUSINESS_RULES.md said no ("this subscription is expired"). The frontend reacts differently to each, so the distinction has to survive the trip.
- **An enum switch still needs a default arm.** Covering every declared `ErrorType` silences CS8509, but C# allows an enum to hold any underlying value, so CS8524 then demands a default — and with warnings-as-errors there is no way to have the compiler guard exhaustiveness here. The guard moved to a test that walks `Enum.GetValues<ErrorType>()`. General lesson: when the compiler cannot hold a rule, a test has to, and it is worth writing down which one does.
- **A 500 must leak nothing.** `GlobalExceptionHandler` returns a fixed sentence and a correlation id — never the exception message, type or stack. Messages carry connection strings, file paths and member names, and they help the reader with nothing; the id is the way back to the full exception in Seq. It also deliberately logs nothing, because ASP.NET Core's exception middleware and Serilog's request log already record it, and three copies of one event is how a log stops being read.
- **Validation is a filter, not the first fifteen lines of every handler.** `ValidationFilter<T>` short-circuits before the endpoint, so handlers can assume well-formed input and are left with the rules that actually need the database. It also means nothing was written on the way to a 400.
- **Where the filter lives is the dependency rule doing its job.** ARCHITECTURE.md originally put `ValidationFilter` in Application, but `IEndpointFilter` is an ASP.NET Core type and the layer test from task 0.1 fails the build on that reference. So the *validators* stay in Application (a command must be valid whoever sends it, including a background job) and only the HTTP shape of the answer moved to Gym.Api. An executable architecture rule caught a documentation error, which is the whole reason for writing those tests.
- **Field errors carry codes, not just sentences.** `Results.ValidationProblem` produces `errors: { field: ["message"] }` — English strings the Persian UI cannot use. This API returns `errors: { "phoneNumber": [ { code, description } ] }` instead, keyed by the JSON property name, so the frontend can attach a Persian message to the right input. The price is a non-standard `errors` shape, which is documented in ARCHITECTURE.md as part of the contract.
- **An assembly scan beats a registration list.** `AddValidatorsFromAssembly` picks up a new validator by its simply being there. A forgotten line in a manual list would not fail the build — it would silently disable validation for one endpoint, which is the worst way to find out.
- **Test the bytes, not the intent.** Asserting `result.ShouldBeOfType<ProblemHttpResult>()` tests what the code meant; `ExecutedResult.RunAsync` executes the `IResult` against a real `HttpContext` and asserts on the JSON that comes out — the casing, the field names, the extensions added by configuration. The frontend only ever sees the bytes.
- **A passing test can still be testing nothing.** The first "two rules on one field" test passed while only one rule was actually failing, so the grouping it claimed to check was never exercised. Worth re-reading a green test once and asking what would have to break for it to go red.
- **`InternalsVisibleTo` instead of widening the API.** The mapping tables are internal because no endpoint should call them; the test project gets access through the csproj rather than by making them public. Letting a test dictate the public surface is a small decision that compounds.

## 0.6 — Test harness

- **Two kinds of test, two kinds of bug.** A unit test asks whether a class is correct; an integration test asks whether the parts were plugged together. `WebApplicationFactory<Program>` starts the real `Program.cs` in process — real DI container, real middleware order, real routing — so it catches the bug a unit test structurally cannot see: a service registered with the wrong lifetime, a middleware nobody wired up, an endpoint that was never mapped. `CorrelationIdMiddlewareTests` proves the middleware works; only the `/health` test proves it is actually in the pipeline.
- **One assertion can cover a lot of seams.** For `/health` to return `Healthy`, the host must start, `AddInfrastructure` must build a working connection string, the migrations must apply, the endpoint must be mapped, and the health check must reach Postgres. Every item on that list is a seam between two things rather than a thing, which is exactly what unit tests cannot reach.
- **Why the InMemory provider is banned, concretely.** It is a *different* provider, not a fast Postgres: it ignores unique indexes, check constraints and concurrency tokens, so a green test there says nothing about the database that will actually reject the write. Testcontainers runs the same `postgres:18` image as production instead, on a random port, and deletes it afterwards.
- **Tests must not touch the development database.** The container is Testcontainers' own, never `gym-postgres` from docker-compose.yml — otherwise `dotnet test` would truncate the data you are looking at in the app. Worth checking explicitly for any harness: which database does this actually connect to?
- **Respawn instead of a fresh database.** Recreating a container or re-running migrations between tests would cost seconds each; truncating rows costs milliseconds. The price is one sharp edge: Respawn deletes *rows*, not tables, so `__EFMigrationsHistory` has to be ignored or the next run finds a fully migrated database that believes it has never been migrated. That is the failure `DatabaseHarnessTests` guards.
- **Collection fixture vs assembly fixture is a cost decision.** An assembly fixture would start Postgres for every run, including the ones that only exercise `Result` mapping in milliseconds. A collection fixture starts the container when the first database test asks for it and tears it down when the collection ends. The serial execution it forces is not a cost here — it is required, since a parallel test would have its rows deleted by another test's reset.
- **`WebApplicationFactory` cannot override configuration that was read before `Build()`.** This cost a debugging round: with minimal hosting, `Program.cs` calls `AddInfrastructure(builder.Configuration)` *before* `builder.Build()`, so the factory's `ConfigureAppConfiguration` delta arrives after the registrations have already read config — the app started with no connection string at all. Environment variables (`ConnectionStrings__Postgres`) are set before the host exists, and they are how production supplies the value too, so the test now travels the real path rather than a test-only hook. General lesson: to override configuration, you have to get in *earlier* than the code that reads it.
- **Environment `Testing`, not `Development`.** Scalar and the permissive CORS policy are development conveniences; a suite running with them on would not be testing the pipeline that gets deployed.
- **Warnings-as-errors keeps reaching into test code too.** CA1711 rejected `DatabaseCollection` (the `Collection` suffix is reserved for real collections) and CA1816 wanted `GC.SuppressFinalize` in an `IAsyncDisposable`. Renaming to `DatabaseCollectionDefinition` costs nothing — only the attribute name matters to xUnit.
- **A harness has to be testable itself.** If `DatabaseHarnessTests` breaks, every test built on the fixture is suspect, so the migration-applied check and the Respawn-configuration check are worth their weight. The probe table is created *before* its Respawner, because Respawn builds its delete plan from the schema it finds at creation time — asserting on the options object alone would have proved nothing.
- **Admitting what cannot be tested yet.** The ideal isolation test — test A inserts a member, test B sees an empty table — needs an entity, and the model has none until task 1.1. Writing a reassuring substitute would have been worse than leaving a note to add the real one then.

## 0.7 — Frontend skeleton

- **Generated API types are a compile-time contract.** `npm run gen:api` turns the API's OpenAPI document into `schema.d.ts`, and `openapi-fetch` only accepts paths and bodies that exist in it. When a backend field is renamed, `npm run build` fails instead of a screen quietly showing `undefined`. The trade-off is one more step after every endpoint change (regenerate and commit), which is why CLAUDE.md lists it as a command.
- **A dev proxy means one origin, like production.** The browser only talks to `localhost:5173`, and Vite forwards `/api` and `/health` to the API. Behind Caddy in production it is the same shape, so cookies and relative URLs behave identically in both places and CORS is never something the app relies on.
- **Server state belongs in TanStack Query, not in `useState`.** `useQuery` owns loading, error, retry, caching and refetching. A component only describes *what* it needs (`["health"]`, `fetchHealth`) and renders the three states. There is no hand-written `useEffect` + `fetch` + flags that could get out of sync.
- **"Unhealthy" is an answer, not a failure.** `/health` returns 503 with the body `Unhealthy` when the database is down. Treating every non-2xx as an error would show "server unreachable" exactly when the server is reachable and trying to tell you something. The test for this was checked by temporarily adding the tempting `if (!response.ok) throw` and watching it go red.
- **RTL works in three layers.** `<html dir="rtl">` is set before JavaScript runs, so there is no flash. Radix `DirectionProvider` exists because Radix computes placement and keyboard direction in JavaScript and does not read the `dir` attribute. And logical utilities (`border-e`, `ps-`) are enforced by an ESLint rule: the navigation is on the right because it comes first in a right-to-left row, not because anything says "right".
- **A business date is a day, not a moment.** `"2026-09-17"` is formatted in UTC so the day it names can never shift. A timestamp is formatted in `Asia/Tehran` so 21:00 UTC shows as 00:30 on the *next* Jalali day. Mixing these two up is the classic off-by-one-day bug.
- **Honest tests, again.** A "never shifts the day" test for dates passed with both the old and the new code, because Tehran is ahead of UTC and can't show the bug. It was renamed to what it actually checks instead of being kept as reassurance.
- **Invisible characters belong in escapes.** ZWNJ, Arabic ي and Persian ی look identical or invisible in an editor, so source code and tests write them as `\u200C`, `\u064A` and `\u06CC`. ESLint rejects literal ones, and the reviewer can see which code point is meant.
- **Normalization is a business rule, not a helper detail.** Treating half-space and space as the same, and stripping harakat and tatweel, decide which members a search finds. That is why these rules were written into BUSINESS_RULES §13 before the code was changed to match.
- **Generators need checking too.** The shadcn CLI read the wrong tsconfig, wrote into a literal `@/` folder and installed an unrelated npm package called `cn`. Reading `package.json` after running any generator is cheap insurance.

## 0.8 — CI and first decision record

- **CI is a clean machine that doesn't trust yours.** Locally, a test can pass because of something only your laptop has: `.env`, user-secrets, a `node_modules` built by an older install. The runner starts from an empty checkout, so anything the repository doesn't contain fails there first. The check that mattered before the first push was what the tests read from disk: `.env.example` (committed) and not `.env` (ignored).
- **The pipeline encodes the project's rules.** "Warnings are errors" and "every task ends with passing tests" were habits. Now `dotnet build -c Release` with `TreatWarningsAsErrors` and the two test jobs make them a gate on every push. A rule a machine enforces doesn't depend on anyone remembering it.
- **Build what you ship.** CI builds `Release`, not `Debug`. Some analyzers and trimming behave differently between them, and production runs Release.
- **Lock files make installs repeatable.** `npm ci` installs exactly what `package-lock.json` records and fails if `package.json` disagrees. `npm install` may quietly pick newer versions. The lock generated on Windows already listed the Linux native bindings (Rolldown, Tailwind oxide, lightningcss), which is why it installs on Ubuntu.
- **Testcontainers needs no CI setup.** GitHub's Ubuntu runners have Docker, so the integration tests start `postgres:18` exactly as they do locally. There's no service container to declare and no second database definition that could drift.
- **A gate you have never seen fail proves nothing.** After the first green run, a throwaway branch with a physical `ml-2` class was pushed to confirm the pipeline goes red on the Lint step. The same idea as the mutation check in 0.7, applied to the pipeline.
- **An ADR records the trade-off, not just the answer.** ADR 0001 lists what the modular monolith costs (more files per use case; module boundaries inside one database are only a convention) next to what it buys. Accepted records are never edited. A changed mind gets a new record that supersedes the old one, so the reasoning at each point stays readable.

## 1.1 — Identity and Owner seeding

- **Questions before code.** Four behaviors this task needed (what "Owner already exists" means, what happens when `Seed:*` is missing, the password policy, the FullName default) were not in BUSINESS_RULES.md. They were asked and answered before writing `IdentitySeeder`, then written back into BUSINESS_RULES.md §1 — so the next task reads the decision, not a comment buried in code.
- **`AddIdentityCore`, not `AddIdentity`.** `AddIdentity` also wires up cookie authentication and `SignInManager`, neither of which task 1.1 needs — there's no login endpoint yet. `AddIdentityCore<User>().AddRoles<IdentityRole<Guid>>().AddEntityFrameworkStores<AppDbContext>()` registers exactly `UserManager` and `RoleManager`, and task 1.2 adds `.AddSignInManager()` only if it turns out to need it.
- **`OnModelCreating` order is load-bearing once Identity joins.** `IdentityDbContext.OnModelCreating` (the `base` call) is what names the six Identity tables `AspNetUsers`, `AspNetRoles`, etc. `UserConfiguration.ToTable("users")` has to run *after* that base call or it gets silently overwritten back to `AspNetUsers` — the opposite of the order `AppDbContext` used before this task, when there were no entities for the order to matter to.
- **A Guid primary key can be client-generated or database-generated, and EF Core decides per-value.** `User`'s constructor sets `Id = Guid.CreateVersion7()` before the row is ever tracked, so EF Core sees a non-default value and inserts it as-is. `new IdentityRole<Guid>(roleName)` leaves `Id` at `Guid.Empty`, so the same convention detects "unset" and generates one instead. Same primary key type, two different paths, chosen by what the constructor already put there.
- **A validator that ignores its own parameters is still worth a real interface.** `LetterAndDigitPasswordValidator.ValidateAsync(manager, user, password)` only reads `password` — case-agnostic letter+digit isn't something `RequireLowercase`/`RequireUppercase` can express without also demanding a specific case. Because it doesn't touch `manager`/`user`, its tests call it directly with `null!` for both rather than standing up a real `UserManager`, which needs a full `IUserStore` to even construct.
- **`[LoggerMessage]` instead of `logger.LogWarning(...)`.** This is the first `ILogger` call in the codebase, and CA1848 (warnings-as-errors) rejected the extension-method form on grounds of allocation cost. The fix is a source-generated `partial` logging method (`[LoggerMessage(Level = LogLevel.Warning, Message = "...")]`) — no new package, since the generator ships with `Microsoft.Extensions.Logging.Abstractions`.
- **The pre-migration startup ordering from task 0.6 became a real design constraint, not just a fixture detail.** `WebApplicationFactory` runs `Program.cs` up to `app.Run()` while building the host, before `DatabaseFixture` calls `Database.MigrateAsync()`. That's exactly the moment `IdentitySeeder.SeedOwnerAsync` runs from `Program.cs`, so it has to decide whether `Seed:*` is configured *before* touching `RoleManager`/`UserManager` — if it queried first, every integration test in the suite would fail at boot, not just the Identity ones.
- **`IdentityResult` is a result, not an exception.** An unchecked `await roleManager.CreateAsync(...)` fails silently. Every Identity call in the seeder now checks `Succeeded`. A bad configured password is an expected mistake and gets a warning. Anything else is unexpected and throws, which is the same line CLAUDE.md draws between `Result` and exceptions.
- **Two saves that must both happen belong in one transaction.** `CreateAsync` and `AddToRoleAsync` each call `SaveChanges`. A crash between them would leave a user with no role, and the seeder would then be stuck forever on `DuplicateUserName`. `UserManager` shares the scoped `AppDbContext`, so `Database.BeginTransactionAsync()` covers both calls.
- **Prove a database invariant with raw SQL.** `UserManager` checks for duplicate names in C# before inserting, so a test through it proves only the C# check. `UserTableConstraintTests` inserts with plain SQL and expects SQLSTATE 23505 (unique) and 23514 (check). `ck_users_full_name_not_blank` exists because `IsRequired()` stops NULL but not `'   '`.
- **An ADR for a rule you bend.** `User` can't live in Domain because `IdentityUser<Guid>` is a framework type. ADR 0002 records that and the rejected "two user classes" option, so the next person doesn't have to rediscover the trade-off.

## 1.2 — Login and access tokens

- **A JWT is a signed claim, not a session.** The server writes "user X, role Owner, valid until 10:15" and signs it with a secret key. On every request it checks the signature and the expiry, with no database lookup. The price is that a token can't be taken back before it expires, which is why it lives only 15 minutes and task 1.3 adds refresh tokens that *can* be revoked.
- **Clock skew is a hidden extension of token lifetime.** The bearer handler accepts tokens up to five minutes past `exp` by default, to tolerate clocks on different machines. One machine issues and checks these tokens, so skew is zero. A mutation check proved the expiry test fails with the default.
- **Lockout and rate limiting guard different things.** Lockout guards one account: after 5 wrong passwords it is locked for 15 minutes, even for the right password. Rate limiting guards the endpoint: 10 attempts per minute per IP, however many accounts are tried. Without it, trying one password against every user name would never trigger a lockout.
- **The order of checks is a security property.** `UserAuthenticator` checks: unknown user → the same error as a wrong password. Locked → refuse before checking the password. Wrong password → count it. Inactive → only reveal it after the correct password. Each step leaks as little as possible to someone who doesn't know the password.
- **Interfaces at the layer boundary, again.** `LoginHandler` in Application can't see the Identity `User` (ADR 0002). It depends on `IUserAuthenticator` and `IAccessTokenIssuer`, which Infrastructure implements with `UserManager` and `JsonWebTokenHandler`. The handler is left with the use case itself: no token without a successful authentication.
- **Fail closed by default.** A fallback authorization policy makes every endpoint require a logged-in user unless it explicitly says `.AllowAnonymous()`. Forgetting a policy now causes a 401 instead of an open endpoint.
- **Validate configuration at startup.** `JwtOptionsValidator` with `ValidateOnStart()` stops the API when the signing key is missing or too short, with a message that says how to fix it. Otherwise the first sign of trouble would be a failed login in front of a user.
- **Options bound lazily see the final configuration.** `Bind(configuration.GetSection(...))` reads the section when the options are first used, not at registration. That's why a test host's `UseSetting` can change the rate limit, where a value read in `Program.cs` before `Build()` would be too late (the gotcha from task 0.6).
- **My notes:**

## 1.3 — Refresh tokens and logout

- **Two tokens, two jobs.** The access token is short (15 minutes) and can't be revoked. The refresh token is long (7 days, renewed on use) and *can* be revoked, because every refresh checks it against the database. Short-lived and stateless for every request, long-lived and checked for the rare refresh: each gets the property it's good at.
- **HttpOnly cookie instead of JavaScript storage.** A token in `localStorage` can be read by any script that ends up on the page. An HttpOnly cookie can't be read by JavaScript at all; the browser just sends it. `SameSite=Strict` stops other sites from making the browser send it, and `Path=/api/auth` keeps it off every other request.
- **Store a hash, like a password, but a fast one.** The database keeps only SHA-256 of the token, so a leaked backup contains nothing that logs anyone in. Passwords need slow hashes because people choose guessable ones. A 256-bit random value has nothing to guess, so a fast hash is enough and lets each refresh look the token up directly.
- **Rotation turns theft into a detectable event.** Each token works once. If a used-up token comes back, one of the two holders is a thief, and the server can't tell which, so it revokes the whole family (every token from that login). The thief loses access, and the real user re-enters a password the thief doesn't have. A mutation check proved the reuse test fails without the detection.
- **Optimistic concurrency with `xmin`.** Two requests can read the same active token at once. Postgres's `xmin` row version makes the second save fail with `DbUpdateConcurrencyException` instead of giving one parent two children. The handler then treats it as reuse, which is the "strict, no grace period" rule. A unique index on `replaced_by_token_id` is a second guard at the database level.
- **Rules in the entity, orchestration in the handler.** `RefreshToken.Rotate` and `Revoke` hold the rules (only active tokens rotate, a revoked token keeps its first reason) and are unit-tested without a database. `RefreshHandler` decides what to do with the results: look up, detect reuse, reload the user, save.
- **Say less when you refuse.** Missing, unknown, expired, revoked and reused tokens all return the same `Auth.RefreshTokenInvalid`, and logout always answers 204. Whoever holds a stolen or guessed token learns nothing about which ones are still worth trying.

## 1.4 — Current user, policies, change password

- **Authentication vs. authorization.** Authentication (1.2, 1.3) proves *who* you are. Authorization decides *what you may do*. They fail differently: 401 means "I don't know who you are, log in"; 403 means "I know who you are, and the answer is no." The frontend reacts to each differently, so the difference is worth keeping sharp.
- **Policies name a permission once.** `OwnerOnly` and `StaffOrOwner` are the permissions table in BUSINESS_RULES.md, written as code. An endpoint says which one it needs, instead of each handler checking roles itself, and a single test checks every combination of role and flag.
- **A requirement is a reusable rule inside policies.** The forced password change gate is `PasswordChangedRequirement`, added to every policy but one. Because it's a named requirement, the failure result says *which* rule failed, and the API can answer `Auth.PasswordChangeRequired` instead of a vague "forbidden".
- **Secure by default.** The fallback policy covers endpoints that forget their policy, `EndpointAuthorizationTests` covers endpoints that forget to *decide*, and the gate is part of both. Forgetting something now makes an endpoint closed, never open.
- **`ICurrentUser` hides HTTP from the inner layers.** Application and Infrastructure ask "who is this?" through an interface. Only Gym.Api knows the answer comes from a JWT claim, so the same handler works from a background job, where the answer is "nobody". The audit interceptor is its first user: `CreatedBy` and `UpdatedBy` now fill themselves.
- **A singleton can depend on per-request data through an accessor.** `IHttpContextAccessor` returns the current request each time it's asked, so `HttpContextCurrentUser` can be a singleton without capturing one request's user forever. Capturing a scoped value in a singleton is the classic DI bug that leaks one user's data into another's request.
- **Transactions have edges; choose what goes inside.** Changing a password saves the hash, clears the flag and revokes tokens in one transaction. The failed-attempt count is saved *before* the transaction, on purpose, so a rollback can't erase evidence of password guessing.
- **Old tokens don't learn about changes.** After a password change, the old access token still says `must_change_password=true` until it expires. The endpoint returns a fresh session, so the user moves on at once instead of hitting the gate for 15 more minutes.

## 1.5 — Staff management API

- **A policy on the group, not on each endpoint.** `MapGroup("/api/staff").RequireAuthorization(Policies.OwnerOnly)` makes "Owner only" a property of the whole URL space. A sixth endpoint added next month is protected without anyone remembering to protect it.
- **"Not found" as a safety rail.** The staff endpoints only see Staff accounts. Asking them to deactivate the Owner's id answers 404, as if the account weren't there, so the Owner can't lock themselves out through the staff screen.
- **Idempotent actions.** Deactivating an inactive account succeeds and changes nothing. A double-clicked button or a retried request can't turn into an error, and the result is the same however many times it arrives.
- **A test that passes for the wrong reason proves nothing.** The first deactivate test checked that refresh fails. But refresh rejects inactive users anyway, so it would have passed without the token revocation. The test now checks the tokens right after deactivation, and a mutation check confirms it fails without the revocation.
- **One rule, two enforcers.** `UserNamePolicy` and `PasswordPolicy` are read by both the FluentValidation rules (a friendly field error before anything is saved) and Identity's options (a guarantee on every path that stores a user). Neither can drift from the other because neither holds a copy.
- **Paging from the start.** Even a list of five staff returns `PagedResponse<T>`. Changing a response shape later breaks the frontend. Paging from day one costs almost nothing.

## 1.6 — Audit log

- **An interceptor sees every change, so no handler has to remember.** The audit rule is "every insert, update and delete". Forty handlers each writing their own audit row would be forty chances to forget. One `SaveChangesInterceptor` reads the change tracker and writes the rows for all of them.
- **Same save, same transaction.** The audit rows are added to the context *inside* `SavingChanges`, so they commit or roll back together with the change they describe. A test proves a failed save leaves no audit row behind.
- **The change tracker knows the old values.** `PropertyEntry.OriginalValue` and `CurrentValue` give "before" and "after" for free, and `IsModified` says which properties changed. EF marks a property modified when it's *assigned*, so the interceptor also compares the values.
- **Exclude secrets by name, and prove it with the real values.** The test doesn't only check that no row has a `PasswordHash` key. It loads every real hash and stamp from the database and checks that none appears anywhere in the log. A mutation check confirmed the test fails if the exclusion is removed.
- **Append-only belongs in the database.** The entity has no update methods, but code isn't the only thing that talks to a database. A trigger rejects UPDATE and DELETE from any connection. Triggers aren't part of EF's model, so the migration creates it with raw SQL and `ARCHITECTURE.md` records that the snapshot doesn't know about it.
- **Know how your tools touch the database.** A DELETE-blocking trigger could have broken every test reset. It doesn't, because Respawn uses TRUNCATE, which row-level triggers ignore. A test now pins that, so a Respawn upgrade that changes it fails loudly in one place.

## 1.7 — UI: login and staff

- **Where a token lives decides who can steal it.** The access token is a variable inside a module, and the refresh token is an HttpOnly cookie. Script on the page can read neither from storage, because there's no storage. The cost is a page reload forgets the access token, so `restoreSession()` asks for a new one with the cookie before the first screen decides anything.
- **One place for "my token expired".** `authFetch` wraps `fetch`: it adds the bearer header, and on a 401 it refreshes and retries once. No screen handles expiry, so no screen can get it wrong.
- **Single-flight refresh.** Three requests failing at once must cause *one* refresh. Refresh tokens rotate strictly, and a second refresh with the same cookie looks like theft and logs the user out. A shared promise makes later callers wait for the first refresh. A test fires three requests at once and counts the refreshes.
- **A request body can be read once.** Retrying a POST needs the body again, so the first attempt sends a `clone()` and the retry sends the original. A test checks that the retried body arrives intact.
- **Guards are for users, the API is for security.** `RequireAuth` and `RequireRole` keep people away from screens that would fail. The API still refuses the request if someone gets past them. The two protect different things.
- **Mock at the boundary, run everything else for real.** Tests replace only `fetch`, with a small router. openapi-fetch, `authFetch`, TanStack Query and React Router all run for real, so a test like "login with a temporary password lands on change-password" exercises the actual wiring.
- **A contract that spans two languages needs its own test.** Nothing links C# error codes to the TypeScript messages. `ErrorCatalogTests` collects every code the API defines, by reflection over errors and validators, and fails when `errors.ts` lacks one. A mutation check confirmed it.
- **Verify the Done-when for real, and doubt surprising results.** The live run through the Vite proxy showed a staff name as `??????`. Instead of assuming an app bug or ignoring it, the same request sent from a UTF-8 file came back intact: the Windows shell had mangled the argument. The dev data was repaired, and the gotcha is in `ARCHITECTURE.md`.

## Phase 1 review

A `code-reviewer` agent read all of Phase 1. It found no auth bypass, but it did find races and gaps that the task-by-task tests had missed.

- **"Read, change, save" is a race.** Identity's failed-login counter loads the count, adds one in C#, and saves. Eight parallel wrong passwords all read the same count: one save won, seven answered 500, and lockout counted one attempt instead of eight. The fix lets Postgres do the arithmetic in one `UPDATE ... SET count = count + 1`, on a row it locks. A test fires eight wrong passwords at once, and it failed on the old code with seven 500s.
- **Concurrency failures are expected, not exceptional.** Two people changing the same account at once is normal, so the answer is a 409 the Owner can retry (or, for token families, a retry loop), never a 500.
- **The same error message isn't enough; it must take the same time.** An unknown user name returned instantly while a known one ran the slow password hash, so timing leaked which names exist. Unknown names now run a dummy hash.
- **"Only one refresh at a time" must hold across tabs.** A module-level promise protects one tab. The refresh cookie is shared by every tab, so tabs coordinate with the browser's Web Locks API.
- **The cookie belongs to the browser, not the tab.** If someone else logs in from another tab, this tab's next refresh would quietly become them. The frontend now compares the token's `sub` and signs out instead.
- **A 401 isn't always an expired token.** Only `Auth.Unauthenticated` is worth a refresh. A handler's own 401 (locked out, deactivated) came with a valid token, and retrying would only resend the request.
- **A rule enforced only by the client is a suggestion.** Password digit conversion lived only in the browser, so a Persian-digit seed password could never log in. The API now converts too.
- **Why a review after the tasks.** Each task tested its own feature. The review looked across them: parallel requests, several tabs, two people at once. That's where these bugs were.

## 2.1 — Member creation and update

- **Canonical form before comparison.** `0912…`, `۰۹۱۲…`, `+98 912…` and `0098-912-…` are one phone number but five strings. A unique index compares strings, so every number is turned into E.164 (`+989121234567`) before it's saved or searched. The index is only as good as the normalization in front of it, which is why a check constraint also refuses anything that isn't E.164.
- **Use the library that knows the data.** Which Iranian ranges are mobiles, and how every country writes its numbers, is data that changes. libphonenumber (Google's, the one Android uses) carries it, behind `IPhoneNormalizer` so only Infrastructure knows it exists.
- **Store as entered, search on the normalized form.** `FullName` keeps what the receptionist typed. `NormalizedFullName` (ي→ی, ك→ک, half-space→space, lower case) is what task 2.2's search reads. Only the `Member` entity writes either, and always both, so they can't drift apart.
- **The first real domain entity.** `Member.Create` and `Update` return `Result` for rule failures (blank name, too long) and throw only for a caller's bug (a phone that wasn't normalized). Ten unit tests run without a database.
- **Check first, then let the index decide.** The handler asks "does this phone exist?" for a friendly 409. Six parallel creates can all pass that check, so the database's unique index decides, and `AppDbContext` turns its error into `UniqueConstraintException` so the losers get the same 409. A mutation check showed they got 500s without that translation.
- **Optimistic concurrency across a whole form.** `xmin` alone protects only the milliseconds between a request's read and write. Returning `Version` with the member, and requiring it back on update, protects the minutes a receptionist spends editing: if someone saved in between, the edit is refused instead of silently erasing their change.
- **Invisible characters need visible source.** A literal Arabic ي looks exactly like Persian ی, and editing tools quietly turned `\u064A` escapes into the character itself. Domain code and tests now write them as code points, `(char)0x064A`, which no tool rewrites and every reviewer can read.

## 2.2 — Member queries and lifecycle

- **Read side vs. write side.** Queries use `AsNoTracking()` and `Select(MemberResponse.Projection)`. The projection is an `Expression`, so EF Core turns it into SQL that reads only those columns and builds no tracked entities. Writes still load the entity and call its methods.
- **One search box, two searches.** The handler decides from the input: only digits, `+`, spaces and dashes means a phone search, anything else a name search. Both sides are normalized the same way before comparing, so "علي" finds "علی" and `۰۹۱۲…` finds `+98912…`.
- **Trigram indexes.** A B-tree index can't help `LIKE '%احم%'`, because the match can start anywhere. `pg_trgm` splits text into three-character pieces, and a GIN index over those pieces can find a match in the middle of a name or a phone number.
- **Escape user input inside patterns.** In `LIKE`, `%` and `_` are wildcards. Without escaping, a search for `%%` would list every member. It's the same idea as SQL injection, one level down.
- **Stable paging.** Sorting only by name lets two "علی"s swap places between two page requests, so one shows twice and the other never. Adding `Id` as a tie-breaker gives every row a fixed position.
- **An action that repeats safely.** Deactivating an already inactive member just succeeds. EF Core sees nothing changed, so it writes nothing, not even an audit row. A double-click or a retry after a network error can't do harm.
- **Where tests found real details.** `timestamptz` keeps microseconds while .NET keeps 100 ns, and the snake-case convention quietly renamed an index. Both are now in the Gotchas in ARCHITECTURE.md.

## 2.3 — UI: members

- **State in the URL.** The search text, page and filter live in the query string, not only in React state. Refresh, back from a profile, and a copied link all show the same results. Typing uses `replace` so the back button doesn't step through every pause; paging and filters push, so back undoes them.
- **Debouncing a call, not a value.** `useDebouncedCallback` waits until typing pauses for 300 ms, then writes the URL once. An effect watching a debounced value would also re-run whenever its other dependencies changed, like `setSearchParams`, which changes on every navigation.
- **Adjusting state during render.** When the URL changes from outside (back button), the search box follows it with `if (q !== shownQ) { … }` in the render itself, React's documented pattern. An effect would first paint the stale text.
- **Two layers of validation.** Zod catches blanks and lengths instantly, with the same Persian messages as the API's codes. Only the server knows whether a phone is a real Iranian mobile or already taken, so those codes are routed to the phone field (`codeFields`).
- **Optimistic concurrency, visible.** The edit form sends back the `version` it was filled from. On `Members.ChangedConcurrently` the page explains and offers to load the colleague's version. The form is keyed by `version`, so React rebuilds it with the fresh values.
- **Cache after a change.** A mutation puts the server's answer straight into the profile's cache entry and invalidates the lists, so a renamed member never keeps the old name in search results.
- **Bidi in practice.** In a right-to-left paragraph, `۰۹۱۲ ۱۲۳ ۴۵۶۷` is laid out as `۴۵۶۷ ۱۲۳ ۰۹۱۲`. Wrapping it in `dir="ltr"` keeps the groups in order.

## 3.1 — Plans API

- **Two groups, one prefix, two policies.** `/api/plans` is mapped twice: a read group with `StaffOrOwner` and a write group with `OwnerOnly`. Every endpoint gets its policy from the group it lives in, so a new write endpoint can't be added without the Owner check. Staff still see plans, because they sell them.
- **Null that means something.** `SessionCount` is `int?`: null is "unlimited". A magic value like 0 or -1 would be a number every caller has to remember isn't a number; `null` makes the compiler remind them. `IsUnlimited` names the meaning and is ignored by EF Core.
- **Money is exact.** `decimal` in C#, `numeric(18,2)` in Postgres. A price with three decimals is refused, not rounded, because silently changing an amount nobody typed is the kind of bug you find in an audit.
- **A rule with one home, used later.** "Inactive plans cannot be sold" is `plan.EnsureCanBeSold()`. There is nothing to sell yet; task 4.2 will call it instead of checking `IsActive` itself, so the rule can't be implemented twice slightly differently.
- **Validator and entity share one source.** The limits are constants on `Plan`, and `PlanRules` uses the same constants and error codes (even `Plan.CheckPrice`). The form gets field-level messages, and the entity still refuses bad values if a caller skips validation.
- **The database repeats the rules.** Check constraints (`BETWEEN 1 AND 365`, `price >= 0`, `session_count IS NULL OR …`) and a unique index on the normalized name. Tests insert bad rows with raw SQL to prove the database refuses them by itself.
- **Unique in normalized form.** Uniqueness is checked on `NormalizedName`, not `Name`, so "ویژه" typed with an Arabic ي is the same plan. Check first for a friendly 409, and let the unique index settle the race (the parallel-create test).

## 3.2 — UI: plans

- **Guards are UX, the API is security.** The three plan routes are wrapped in `RequireRole role="Owner"` (now through a small `ownerOnly()` helper, also used for staff) and the menu item has `role: "Owner"`. A staff user who types `/plans` sees "no access" and no request is sent. The API's `OwnerOnly` group would refuse them anyway.

The form keeps the price as text and sends it as a JSON string (`"price": "1500000.50"`). ASP.NET reads a string straight into `decimal`, and a new integration test proves it (`CreatePlan_PriceAsJsonString_IsStoredExactly`).

## 4.1 — Subscription domain model

- **Snapshot at the sale.** A subscription copies `PlanName`, `Price`, `DurationDays` and `TotalSessions` from the plan when it is sold. Editing or deactivating the plan afterwards changes nothing, like a receipt that keeps the price it was printed with. A test edits the plan after the sale to prove it.
- **Calculated, never stored.** `GetStatus(today)` works the status out from the dates, the sessions, the freeze and the cancel. A stored status would be wrong the morning after a subscription expires, until some job rewrote it.
- **Precedence as code.** When two statuses apply at once (frozen *and* past the end date), a fixed order decides: Cancelled, Frozen, Upcoming, Expired, Exhausted, Active. The `if` chain in `GetStatus` is that order. A test per pair pins it, and breaking the order on purpose showed the tests catch it.
- **"Today" is a parameter.** The entity never reads a clock. It receives a `DateOnly` in the gym's time zone, so a test can place it on any day. The tests use `FakeTimeProvider` to show why the time zone matters: at 20:30 UTC on 30 September it is already 1 October in Tehran (UTC+03:30), so the subscription has expired.
- **An inclusive end date.** `EndDate = StartDate + DurationDays - 1`. A one-day plan starts and ends on the same day. Off-by-one bugs in dates hide exactly here, so both edges (the end date itself and the day after) are tested.
- **Errors that say why.** Using a subscription fails with a different code per status (`NotStarted`, `Expired`, `NoSessionsLeft`, `Frozen`, `Cancelled`), because at the front desk each one is a different conversation with the member.
- **A limit that never traps anyone.** A freeze longer than the remaining allowance still ends. `Unfreeze` just caps the extension at the days left and returns how many days it added, so task 4.3 can move queued subscriptions by exactly that amount.
- **Bugs throw, users get `Result`.** A blank cancel reason is a user mistake, so it returns an error. Unfreezing on a date before the freeze began can only be a bug in the caller, so it throws.

## 4.2 — Assign and renew

- **A rule the database guarantees.** "A member never has two subscriptions covering the same date" is an **exclusion constraint**: `EXCLUDE USING gist (member_id WITH =, daterange(start_date, end_date, '[]') WITH &&) WHERE (cancelled_at IS NULL)`. A unique index can only compare equal values; an exclusion constraint compares with any operator, here "same member *and* overlapping dates". `btree_gist` lets a GiST index handle the plain `member_id` column. EF Core can't express this, so it's hand-written SQL in the migration.
- **What the race test found.** Six parallel sales for one member failed with 500. With the constraint deferred, each transaction waited at commit for another's uncommitted row, in a circle: a **deadlock** (40P01). Running the test ten times caught it 2 times out of 10. A race test that passes once proves little.
- **Take turns, don't fight.** The fix is a row lock: the sale opens a transaction and runs `SELECT … FOR UPDATE` on the member first. A second sale for the same member waits, then reads the first one's subscription and queues after it, so all six succeed. The constraint stays as a safety net. Removing the lock made the test fail 3 out of 3 times, which proves the lock is what fixes it.
- **Deferred vs immediate.** A deferred constraint is checked at `COMMIT`, and its error arrives from the commit itself, not wrapped in `DbUpdateException` like other save errors. It's now `DEFERRABLE INITIALLY IMMEDIATE`: checked on every write, but task 4.3 can defer it inside its own transaction when unfreezing moves several subscriptions at once.
- **"Today" has one owner.** `IGymCalendar.Today()` turns `TimeProvider` plus `Gym:TimeZone` into a Tehran date. A misspelled time zone stops the app at startup (`ValidateOnStart`) instead of quietly expiring subscriptions 3.5 hours late.
- **Shared logic without a framework.** Assign and renew differ only in *which* plan. `SubscriptionSeller` is a plain injected class holding the common part (lock, schedule, create, save), and the two handlers stay small.
- **The foreign key is the last word.** `ON DELETE RESTRICT` means a member or plan with sales can never be deleted, even by hand. It reports SQLSTATE 23001, not 23503, which the test found.
- **My notes:**

## 4.3 — Freeze, unfreeze, cancel endpoints

- **One row vs. several rows.** Freeze and cancel each change one field on one subscription, so the `xmin` token from task 4.2 is enough: a concurrent second write just fails with `DbUpdateConcurrencyException`. Unfreeze can change *several* subscriptions' dates at once (the one unfrozen, plus everything queued behind it), so it needs the member lock too — the same reason `SubscriptionSeller` takes it.
- **Deferring a constraint on purpose.** Moving a chain of date ranges later has to pass through a moment where the old, not-yet-shifted ranges overlap the new ones — if row A is updated before row B, A's stretched range briefly overlaps B's old one. `SET CONSTRAINTS ex_subscriptions_no_overlap DEFERRED` tells Postgres to check the exclusion constraint once, at `COMMIT`, after every row in the transaction is consistent, instead of after each `UPDATE`. This is exactly what the `AddSubscriptions` migration's comment (written in task 4.2) was waiting for.
- **Commit can fail too.** A deferred constraint's violation surfaces from `transaction.CommitAsync()`, not from `SaveChangesAsync()`, and it isn't wrapped in `DbUpdateException` the way an immediate one is. `IAppDbContext.CommitTransactionAsync` exists just to catch that raw `PostgresException` in Infrastructure (the only project allowed to know about Npgsql) and re-throw the same `ExclusionConstraintException` the immediate path already throws, so the handler's `catch` doesn't care which path it came from.
- **A second `IOptions<T>` on the same section.** `Gym:MaxFreezeDaysPerSubscription` sits in the same `"Gym"` configuration section as `Gym:TimeZone`, but it's bound by its own `SubscriptionPolicyOptions`, not added to `GymCalendarOptions`. Two small, single-purpose Options types reading the same section beat one growing type that answers unrelated questions.
- **The entity still only knows how to move.** `Subscription.ShiftQueued(days)` moves `StartDate` and `EndDate` together; it has no opinion on *which* subscriptions should be shifted or why. `UnfreezeSubscriptionHandler` decides that (same member, not cancelled, starts after the original end date) — the same split as `SubscriptionSchedule.NextStartDate` in task 4.2: the entity enforces the rule, the Application layer decides who it applies to.

## 4.4 — Payments

- **A pure function instead of a method on the entity.** `Subscription` doesn't know its own payments, so "payment status" can't be `subscription.GetStatus()`'s style of self-contained method. `PaymentStatusCalculator.Calculate(price, netPaid)` takes both numbers in and has no dependencies at all — the caller (`RegisterPaymentHandler`, later a history screen) is the one who sums the rows and asks.
- **An edge case the business rules didn't spell out.** "Paid when net paid >= Price, Unpaid when net paid = 0" both match a free (`Price = 0`) subscription with no payments. Checking the `Paid` condition first resolves it: a free subscription owes nothing, so it reads as `Paid`, not `Unpaid`. Documented in BUSINESS_RULES.md as a pending-review decision rather than silently picked.
- **A lock reused for a reason that isn't its name.** `IAppDbContext.LockMemberAsync` was built in task 4.2 so two sales for one member take turns. Registering a payment doesn't touch a member row or a subscription row at all, but "a subscription cannot be overpaid" is exactly the same shape of bug — two concurrent requests each reading net-paid-so-far as 0 and both approving a payment that only fits once. The same per-member lock, held across the read-then-write, closes it without a new mechanism.
- **A schema built ahead of its own feature.** `Payment.Kind` and the `ck_payments_refund_reason` check constraint model refunds now, even though nothing can create one until task 4.5 (Refund and void). The same thing happened with `Subscription.Freeze`/`Unfreeze`/`Cancel` in task 4.1, built a full task before their endpoints existed in 4.3: the entity's shape comes from the business rule, not from which use case is wired up this week.
- **Enums are numbers unless told otherwise.** `System.Text.Json` serializes an enum as its underlying integer by default. `SubscriptionResponse.Status` already opted a single field into strings with `JsonConverter(typeof(JsonStringEnumConverter<T>))`; `PaymentMethod` and `PaymentKind` use the same attribute on both the response and the request command, so the frontend sends and receives `"Cash"`, not `0`.
- **A validator rule that looks dead but isn't.** `.IsInEnum()` on `Method` seems unreachable once the command binds through a string converter — an unrecognized string would throw during JSON deserialization, before validation runs. But `JsonStringEnumConverter`'s default `allowIntegerValues: true` still accepts a raw out-of-range number (`"method": 99`), which deserializes without throwing and reaches the validator, where it belongs.

## 4.5 — Refunds and member history

- **"Void" is a description, not a code path.** BUSINESS_RULES.md §5 says a mistaken entry is fixed with "a full refund whose reason explains the mistake (a 'void')". There is no `Kind.Void` and no second endpoint — `RegisterRefundForSubscription` with an amount equal to the mistaken payment's amount *is* a void. `RefundEndpointTests.Refund_FullAmountOfAMistakenPayment_IsAVoidThatRecalculatesToUnpaid` names the concept in a test instead of in a type.
- **Pulling the shared part out once it's shared twice.** `Payment.RegisterForSubscription` and `RegisterRefundForSubscription` both need "check the amount, trim and check the reference number, build the row" — task 4.4 didn't extract that because there was only one caller. A private `Create(...)` now holds it; each public factory adds only what makes it a payment or a refund (nothing extra vs. a required, length-checked reason).
- **The same response shape, opposite direction.** `RegisterRefundHandler` returns the exact `PaymentResponse` shape `RegisterPaymentHandler` already returns — `SubscriptionNetPaid`/`SubscriptionPaymentStatus` computed after the write. "Status recalculates" (the roadmap's own words) is just that number going down instead of up; no new response type was needed to prove it.
- **A list gets its own response, on purpose.** `PaymentHistoryResponse` looks like a trimmed `PaymentResponse` but is a separate type: `SubscriptionNetPaid`/`SubscriptionPaymentStatus` describe "the result of the payment/refund that was just registered", a question that stops making sense for a list of many historical rows, possibly from different subscriptions. Reusing `PaymentResponse` there would mean either computing a meaningless field for every row or leaving it always wrong.
- **An inner join is a filter, not just a shortcut.** `ListMemberPaymentsHandler` joins `payments` to `subscriptions` instead of filtering `payments.SubscriptionId != null` by hand — a payment with no subscription (a future cafe-order payment) has nothing to join to and drops out on its own, which happens to be exactly "this member's payments".
- **A parent id gets checked before its children are listed.** Both new list handlers confirm the member exists (`MemberErrors.NotFound`, `404`) before querying subscriptions or payments, the same check `AssignSubscriptionHandler` already made for a *write* — a list is read-only, but "no such member" and "no history yet" are still different answers.

## 4.6 — UI: subscriptions and payments

- **A dialog is a concept, not a component.** The roadmap said "dialog" for assign/renew and register payment, but this codebase's only precedent (`StaffPage`'s password-reset, `CreateStaffForm`) is a button that reveals a form in place — no modal exists anywhere and no shadcn `Dialog` had been added. Decided with the developer to keep it that way rather than introduce Radix `Dialog` for the first time; the same reasoning made the history section a manual button-group "tablist" (`PlansPage`'s active/inactive filter, generalized) instead of shadcn `Tabs`.
- **Closing a gap left on purpose.** Tasks 4.4 and 4.5 deliberately kept `NetPaid`/`PaymentStatus` off `SubscriptionResponse`, noting in this same journal that it was "deferred to whenever the UI explicitly needs it." This task is that moment: one field added to the response, six call sites each passing a real net-paid figure (`PaymentLedger.GetNetPaidAsync` for one row, a single grouped query for a whole page to avoid N+1). Reading the earlier entries turned "should this touch five files" into "yes, exactly these five, for exactly this reason."
- **Two labels beat one ambiguous one.** Every inline form's submit button first repeated its toggle button's own label ("ثبت پرداخت" opened *and* submitted a payment). Beyond being confusing for a screen reader user (two same-named controls), it broke `getByRole` in tests, which resolves by accessible name. Renaming submits to "تأیید …" (confirm …) fixed both at once — accessibility and testability were the same problem.
- **A calculated field's ambiguity, from a test.** `getByText("فعال")` failed with "found 3" the first time: the same subscription is shown by the current-subscription card *and* by its own row in the default-selected history tab underneath it, each with its own status badge, plus the member's own "فعال". Real duplication, not a test bug — fixed by asserting counts (`getAllByText(...).length`) instead of assuming one match, and reaching for `waitFor` where two independent queries race to render the same text.
- **`findBy*` waits for one render, not for "done."** `screen.findByText("اشتراک فعلی")` resolved instantly because that title renders identically in the loading, error and loaded states — so it never actually waited for data. The fix is waiting for something that only exists in the loaded state (a button that depends on the fetched data), the same lesson as the earlier `isPending`/`isSuccess` split.

### Follow-up fixes (post-4.6 UI review)

- **Two different "active" flags, one confusing label.** `Member.IsActive` (an account toggle, defaults to true) and a subscription's calculated `Active` status look like the same word next to a member's name, but selling requires the member to already be active (`Members.Inactive`), so defaulting new members to inactive would make the very first sale impossible. The fix here was not code — it was confirming with the developer that the badge is correct as documented in BUSINESS_RULES.md §2 and §4, and that no business rule needed inventing.
- **A one-click button that mutates is a bug waiting for a double-click.** "تمدید" called `useRenewSubscription` straight from `onClick`, so a second click (or an impatient tap) queued a second subscription — renew has no idempotency key, each call is a new sale. Every other mutating action in this card already opens a confirm panel first (Assign, Cancel, Freeze uses a disabled-state guard); Renew was the one exception, fixed by giving it the same `RenewSubscriptionForm` panel pattern so the API call only fires from an explicit "تأیید تمدید" click.
- **Show the computed result instead of re-deriving the rule.** The renewed subscription's start date depends on the member's whole subscription history (today vs. queued-after-latest-`EndDate`, plus the `Exhausted` edge case in §4) — logic that already lives correctly on the server. Reimplementing it in the confirm panel would be a second, driftable copy of a business rule with edge cases; instead the panel stays generic before confirming, and the success message reads the actual `startDate`/`endDate`/`status` off the mutation's own response.
- **The same duplicate-accessible-name trap, one task later.** Adding a per-row "ثبت پرداخت" button to the subscription history table recreated the exact ambiguity already logged above for "فعال": whenever a member has exactly one subscription, its row and the current-subscription card both show a same-named button. Fixed the same way — `aria-label` carries the disambiguating detail (plan name and date) while the visible button text stays short.
- **"Current subscription" is a display convenience, not a management scope.** The developer found the real gap: freeze an active subscription, then renew it, and freezing the *active* one becomes impossible — the card always shows the newest subscription by start date (a queued renewal, once one exists), and every action button on it (freeze, unfreeze, cancel, refund, payment) only ever targeted that one id. The fix moved every action that operates on an *existing* subscription onto that subscription's own row in the history table (`SubscriptionHistoryRow`), each calling the API with its own row's id. The card kept only Assign and Renew, the two actions that always create a *new* row, where "which subscription" is never ambiguous in the first place.
- **A table row can render two rows.** Each history row optionally renders a second `<tr>` directly beneath it (`colSpan` across every column) holding whichever form is open, by returning a fragment of two sibling `<tr>` elements — valid because `<tbody>` only cares that its children are eventually `<tr>`, not that each mapped item produces exactly one. This put the open form right next to the row it belongs to, instead of pooling at the bottom of the whole table below the pager regardless of which row was clicked, which was the developer's other complaint: nothing about the form even said which subscription it targeted.
- **Not every mutating button needs a confirm panel.** Freeze and unfreeze kept their original direct-`onClick` shape (no inline form) — unlike Renew, calling Freeze twice on the same subscription is not silently repeatable: the domain only allows freezing an `Active` one, so a second click after the first succeeds just fails cleanly with an error instead of doing something wrong twice. Cancel, refund and payment need a form regardless, because they need typed input (a reason, an amount).
- **The row-based fix did not touch what the summary card itself shows.** The developer's very next screenshot found the deeper version of the same bug: "current" picked the newest subscription by start date, so a cancel-then-resell history put a *cancelled* subscription on the card while the actually-active one sat further down, invisible above the fold. `pickCurrentSubscription` (`features/subscriptions/api.ts`) replaced that with an explicit priority — active or frozen wins outright; otherwise the soonest upcoming; otherwise the most recently ended — computed client-side over a generously-sized page (50) rather than a new backend endpoint, since the history table below remains the exact source of truth for the rare member who exceeds it. A "sort order" decision turned out to encode a business judgment (what does "current" even mean) that was worth writing down, not just picking arbitrarily.
- **Reformat the DOM value, not the React value.** The money-grouping input (`MoneyField`) tried `useController` first so the field could be "controlled" — same digits stored, reformatted for display — and every property read off the returned `field` object (`.value`, `.name`, `.ref`, `.onBlur`) tripped this repo's `react-hooks/refs` rule (`eslint-plugin-react-hooks` v7, the React Compiler ruleset), which treats a destructured object as ref-tainted once any of its properties feeds a `ref` prop. The fix stayed uncontrolled instead, matching every other field in the codebase (`register()` spread straight onto the `<input>`): reformat `event.target.value` in place before `register`'s own `onChange` ever reads it, so react-hook-form stores exactly what's on screen. That value (with separators and Persian digits) was already valid input — `amountProblem`/`normalizeAmount` were written to accept it by hand from the start.
- **A "sort order" question turned into a member-list feature.** The developer's read of the same screenshot was product-level, not just UI: front-desk staff mostly want to see who *owes* money, not each member's payment status one subscription at a time — most members pay in full up front, so a "current subscription paid?" column would rarely fire. `MemberResponse` gained `HasUnpaidSubscription` (BUSINESS_RULES.md §4: net paid below price), computed only by `ListMembersHandler` in two batched queries (subscriptions for the page's member ids, then a grouped payments sum — the same shape `ListMemberSubscriptionsHandler` already used for its own N+1 avoidance) rather than per-member round trips. A cancelled-but-unpaid subscription does not count: cancelling is already how the gym says it is not chasing that money. Every other `MemberResponse` path (create, update, get-by-id, activate) leaves the field `false` by default — it costs nothing there and nothing reads it there.
- **A locked build output means someone is running it.** `dotnet build` failed copying into `Gym.Api`'s `bin` folder mid-session — not a compile error, but a `Gym.Api.exe` the developer had left running (from testing the earlier fixes) still holding the file open. Checked with `Get-Process -Id` before touching it, and asked before stopping someone else's running process rather than assuming a locked file is safe to fight past.

## 5.1 — Lockers API

- **A fact the entity can't look up, so it's a parameter.** `Locker.MarkOutOfService(isOccupied)` needs to know whether the locker is occupied, but Domain has no EF Core reference and cannot query Attendance itself. The caller (the handler, which *can* query) works it out and passes it in — the same shape as `Subscription.ConsumeSession(today)` taking today's date instead of reading a clock.
- **Derived, not stored, and not fakeable either.** BUSINESS_RULES.md §6 says occupancy is derived from an open attendance, never stored. Task 5.2 hasn't added Attendance yet, so today there is no way for any locker to be occupied — `IsOccupied` is hardcoded `false` in `LockerResponse`, with a comment explaining that's the *correct* answer right now, not a placeholder being left broken.
- **One mapping, two shapes.** `LockerResponse.From(Locker)` builds the response from a tracked entity (used after a write); `LockerResponse.Projection` is the same mapping as a `LINQ` expression tree, which EF Core translates straight to SQL for reads (`GetLocker`, `ListLockers`) so the database returns only the columns needed instead of whole rows.
- **The same two race guards, a third time.** Duplicate locker numbers and concurrent edits reuse exactly the patterns from Members and Plans: check first for a friendly error, then catch the unique-index violation (`UniqueConstraintException`) for the race the check can't close; `xmin` (exposed as `Version`) catches a concurrent status change (`DbUpdateConcurrencyException` → `Lockers.ChangedConcurrently`). Writing it a third time is what turns a solution into a habit.
- **A check constraint the entity already enforces.** `Locker.CheckNumber` rejects non-positive numbers before anything touches the database; the migration adds `ck_lockers_number_positive` as well, so a hand-written `INSERT` can't sneak one past application code. A test inserts one directly with raw SQL to prove the database, not just the app, refuses it.
- **The frontend error catalogue is a real test, not a suggestion.** Adding `Lockers.*` error codes without a matching Persian entry in `web/src/lib/errors.ts` fails `ErrorCatalogTests` on the .NET side — a reflection-based test that lists every `Error` in Domain/Application plus every FluentValidation code and checks the frontend file mentions each one. It caught the omission here.

## 5.2 — Check-in

- **A placeholder from last task became real, not a new decision.** Task 5.1 hardcoded `LockerResponse.IsOccupied` to `false` because Attendance didn't exist yet. Adding Attendance here means that hardcoding was no longer the accurate answer — `LockerResponse.Projection` changed from a static field to a method that takes the open attendances as an `IQueryable<Attendance>` and closes over it in the expression tree, so EF Core still translates the whole thing to one SQL query with a correlated `EXISTS` subquery. `SetLockerOutOfServiceHandler` got the same fix: the `isOccupied` it feeds to `Locker.MarkOutOfService` is now a real query, not a hardcoded value. A pattern from 5.1's own learning note repeated: a column or field can exist a task before the feature that fully uses it, as long as the note says why.
- **A filtered index instead of an exclusion constraint.** Subscriptions needed a hand-written exclusion constraint (task 4.1/4.2) because "no two date ranges overlap" isn't expressible in EF Core's fluent API. "At most one *open* row per member" is simpler: `checked_out_at IS NULL` is an ordinary filter condition, so `HasIndex(...).IsUnique().HasFilter("checked_out_at IS NULL")` is enough, and Postgres enforces it exactly like any other unique index — no raw SQL in the migration, no deferred-constraint machinery.
- **A column before the feature that mutates it.** `Attendance.CheckedOutAt` exists from this task and is never set by any code in it — check-out and cancel are task 5.3. It has to exist now because both partial unique indexes filter on it; without the column there's nothing to filter on. Same reasoning as `Locker.IsOutOfService` existing before task 5.1 had a UI for it, just one layer earlier (schema before behavior, instead of behavior before UI).
- **Reusing a lock for a reason that wasn't originally about check-in.** `IAppDbContext.LockMemberAsync` was built in task 4.2 so two subscription sales for the same member can't both read the same calendar. Check-in needs the identical guarantee for a different reason — two check-ins can't both consume the last session — so `CheckInHandler` opens a transaction and takes the same lock before touching the member's subscriptions. The lock is about "changes to this member happen one at a time," not about subscriptions specifically, so it was already the right tool.
- **Reusing `ConsumeSession`'s errors instead of inventing new ones.** Check-in's precondition is "has an Active subscription," but the roadmap's own test list names specific reasons a subscription might not qualify: expired, frozen, exhausted. Rather than re-deriving those as new `Attendance.*` codes, the handler picks the member's latest non-cancelled subscription and calls `subscription.ConsumeSession(today)` — the same method `Subscription` already exposes — and returns whatever `Result` it produces. One rule, enforced in one place, told to two different call sites (selling a subscription and using one).
- **No `Result` on `Attendance.CheckIn`.** Every other `Create`-style factory in this codebase (`Locker.Create`, `Subscription.Create`) returns `Result<T>` because it checks a field-level invariant. `Attendance.CheckIn` has none — every precondition it depends on (member active, subscription active, no open attendance) is a fact about *other* entities that Domain cannot look up, so it's checked in the handler before `CheckIn` is ever called. The entity just records what already passed.

## 5.3 — Check-out, cancel, lists

- **One field closes two different stories.** `Attendance.Cancel` sets both `CancelledAt` *and* `CheckedOutAt` to the same moment. `CheckedOutAt` is what the partial unique indexes and every occupancy query (`LockerResponse.Projection`, the "currently inside" list) actually filter on, so a cancelled visit has to look closed to all of them without teaching each query a second condition. `CancelledAt` alone answers a narrower question — *why* it closed — for the one place that cares (the member's own history).
- **Resource address depends on whether the resource exists yet.** Check-in stays posted under the member (`POST /api/members/{id}/attendance/check-in`) because there's nothing to address until it returns one. Check-out and cancel address the attendance directly (`POST /api/attendance/{id}/check-out`) once it exists, the same split `SubscriptionsEndpoints` already made between selling (posted under the member) and freeze/unfreeze/cancel (addressed by the subscription's own id).
- **"Who and when" doesn't always need its own column.** BUSINESS_RULES.md says cancelling "marks the attendance cancelled (who and when)." *When* is `CancelledAt`, a real column, because the domain rule (the cancel window) needs it. *Who* is already on every entity for free — `Entity.UpdatedBy`, stamped by `AuditableEntityInterceptor` from `ICurrentUser` — so no `CancelledByUserId` was added. `Subscription.Cancel` made the identical call in task 4.1; this is the second time it came up, which is what makes it a pattern rather than a coincidence.
- **A second method on an interface that only had one.** `IGymCalendar` existed to answer "what day is it" (`Today()`). Filtering `Attendance.CheckedInAt` — a UTC moment — by a `DateOnly` range needed the inverse operation, turning a business day back into a UTC moment (`StartOfDayUtc`). It belongs on the same interface because it's the same responsibility (the one place that knows `Gym:TimeZone`), not a new concern bolted on.
- **Deliberately not adding concurrency protection here.** Every other mutable entity (`Member`, `Plan`, `Subscription`, `Locker`) carries an `xmin`-backed `Version`. `Attendance` still doesn't, even though `CheckOut` and `Cancel` are its first mutations. The roadmap gives concurrency races for this exact feature their own task (5.4: "two parallel check-ins... fix any issues found"), so adding a guard now would be solving a problem before the task whose job is to go looking for it. Task 5.2's member lock was different: double-consuming a session was 5.2's own correctness requirement, not a race deferred to later.
- **Two aggregates, one `SaveChangesAsync`.** Cancelling loads and mutates both an `Attendance` and its `Subscription` in one handler, then calls `SaveChangesAsync` once. No explicit `BeginTransactionAsync`: EF Core already wraps a single `SaveChangesAsync` in one database transaction, so both writes commit together or neither does, without reaching for the heavier transaction+lock pattern `CheckInHandler` needed for a different reason (serializing two *concurrent requests*, not two writes in the same request).
- **An ambiguous business rule, asked rather than guessed.** BUSINESS_RULES.md excludes cancelled attendances from "attendance reports" (§7, §12), but 5.3's own member-history endpoint isn't the Phase 9 report the rule was written for. Rather than write another "decided by Claude, pending review" note, this one was asked directly: history includes cancelled visits, marked by `CancelledAt`, because it's an operational audit view of one member, not a statistic. The difference from the standing "decided while away" notes elsewhere in BUSINESS_RULES.md is that the developer was here to ask.
- **A cross-field FluentValidation rule.** `From <= To` isn't a per-property rule, so it's `RuleFor(query => query)` with a `.Must(...)` over the whole record, plus `.OverridePropertyName(nameof(To))` so the 400 response still points at a sensible field — the same trick `CreateStaffValidator` already used for a full-name check that depends on more than one input.

## 5.4 — Concurrency tests

- **A lock can turn a race into an ordinary business rule.** The roadmap expected "two parallel check-ins for the same member... one gets 409," but tracing `LockMemberAsync` shows the second request physically blocks at `SELECT ... FOR UPDATE` until the first commits — by the time it wakes up, it just sees an already-open attendance and returns the same `Attendance.AlreadyCheckedIn` (422) as two *sequential* calls would. The database's unique index (which would answer 409) never gets a chance to fire, because the lock already resolved the conflict one layer up. Two different-looking outcomes — "prevented" and "detected" — are really the same safety net working at two different points, and a concurrency test has to trace which one a given precondition actually reaches.
- **No lock at all is sometimes the right call, if something else catches the miss.** The free-locker query in `CheckInHandler` takes no lock — two different members' check-ins never serialize against each other — so two transactions can both see the same locker as free before either commits. That is the genuine race: whichever `INSERT` loses hits the partial unique index on `locker_id` and the handler's existing `catch (UniqueConstraintException ...)` turns it into `Attendance.ChangedConcurrently` (409). Locking every locker row would remove the race but serialize unrelated members' check-ins for no reason; catching the constraint violation costs nothing until two people actually grab for the same locker at once.
- **A concurrency test can pass for the wrong reason.** `ShouldAllBe(status == Created || status == Conflict)` is true even if the race never actually happens in a given run — every response could just come back `Created` because the six requests happened to interleave without ever colliding. Before trusting the test, it was run several times with the status codes captured to a file: every run produced exactly one `Created` and five `Conflict`s, confirming real parallel HTTP requests against the Testcontainers Postgres instance genuinely overlap enough to hit the index, not just that the assertion is loose enough to always pass.
- **This task's "fix any issues found" had nothing to fix.** Both races were already handled correctly by code written in 5.2 (the member lock, and the `UniqueConstraintException` catch block) — 5.3's own learning note even predicted this task by name when it explained why `Attendance` deliberately has no `xmin` column yet. Writing the tests here didn't change behavior; it turned an implicit design decision into an explicit, regression-proof guarantee. A concurrency task doesn't have to find a bug to be worth doing.
- **My notes:**

## 5.5 — Background jobs

- **A job persisted in the database survives what an in-process timer doesn't.** A `Timer` or `IHostedService` loop forgets everything the moment the process restarts — if the API redeploys at 22:58, a 23:00 in-memory schedule never fires. Hangfire writes the job's *definition* to Postgres (`RecurringJob.AddOrUpdate`) and a separate polling loop reads it back, so the schedule survives restarts and deploys. This is the same reasoning refresh tokens are rows instead of server memory (task 1.3): anything that must outlive one process belongs in the database.
- **Cron needs a time zone, not just a time.** `Gym:ClosingTime = 23:00` alone is ambiguous — 23:00 in what frame? `RecurringJobOptions.TimeZone` (built from the same `IGymCalendar.TimeZone` that already computes "today") is what makes Hangfire fire at 23:00 *Tehran* time regardless of the server's own clock, the identical problem `GymCalendar.Today()` solved for business dates in task 0's very first ADR-adjacent decision.
- **A second interface gains a member for a caller nobody expected yet.** `IGymCalendar` had `Today()` and `StartOfDayUtc()`, both consumed by request handlers. Nothing in Application needed the raw `TimeZoneInfo` until the job *scheduler* — infrastructure code that runs once at startup, not a use case — needed to hand it to Hangfire. Same interface, same responsibility ("the one place that knows `Gym:TimeZone`"), a caller in a different layer.
- **A background job goes through the same audit path as everything else, on purpose.** `AutoCheckoutHandler` loads open attendances as tracked entities and calls `SaveChangesAsync`, instead of a faster set-based `ExecuteUpdateAsync`. The set-based version would silently skip `AuditableEntityInterceptor` (which stamps `UpdatedBy`) entirely, because it issues raw SQL outside the change tracker. The interceptor's own doc comment already anticipated this: "`ICurrentUser` is null for rows written by... background jobs, which act on nobody's behalf" — so `UpdatedBy = null` is the *correct*, already-designed-for answer, not a gap to work around.
- **One database, two schemas.** Hangfire's own job-queue tables live in a `hangfire` schema instead of the app's `public` one. Not a style preference: the integration test harness's Respawn reset is scoped to `SchemasToInclude = ["public"]` specifically so a per-test cleanup can never touch infrastructure bookkeeping it doesn't own — the schema split is what makes that scoping safe to add here without either tool needing to know about the other.
- **A design decision walked back within the same session.** The Hangfire dashboard was first mapped alongside Scalar with `.AllowAnonymous()` reasoning applied only in a code comment, not in code — `UseHangfireDashboard` is old-style branch middleware (matches on `HttpContext.Request.Path` directly), not a routed endpoint, so there is no `IEndpointConventionBuilder` to call `.AllowAnonymous()` on. It still got routed through `UseAuthorization()`'s fallback policy and answered 401. A quick manual smoke test (`curl -i /hangfire`) caught it before calling the task done; the fix was to move the mapping *before* `UseAuthentication`/`UseAuthorization` in the pipeline, so it never reaches the fallback policy at all. Lesson: a conditional environment gate and an authorization bypass are two different things, and only one of them was actually written at first.
- **A real business-rule gap, not a hypothetical one.** BUSINESS_RULES.md §0 listed `Gym:ClosingTime` as "still to decide" before this task started — the roadmap needed it and the docs said to ask, so the developer picked 23:00 Asia/Tehran before any code was written, and the decision was recorded back in BUSINESS_RULES.md's "Decided values" list the same way `MaxFreezeDaysPerSubscription` was in task 4.1.
- **"Restricted to Owner" was scoped down, deliberately and visibly.** The JWT-bearer-only auth model has no way to authenticate a plain browser navigation to `/hangfire` (no session cookie, no ambient credential) — solving that properly (a query-string token bridge, or a second cookie-auth scheme just for this one route) was judged bigger than this task's actual size. The dashboard is Development-only for now, the same gate Scalar and OpenAPI already use, and the roadmap checkbox says so explicitly rather than silently claiming full compliance.

## 5.6 — UI: front desk

- **Generated types are a snapshot, not a live view.** `web/src/lib/api/schema.d.ts` still described check-in-only Attendance from task 5.2 — three tasks and a dozen fields out of date, because nothing had re-run `npm run gen:api` since. The generator needs the API actually *running*; it's easy to finish a backend task, commit, and forget the frontend has no way to know the contract changed until someone tries to use it. The type system caught it immediately once this task started (`AttendanceResponse` had no `checkedOutAt` to read), which is the whole point of generating types from the OpenAPI document instead of hand-declaring them — a stale contract is a compile error, not a runtime surprise.
- **A shared presentational table takes a callback, not a hook.** `MembersTable` grew an optional check-in column (`onCheckIn`/`checkingInId`) rather than calling `useCheckIn()` itself, the exact shape `PlansTable` already used for `onToggleActive`/`busy`. One `GET .../attendance` call serves both the profile's "currently inside" banner and its history table below it, instead of two requests asking almost the same question.

Locker creation became one inline number field on `LockersPage`, not a separate `/lockers/new` route with React Hook Form and Zod, because Members and Plans need that machinery for multi-field forms with cross-field rules and this one doesn't. Neither shortcut was silent: both are named in the plan and in this note, the same way `AttendancePolicy`'s Development-only dashboard was named in task 5.5.
- **"Attempt, then explain" beats duplicating a business rule in the client.** The cancel-check-in window (30 minutes) and a locker's occupied-while-out-of-service rule are both enforced only server-side; every button that could hit either one is always shown, always clickable, and a rejection just surfaces the server's own Persian message through the same notice pattern every other mutation on this page uses. Teaching a form to also know `Gym:CancelCheckInWindowMinutes` would be a second copy of a rule that already lives in `Attendance.Cancel`, guaranteed to drift the day someone changes one without the other.
- **A test suite can prove a feature works without a browser.** This session's Chrome extension wasn't connected, so there was no literal click-through — but 23 new Testing Library tests render the *actual* `CurrentlyInsidePage`, `MemberProfilePage` and `LockersPage` components into real jsdom, fire real clicks, and assert on what a person would actually see, against a mocked network boundary. That is meaningfully different from a type-check passing: it is proof the UI text, the button labels and the state transitions are correct, just not proof of pixels. The dev server and Vite's `/api` proxy were confirmed serving and forwarding correctly against the real backend; what wasn't done was an authenticated interactive walkthrough, and the roadmap says so rather than implying more coverage than there is.

Renamed to "ثبت خروج" ("record check-out"). A small reminder that accessible names are a shared namespace across the whole rendered page, not just within one component.

## 6.0 — Deployment decisions (planning session, no production code)

The question that started this was whether a gym that is entirely internal — Iranian server, Iranian SMS panel, members who never log in — breaks anything in the design. The answer was no: the application needed no change, but Phase 6 of the roadmap had been written against assumptions that turned out to be wrong, so this session rewrote Phase 6 and recorded the deployment shape as `docs/adr/0003-deployment-topology.md`.

- **"Does this break the architecture?" is answered by looking for external dependencies, not by reading the architecture.** The check was concrete: does any layer call a foreign service, does the frontend load anything from a CDN, does business logic read a clock the deployment controls? All three were already no — `client.ts` uses `window.location.origin`, fonts are self-hosted by rule, "today" comes from `IGymCalendar`. Decisions made for other reasons (same-origin so cookies behave identically in dev and prod; self-hosted fonts so the build is reproducible) turned out to be exactly what a locally-hosted deployment needs. That is the usual shape of portability: it is the accumulated absence of ambient dependencies, not a feature someone adds later.
- **Capacity planning means finding the one number that binds.** The first version of this plan treated 5 GB of disk as the constraint and built the whole phase around slimming things down. The real figure was 50 GB, and the binding constraint turned out to be 2 GB of RAM instead. The plan changed shape completely — not because the conclusion "don't run Seq in production" changed, but because its *reason* did, and a reason recorded wrongly is a decision nobody can revisit correctly later. ADR 0003 says "rejected on memory" specifically so that adding RAM is recognisable as the thing that reopens it.
- **A reverse proxy is what makes "one origin" true in production.** Caddy serving the React build and proxying `/api` to the API is the production twin of the Vite dev proxy, and `vite.config.ts` says so in a comment written back in task 0.7. The payoff is that CORS stays a development-only safety net instead of something the application depends on, and the `SameSite=Strict` refresh cookie works in both places for the same reason rather than by coincidence.
- **A `Secure` cookie is a deployment requirement, not just a flag.** `RefreshTokenCookie` sets `Secure`, so a browser will not store or send it over plain HTTP to anything but `localhost`. That single line decides that production must be HTTPS — there is no "we'll add TLS later" path that does not also mean weakening authentication. Constraints that propagate outward from a security choice like this are worth noticing early, because they are cheap to satisfy when planning and expensive to discover during a go-live.
- **Automatic certificates need a name, not an address.** Let's Encrypt issues for domains through a challenge that proves you control the name; a bare IP has nothing to prove control of in the ordinary flow. This is why the plan spends a domain registration rather than deploying to `https://<ip>`, and why the earlier on-premise plan had reached for Caddy's `tls internal` instead — on a LAN with no public name, a private CA whose root you install on a handful of machines is the honest answer. Different topology, different correct answer.
- **Build where the RAM is.** `dotnet publish` and `npm run build` each comfortably exceed a gigabyte, and running one beside a live Postgres on a 2 GB host invites the OOM killer to pick a victim mid-deploy — possibly the database. Building on the development machine and shipping the image with `docker save`/`docker load` costs one extra step and removes an entire class of deploy-day failure. Note the reason is memory, not disk: with 50 GB the *space* was never the problem.
- **An EF migration bundle is a self-contained executable, so the server needs no SDK.** `dotnet ef migrations bundle --self-contained` produces one binary that applies the migrations and exits. The alternative — migrating at application startup — is convenient and already ruled out in ARCHITECTURE.md, because two API containers starting at once would race each other through the same migration, and a failed migration would leave you with an application that boot-loops instead of one that simply has not been upgraded yet.
- **Containers do not automatically have a time zone database or ICU.** `InvariantGlobalization=false` needs ICU to format Persian dates; `Gym:TimeZone = Asia/Tehran` needs tzdata to resolve at all. Debian-based .NET images carry both, Alpine does not. The good news is that the startup validation of `Gym:TimeZone`, added long before there was a container, makes this fail loudly: the app refuses to start rather than quietly computing "today" in UTC and expiring subscriptions a few hours early.
- **A proxy makes every client look like one client.** ASP.NET reads `RemoteIpAddress`, which behind Caddy is always Caddy. The login rate limiter would then put every user in one bucket, and `UseForwardedHeaders` is what restores the real address from `X-Forwarded-For`. This was already written down as a task 11.2 item; it moved to 6.2 because the severity depended on the topology — sharing a bucket among three staff on a LAN is a nuisance, but doing it on a publicly reachable login endpoint is a defect.
- **A dump is not a replica, and a backup is not a backup until it has been restored.** What the gym's flash drive will hold is a `pg_dump` file: bytes that *can* become a database, after a deliberate manual step nobody has practised. Calling it "a second database" would be comfortable and wrong, which is why task 6.3 has "restore rehearsed" as its own checkbox and its own "Done when". The failure mode being defended against is not losing the file; it is discovering on the worst possible day that the restore command was never run.
- **Direction of connection is decided by NAT, not by preference.** The server cannot open a connection to the gym's computer, because that machine sits behind a router with no inbound route to it. So the backup copy is *pulled* from the gym side on a schedule, not pushed from the server. Whenever one side of a link is publicly addressable and the other is not, the addressable side is the one that gets connected *to*.
- **Design an interface against the provider's real constraint, not the one you wish it had.** Iranian SMS panels generally require a pre-approved template for service messages: you send a template id and named parameters, not a sentence. An `ISmsSender` shaped as "send this string" would have to be rewritten the day the real provider was wired up in task 10.3. A template-first interface still works if the panel happens to allow free text, but the reverse is not true — so when two shapes are not symmetric in cost, pick the one that survives being wrong.
- **Log rotation without a new package.** Dropping Seq in production could have meant adding `Serilog.Sinks.File`, which CLAUDE.md would require asking about. It did not: Serilog already writes to the console, and Docker's `json-file` driver rotates that with `max-size` and `max-file`. Reaching for a dependency to solve a problem the platform underneath already solves is a habit worth catching.

## Random locker assignment

- **Not all non-determinism needs injecting.** CLAUDE.md is strict that time is never read ambiently: `DateTime.Now` is banned and `TimeProvider` is injected, because business rules depend on the *exact value* — expiry, freeze days, which day a subscription starts — so a test has to pin it down. Randomness here looked like the same problem and is not. No rule depends on *which* locker a member gets; every free one is equally correct. There is nothing for a test to pin, so `EF.Functions.Random()` goes straight into the query and no new interface appears. The question to ask is not "is this non-deterministic?" but "does any rule depend on the value?"
- **A statistical assertion can be stronger than it looks.** `CheckIn_RepeatedVisits_DoesNotAlwaysPickTheSameLocker` draws ten times from five lockers and asserts more than one distinct number came back. That sounds flaky, but the odds of a false failure are 5⁻⁹ — about one run in two million — while the behaviour it guards against (ordering by number again) fails it on *every* run. A test does not have to be deterministic to be reliable; it has to have a failure probability far below the rate at which real bugs appear.
- **`EF.Functions` is the escape hatch that stays translatable.** `OrderBy(l => Guid.NewGuid())` or `Random.Shared.Next()` inside a LINQ query cannot be turned into SQL — EF would either throw or silently pull the whole table into memory and sort it there. `EF.Functions.Random()` exists precisely so the provider can map it, and Npgsql's `RandomTranslator` turns it into Postgres's `random()`. Worth checking the provider actually has the translator before relying on one of these, which is a two-second look inside the package.
- **Changing a rule means changing the file that owns it.** The lowest-numbered pick was not an implementation detail; it was written down as step 3 of BUSINESS_RULES.md §7. Editing the handler without editing that line would have left the source of truth lying, and CLAUDE.md says the file wins when they disagree — so the next person would have "fixed" the code back.
- **The concurrency guarantee was never in the ordering.** It was tempting to worry that random picking would break `CheckIn_ParallelForTheLastFreeLocker_NoLockerIsAssignedTwice`. It does not, because that safety never came from *how* a locker is chosen — it comes from the partial unique index on `locker_id where checked_out_at is null`. Random picking actually reduces collisions, since two simultaneous check-ins no longer both reach for locker 1. When a change feels like it threatens an invariant, the useful move is to find where the invariant is actually enforced.

## Two reported bugs: live plan name, and which subscription a check-in uses

- **Snapshot or live is a per-field decision, not a per-entity one.** `Subscription` copied four things from `Plan` at sale time, and the reported problem was that renaming a plan left old sales showing the old name. The fix was not "stop snapshotting" or "keep snapshotting" but splitting the four: the **numbers** (`Price`, `DurationDays`, `TotalSessions`) stay copied because they are what the member bought and a receipt has to keep saying so; the **name** is read live because it is only a label. Asking "what breaks if this changes later?" field by field gives a different answer for money than for text.
- **Deleting the duplicate is what makes the rule true.** Once the name comes from `Plan`, leaving `plan_name` on `subscriptions` would have been a column nobody reads and nothing updates — the next person to query the table directly would get the stale one. Dropping it in a migration costs the historical name, which is exactly what the decision gave up, and leaves one place that can answer "what is this plan called".
- **Changing a method signature is a cheap way to find every caller.** `SubscriptionResponse.From` gained a `planName` parameter rather than reaching for the plan itself. Six call sites stopped compiling, each had to decide where its name comes from, and `SubscriptionSeller` — which already had the `Plan` in hand — needed no query at all. A default value or a nullable would have let some of them quietly keep serving nothing.
- **The same rule implemented twice will drift.** The check-in bug was not a typo. The frontend's `pickCurrentSubscription` knew that an active subscription beats a later-starting queued one, and said so in a comment. The backend's check-in sorted by end date and took the first. Both were written deliberately; neither knew about the other. The symptom was the worst kind: the profile card showed the right subscription while the button next to it refused the member. `SubscriptionSchedule.InEffectToday` is now the one place that answers the question, and the frontend rule is a display concern layered on top of it rather than a second copy.
- **A test that never existed is more dangerous than a test that fails.** Every check-in failure mode had a test — expired, frozen, exhausted, no subscription. Nothing covered "active **and** queued", because that combination only appears when a member renews early, and the tests each set up one subscription. The gap was invisible in a green run.
- **A rule written for one moment may need to hold at another.** BUSINESS_RULES.md §4 already said an exhausted subscription must not make anyone wait, and `NextStartDate` implemented it — at the moment of sale. A member who bought the renewal *first* and used up their sessions *afterwards* hit the same situation from the other direction and was stranded. Extending the rule meant asking when it should apply, not just what it says.
- **Shipping a schema change is two steps, and the second one has no reminder.** Dropping `plan_name` was correct in the code and correct in the migration, and the whole suite stayed green — because the integration fixture builds a fresh Postgres and migrates it on every run. The development database was never migrated, so the running app inserted subscriptions without a column that was still `NOT NULL`, and every single sale answered 500. Green tests say the code and the migration agree with each other; they say nothing about the database on your machine.
- **The log had the answer in one line, and guessing did not.** Two rounds of reasoning about exclusion constraints and queued subscriptions produced plausible theories and no progress. One query against Seq returned `23502: null value in column "plan_name"`, which named the cause exactly. When a system already records what happened, reading that record comes before reasoning about what might have happened.
- **"Unexpected error" is a design failure, not just an unlucky message.** A pending migration is a precise, detectable state with a one-line fix, and the application presented it as a mystery on an unrelated screen. `PendingMigrationsHealthCheck` gives that state a name in the place built to report exactly this kind of thing: `/health` turns Unhealthy, lists the missing migrations, and says what to run. The cost of not doing that is paid by whoever hits it next, including on the production server after a deploy that forgot the bundle.
- **Invalidating a cache is part of writing the feature, not cleanup.** Promoting a queued subscription during check-in rewrites its dates, so the attendance mutations now invalidate the subscription caches too. Seven frontend tests started failing — not because the change was wrong, but because they had stubbed only the endpoint they were thinking about while the page had always called two. The failing tests were describing the page less accurately than the page described itself.

## Reported bug: "the subscription has not started yet" after a same-day renewal

- **Not every reported bug is a defect in the behaviour; sometimes the defect is in what the system *says* about it.** Refusing that check-in was correct: BUSINESS_RULES.md §4 says an exhausted subscription that only started today still covers today, so the renewal starts tomorrow — and `InEffectToday_ExhaustedOnItsFirstDay_DoesNotPromote` had been asserting exactly that all along. Separating "the rule is wrong" from "the explanation is wrong" before touching anything is worth the ten minutes: the first needs a business decision and a migration, the second needed one error code.
- **An error chosen by convenience tells the wrong story.** The handler reported the failure through `live.MaxBy(s => s.EndDate)`, which in this case is the queued renewal, so the front desk was told "the subscription has not started yet". Every word of that is true and the whole sentence is misleading — it sounds like the sale went wrong, when the answer the member needs is "come back tomorrow". Which error a handler returns is part of the feature, not a leftover from the last check.
- **A message may only promise what the code guarantees.** "The next one starts tomorrow" is safe to say here, and not by luck: the branch is only reached when the exhausted subscription was clamped to its own start date, which is today, so the queue moves up on the first check-in attempt tomorrow whatever start date was sold. Had the queued row's own `StartDate` been used for the sentence, the message would have named a date three weeks out that the promotion rule was about to overwrite.
- **Knowing where an invariant is enforced tells you the price of changing it.** "Just let the renewal start today" reads like a one-line change to `CloseExhaustedEarly`. It is not: no-overlap is a Postgres exclusion constraint, and `ck_subscriptions_dates` requires `end_date >= start_date`, so a zero-day subscription needs a migration on both and leaves history showing a row that ended before it began. That cost is exactly what made "fix the sentence" the better trade here — the situation it describes happens only when a member burns every session on the day they bought the plan.

## 2.4 — Member birth date (and the first Jalali date input)

- **A rule that needs a calendar cannot live in a validator, and here that is enforced by a test you would not expect.** "Not in the future" is meaningless without a today, and the gym's today is Asia/Tehran, not the server's — so BUSINESS_RULES.md §2 puts the rule in the entity and has the handler pass the date in. What makes it non-negotiable is `ErrorCatalogTests`: it collects every validator's error codes by calling `Activator.CreateInstance` on each one. A `CreateMemberValidator(IGymCalendar)` would throw `MissingMethodException` and fail an architecture test that has nothing to do with birth dates. The same shape already existed — `Members.PhoneNotMobile` needs libphonenumber, so it too arrives as a whole-request failure and `codeFields` puts it under the right box on the form.
- **A nullable column still gets a constraint, but only one an immutable expression can state.** `birth_date <= CURRENT_DATE` is the obvious database mirror of the rule and Postgres refuses it outright: `CURRENT_DATE` is not immutable, so it cannot appear in a `CHECK`. The database therefore keeps the half it can enforce — a fixed `>= DATE '1900-01-01'` floor — and that floor is not a weak version of the 120-year rule. It catches a different bug: a Jalali year (`1370-05-12`) written straight into a Gregorian column, which is exactly the mistake this whole feature invites.
- **Changing a signature is how you find every caller, and it is worth the noise.** `Member.Create` gained two required parameters and seventeen call sites stopped compiling. Giving them defaults (`DateOnly today = default`) would have compiled everything untouched and made `today` silently `0001-01-01` for any caller passing a real date — turning every birth date into "in the future". Fourteen of those call sites were the identical fixture line, which is why they became one `TestMembers.Seed` helper rather than fourteen edits that would need making again next time.
- **`toString` on a date is a locale bug waiting for a machine with different settings.** `tomorrow.ToString("O")` failed the build on CA1305. The fix was not to add a format provider but to delete the formatting: `System.Text.Json` already writes a `DateOnly` as `yyyy-MM-dd`, so the anonymous object can carry the `DateOnly` itself. Converting a value to a string before something that already knows how to serialise it is usually a step backwards.
- **Midnight is not a safe time to build a date, and this is the bug that would have shipped.** `new Date(y, m, d)` builds local midnight, and Iran moved its clocks *at midnight* through 1991–2005 and 2008–2022 — precisely the years member birth dates fall in. A date built at 00:00 on one of those nights lands on the day before, so a birthday would silently shift by one. Every `Date` the conversions build is at **noon**, which no time zone has ever skipped. `toISOString()` is never called on these values either, for the same reason.
- **A library that is lenient about impossible dates will happily invent one.** `date-fns-jalali`'s `newDate(1404, 11, 30)` does not refuse the 30th of Esfand in a common Jalali year — it rolls over into 1 Farvardin 1405. Without converting back and checking the parts match, the form would have saved a date nobody picked. The round-trip is three comparisons and it is the difference between "refused" and "wrong".
- **Two implementations of the same calendar is a fact to test, not a thing to avoid.** The profile page shows dates through ICU (`Intl` with `calendar: "persian"`); the edit box shows them through date-fns-jalali. Merging them was not worth it — ICU is already there and free, and the picker needs real arithmetic — but if a Node or ICU upgrade made them disagree, a member's profile and their edit form would show different birth dates. `toJalaliInput_AgreesWithFormatDate` is the tripwire.
- **The widget decides whether a field can stay uncontrolled.** Every other field in `FormField.tsx` is spread from `register()`, and `MoneyField` shows the trick that keeps a *formatting* field uncontrolled: rewrite `event.target.value` before `register`'s `onChange` sees it. That trick cannot work here, because the value (`1991-08-03`) and the display (`۱۳۷۰/۰۵/۱۲`) are different strings, and clicking a day in a popup fires no native `change` event at all. So this is the codebase's first `Controller` — placed at the call site, so `JalaliDateField` itself stays as ignorant of React Hook Form as its neighbours.
- **Replacing a library's input was the cheaper path, not the harder one.** `react-multi-date-picker` renders its own `<input>`, and its own typings say `id`, `name` and `placeholder` stop working the moment you use `render`. Using `render` anyway bought three things at once: the field keeps the `<label htmlFor>` and `aria-describedby` wiring that the existing tests assert and `getByLabelText` depends on; typed text is parsed by `toIsoDate`, the one conversion this app tests, instead of a second parser that does not know Arabic-Indic digits; and the clear button has somewhere to live.
- **A test that fails can be right about the code and wrong about the intent.** `JalaliDateField_Blur_SnapsTheTextBackToTheCommittedDate` asserted that deleting part of a date and tabbing away restored the old one. It failed, and the component was correct: once the text stops being a whole date the value must become empty, or the form would send a date the box no longer shows. The invariant worth keeping is "what is on screen is what will be sent", and the test was renamed to say that instead.
- **A warning you did not cause is still worth measuring before you mention it.** `npm run build` warns that the bundle is over 500 kB. Stashing the frontend changes and building again gave 600.63 kB against 690.04 kB — so the warning predates this task, and the calendar added about 89 kB to a chunk that was already too big. Two minutes of checking turned "I think this was already there" into a number.
- **A green test suite does not prove a dependency renders in a browser, and this one did not.** Every jsdom test passed — including one asserting the Persian calendar mounts — and `/members/new` still died with "Element type is invalid … got: object". `react-multi-date-picker` is CommonJS and puts its component on `exports.default`; Vitest's interop reads that and hands back the component, while Vite's pre-bundling hands a default import the whole module object. Two toolchains, two answers, and only one of them is what the user sees. The fix was three lines; the finding was that the test I trusted most — "the calendar really mounts" — was the one that could not see the bug.
- **The transformed module is the evidence; everything before it is theory.** Two rounds of reasoning about ESM/CJS interop produced plausible stories. Fetching `http://localhost:5173/src/components/FormField.tsx` from the running dev server ended it in one line: `const DatePicker = __vite__cjsImport4_reactMultiDatePicker;` beside `const DateObject = __vite__cjsImport4_reactMultiDatePicker["DateObject"]` — the named import resolved, the default one did not. When a tool rewrites your code, read what it wrote.
- **A verification that cannot fail is not a verification.** After fixing it, a throwaway page rendered the field in headless Edge and showed `۱۳۷۰/۰۵/۱۲` over `1991-08-03`. That only meant something after putting the broken import back and watching the same page report the exact error the user had. A check nobody has seen fail is a check nobody knows works.

## 4.7 — Open accounts: member debt, and who may cancel or refund

- **A calculated number needs one owner, not one implementation per screen.** Debt shows up in three places (the members list, the profile card, the check-in response) and each could have summed the subscriptions itself. `MemberDebt` in Application is the single answer, the way `PaymentLedger` already owns "net paid" and `PlanNames` owns "the plan's name now". The proof it was the right seam: `ListMembersHandler` got *shorter* — its hand-rolled two-query `HasUnpaidSubscription` batch was already this calculation, written for a boolean.
- **A boolean answered the wrong question.** `HasUnpaidSubscription` told the front desk *that* a member owed something. Once the gym runs open accounts, everyone owes something sooner or later, so the flag lights up for a member who is 10,000 Toman short and for one who never paid at all. The column had to become an amount, and that is an API change (`bool` → `decimal`), not a formatting change.
- **Adding a required parameter is a search for callers that the compiler runs for you.** `Cancel(reason, now)` became `Cancel(reason, today, now)` because "is this expired?" needs a date, and seventeen call sites stopped compiling. A default (`DateOnly today = default`) would have compiled everything and silently evaluated every cancellation against year 1, where nothing is ever expired — the rule would have been in the code and absent from the behaviour.
- **The tests that break tell you whether you understood the rule.** The old `Cancel_AnyStatusButCancelled_Succeeds` theory listed five states. Under the new rule three of them still pass, `exhausted` fails as `AlreadyUsed` and `expired` fails as `Expired` — and the existing fixtures produced exactly that split without being touched, because `InState("exhausted")` consumes sessions and `InState("expired")` does not. A rewritten test that needs new fixtures to pass is worth re-reading; this one only needed splitting.
- **Where a check sits decides whether it is a rule or a suggestion.** `RefundAfterUse` first went in above the transaction, next to the `subscription` already loaded there. That reads fine and is wrong: check-in takes the member's lock before consuming a session, so a visit starting at that moment would slip between the read and the refund. Moving the read under `LockMemberAsync` costs one small query and makes the invariant true rather than usually true.
- **Two ways to say "you cannot do that", and only one of them is honest.** The subscription row used to grey out buttons. Disabled tells the user "not now" for an action that will *never* be possible again on a finished subscription, and it hides the one that is — "ثبت پرداخت" stays for as long as anything is owed, whatever the status, because debt outlives the thing that created it. Rendering only the possible actions made the row's five `disabled=` expressions into five named conditions, each one the rule the API would answer with.
- **A fixture that cannot exist teaches the test nothing.** `queuedRenewal` inherited `usedSessions: 3` from the subscription it was spread from — an `Upcoming` subscription with three visits on it. Nothing had cared until a rule started reading that field. The fix was one line, but the lesson is that a fixture is a claim about the domain, and an impossible one quietly waits for the rule that will trip over it.
- **Verification has to reach the thing that changed.** Task 2.4 ended with a jsdom suite that could not see a browser-only bug, so this task's check-in was a real browser again — except the app needs a login and the seeded owner password had been changed. Rather than reset the developer's database, a throwaway page mounted the three changed components in headless Edge behind a stubbed `fetch`. The dumped DOM listed five `aria-label`s: the used subscription offering payment and freeze, the unused one offering cancel and refund, and the finished, settled one offering nothing at all. That is the rule, read off the screen rather than off the test.

## 4.8 — One money field for the whole app

- **A formatting field can stay uncontrolled; a field that *explains* its value cannot.** Task 2.4's note said `MoneyField` showed the trick for keeping a formatting field on `register()`: rewrite `event.target.value` before React Hook Form's `onChange` sees it. Adding the words underneath broke that, and not for a stylistic reason — the words have to be right before anybody types, and an uncontrolled input's initial value is put there by RHF through a `ref` after render, where no `onChange` ever fires. The plan *edit* form is where that showed: it loads a price of `900000` and would have shown a bare run of zeros with no words under it. Making the field controlled, exactly like `JalaliDateField` beside it, fixed the display and the words in the same move. The dividing line is not "does it format" but "does the field need to know the value".
- **Removing duplication is easy; knowing which half to remove is the work.** `normalizePrice` and `normalizeAmount` were character-for-character identical, and `payments/schemas.ts` carried a comment explaining that the copy was deliberate. Only the *spelling* of an amount merged into `normalizeMoney`. `priceProblem` and `amountProblem` stayed apart, because they answer to `Plans.*` and `Payments.*` codes and the frontend maps codes to Persian text — merging them would have meant one of the two forms reporting an error code the API never sends for it.
- **Validation that can be made unreachable beats validation that fires.** `priceProblem` still returns «قیمت نمی‌تواند منفی باشد.», and the plan form can no longer produce it: `moneyDigits` drops a minus before it reaches the box. The `{ price: "-1" }` row in `CreatePlanPage.test.tsx` had to go, replaced by a test asserting that typing `-900000` sends `900000`. A rule the user cannot break is better than a rule the user breaks and is then told off for — but the server-side code stays in `codeFields`, because the API is still entitled to say it.
- **`bigint`, not `number`, is what a `numeric(18,2)` actually is.** `SubscriptionHistoryRow` computed the amount still owed as `Number(price) - Number(netPaid)`. Two doubles, so `0.30 − 0.10` can land on `0.19999999999999998` and an amount near the sixteen-digit ceiling loses its last digits outright. `subtractMoney` converts both sides to whole hundredths as a `bigint`, subtracts, and puts the point back — eighteen significant digits, which a double runs out of at fifteen.
- **A rule can be unenforceable at exactly one point and still worth stating.** §13 says no money value is ever a JavaScript number. Everything typed now obeys it, and so does everything displayed. The read path cannot: the API serializes `decimal` as a JSON number, so `JSON.parse` has already produced a double before a single line of this code runs, and 4.8 was scoped "no API change". `formatMoney` and `isPositiveMoney` therefore accept `string | number` and convert back to a string immediately, which turns an invisible leak into one named boundary. Closing it properly is a `JsonConverter<decimal>` on the API — worth doing, worth not smuggling into a frontend task.
- **An accessibility wire is also a correctness wire.** The words line is the check against a miscounted zero, so it is in the input's `aria-describedby` alongside the error. That turned two existing assertions from `toHaveAttribute("aria-describedby", message.id)` into `toContain(message.id)` — the price box is now described by two things. The failing assertions were right that the attribute changed and wrong that it should hold only one id.
- **Hand-writing number-to-words is mostly deciding what people actually say.** The tables are twenty minutes of typing. The judgement is that ۱۰۰۰ is «هزار تومان» and never «یک هزار تومان», while ۱٬۰۰۰٬۰۰۰ *is* «یک میلیون تومان» — so the rule is "drop the یک when the scale word starts with هزار", which also gives «هزار میلیارد» for 10¹². And `amountInPersianWords` returns **nothing** rather than a guess for a half-typed amount or one with three decimals: a line under a money box that is not the amount is worse than no line at all.

## 5.7 — Cardio (هوازی) and gym service charges

- **The rule you argue against is sometimes one you wrote yourself.** §5's "there is no wallet and no credit balance" was marked *"Decided by Claude during this session; pending review."* When the developer proposed a wallet, the honest first move was to say that out loud rather than defend the line as settled. The trade-off that decided it: a wallet splits "money arrived" from "money earned", so Phase 9's revenue figure would have to choose between the deposit date and the allocation date; debt stops being the sum of items the breakdown can point at; and refunds gain a destination. The rule survived review, which is worth more than a rule nobody looked at twice — and §5 now records the reasoning so the question does not start from zero next time.
- **A void of a paid charge needs somewhere for the money to go, and "nowhere" is not an option.** Without a wallet, a voided charge that had been paid would leave the gym holding money for something it has decided is not owed. So the void writes refunds in the same transaction. The part that took thought was the payment *method*: asking the user is impossible on the cancel-check-in path, which voids charges as a side effect and has nobody to ask. Grouping the net paid **by method** and writing one refund per method answers it without input and without guessing — and it is also the more correct answer, because money goes back the way it came.
- **Where a check sits decides whether it is a rule or a suggestion — again.** `ChangeAmount` refuses once anything has been paid. Reading the payments above the transaction would have been a suggestion: a payment committing between the read and the save would leave a paid charge showing an amount nobody agreed to. Both it and the void read under `LockMemberAsync`, the same lock registering a payment takes. This is the second task in a row where that was the subtle part; it is becoming the house pattern rather than a one-off.
- **The one-target rule moved from a comment into the type system.** `Payment` gained a third possible parent, and `Create` was about to grow a second nullable `Guid?` parameter with a comment explaining that exactly one must be set. A private `Target` record struct with `Target.Subscription(id)` and `Target.ServiceCharge(id)` says it instead, and Phase 7 adds one factory rather than a third nullable. The check constraint in the database says the same thing; the difference is that now the C# cannot express the invalid state either.
- **A boolean flag that the API answers beats a rule the screen re-derives.** `ServiceChargeResponse.CanChangeAmount` is "the visit is open, nothing is paid, not voided" — three facts living in three tables. The frontend could have re-derived it from `voidedAt`, `netPaid` and the visit's `checkedOutAt`, and would then hold a second copy of a rule that belongs to the API. One flag means the screen and the endpoint can never disagree about what is still allowed.
- **A test that will not compile is better than a fixture that quietly lies.** `MemberDebtItemResponse` lost `SubscriptionId` for a kind-tagged `Id`, and the .NET tests stopped compiling — good. The frontend's `debtItem()` fixture kept its old `subscriptionId` field and every test still *passed*, because TypeScript accepted the extra property and the component simply read `undefined`. The green suite was measuring nothing. Typing the fixture as `DebtItem` rather than letting its return type be inferred is what turned that back into a compiler error.
- **`tsc --noEmit` and `tsc -b` are not the same check, and only one of them is the build.** The frontend type-checked clean and the tests were green while three real type errors sat in the code, including a renamed field on `PaymentStatusBadge`. `npm run build` runs `tsc -b`, which walks the project references; `npx tsc --noEmit` at the root did not. The lesson is not about a flag: it is that the check to trust is the one CI runs.
- **A generated type can be nullable for a reason that has nothing to do with it.** `ServiceChargeKind` came back from openapi-typescript as `"Cardio" | null`, because the enum is used as an optional field on two responses and the generator marks the shared component nullable rather than the two usages. `NonNullable<...>` at the one place the frontend names the type is the honest fix: the null belongs to "this row is not a service charge", not to the kind itself.
- **Writing the test for a rule is what found the hole in the screen.** "Debt outlives the thing that created it" (§5) was already implemented in the API — a closed visit's charge still takes a payment. The test asserting it from the UI failed, because the member profile only renders the charge box for the *open* visit, and a finished visit had left that card. Nowhere on any screen could that money be collected. The fix was to give the attendance history row the full box for closed visits and leave the open one to the card above it. The API was right the whole time; nobody could reach it.

## 6.1 — Production image and compose

- **A Dockerfile is a build recipe, a compose file is a running recipe.** The Dockerfile says how to make an image (`dotnet publish`, then copy the result into a small runtime image); `docker-compose.prod.yml` says how images run together (ports, memory, restart, health). Keeping them apart is why one image can run on your laptop and on the server unchanged.
- **Multi-stage build.** The SDK image (compilers, about 1 GB) builds the app; only the published output is copied into the much smaller `aspnet` runtime image. The final image never contains source code or build tools.
- **Layer caching decides how fast a build is.** The `.csproj` files are copied and restored before the source, so a code change reuses the cached restore layer instead of downloading every package again. Same idea for `package-lock.json` and `npm ci` in the web image.
- **The build context is the repository root.** The projects share `Directory.Build.props`, `Directory.Packages.props` and `global.json`, and a Dockerfile can only `COPY` from inside its context. `.dockerignore` keeps `bin/`, `obj/`, `node_modules`, `.env` and `.git` out of it.
- **A healthy container is not the same as a running one.** `depends_on: condition: service_healthy` makes the API wait for `pg_isready` and Caddy wait for `/health`. `/health` also reports pending migrations, so an API against an unmigrated database never becomes healthy and Caddy never starts: deploy order is migrate, then start.
- **A minimal image has no `curl`.** The `aspnet` image is Debian but ships neither `curl` nor `wget`, so the health probe is a hand-written HTTP request over bash's `/dev/tcp`, the same trick as the Seq probe in the dev compose file.
- **`${VAR:?message}` fails at `up`, not at 3 a.m.** A missing secret stops compose with a readable message instead of starting a database with an empty password.
- **Defaults in the file, sizes in `.env`.** Memory limits and Postgres tuning are `${VAR:-default}`, so a server with more RAM is a change to `/opt/gym/.env` and not to a tracked file.
- **A limit somewhere is a limit everywhere.** `max_connections=50` looked like a Postgres setting, but Hangfire's default of 20 workers held 24 idle connections, leaving the API's own pool under half. Checking `pg_stat_activity` found it; `WorkerCount = 2` fixed it (24 connections became 6).
- **Persist the certificates.** The `caddy-data` volume holds the issued Let's Encrypt certificate. Without it every recreate asks again, and Let's Encrypt rate-limits repeated requests.
- **Verify on the real image.** A green `dotnet test` runs the app on your machine, not in the container. The smoke test found the things only the image can show: the timezone resolves, the Secure cookie is set through HTTPS, `/hangfire` and `/openapi` are not reachable, and the whole stack idles at about 225 MB.

## 6.2 — Release process

- **Trust a header only from whoever is allowed to set it.** `X-Forwarded-For` is just text a client can write. The API believes it only when the connection comes from Caddy's network; from anyone else the header is ignored, so nobody can invent a new address per request and dodge the login limit. The test that proves this (a sender outside the network forges the header and still hits the limit) matters more than the one that proves the happy path.
- **Prove a test can fail.** After the forwarded-headers tests passed, the middleware was removed on purpose and one test turned red. A test that cannot fail proves nothing; it takes ten seconds to check.
- **A test can stand in for the network.** The test server has no peer address, so a small `IStartupFilter` gives every request one, playing Caddy's part. Same idea as the fake `ssh` used to rehearse the deploy: replace only the thing you cannot have, run everything else for real.
- **Rehearsing found what reading could not.** The migration bundle looked like "just run it with a connection string". Running it showed it boots the whole application host and fails without the JWT key. Nothing in the docs said so. Run the real thing once before trusting the plan.
- **One block of settings, two consumers.** A YAML anchor (`&api-environment`) feeds both `api` and `migrate`, so the two cannot drift. Shared configuration in one place is the same principle as one `Policies.cs` for authorization.
- **Migrate before you start, and never at startup.** If the migration fails, the old containers are still running and the new version never started. Migrating inside the app on boot would risk a half-started new version against a half-migrated database.
- **Rollback is not time travel.** Going back to the previous image does not undo a migration. That is why a migration should add before it removes: one release where old and new code both work is what makes the rollback safe.
- **A script's error message is its user interface.** `server.sh` says "`.env` has mode 644; run chmod 600" and "no previous release recorded" instead of failing somewhere deep. The person reading it will be you, at night, on a server.
- **Only record a rollback target that exists.** The first rehearsal stored the placeholder `latest` as "previous" and offered a rollback to an image that was never there. State that can be wrong should be checked when it is written, not when it is used.

## 6.3 — Backups

- **A backup you have not restored is a hope, not a backup.** The rehearsal destroyed the members table, ran `restore --yes`, and checked that the three members, the changed owner password and `/health` all came back. Writing the dump script was twenty minutes; that check is the actual task.
- **Write to a name nobody looks for, then rename.** The dump goes to `.gym-*.partial` and becomes `gym-*.dump` only after `pg_restore --list` can read it. A rename is atomic, so the pull script can never download a file that is still being written, and a failed dump never looks like a backup.
- **Verify before you trust, at both ends.** The server checks the dump can be read back; the Windows script checks the downloaded size against the server's before renaming. Each is one cheap line, and each catches a failure that would otherwise be found on the worst day.
- **Rotation must know what it may delete.** It removes only `gym-*.dump`. The `pre-restore-*` safety copies and the log sit in the same folder and survive; the test put a `pre-restore` file in the folder on purpose to prove it.
- **Pull, not push, and give the puller almost no power.** The gym computer is behind a router, so it cannot be pushed to. The account it logs in as is not in the docker group and cannot read `.env`: if that PC is stolen, the thief can read backups and nothing else on the server. Least privilege is a design choice made before the incident.
- **A destructive command needs a way out and a speed bump.** `restore` demands `--yes`, and it takes a `pre-restore` dump first. The dangerous stretch is between `DROP DATABASE` and the end of `pg_restore`; the script says exactly where the old data is if that stretch fails.
- **Exit codes are a user interface for schedulers.** Task Scheduler shows only a number. 0 is fine, 1 is failure or a stale backup, 2 is "saved, but no flash drive". Being stale counts as failure on purpose: the most dangerous backup problem is the job that quietly stopped running.
- **Match the tool to the machine that runs it.** The server is Linux, so bash; the gym's computer is Windows, so PowerShell 5.1. Trying to share one script would have made both worse. Windows PowerShell 5.1 has no `&&` and no `?:`, so the script avoids them.
- **Rehearsing with stand-ins is honest only if you say what they stand in for.** `ssh`, `scp` and a file mode were faked; the scripts, Docker, Postgres and PowerShell were real. What is still unproven (the real SSH key, cron, the `gymbackup` account) is written down as unproven.

## 6.1–6.3 review — re-checking what was already "done"

- **Re-reading finds typos; re-running finds bugs.** Every one of these was invisible on the page and obvious the moment it ran. The scripts had already been rehearsed end-to-end and still held four real defects, because the rehearsal only ever walked the happy path.
- **`set -e` does not cover functions; `set -E` does.** The `ERR` trap in `restore` was never firing, so the one message naming the `pre-restore-*` dump — the whole point of taking it — was dead code. A safety net nobody tested is not a safety net.
- **Test the failure path of the failure path.** The trap was cleared halfway through `restore`, so a failure *after* the data was back left the gym's system stopped in silence. Found only by deliberately breaking `efbundle` mid-restore.
- **A security check can be wrong in the safe direction and still be wrong.** `[ "$mode" = "600" ]` rejected mode 400, which is stricter. The property that matters is "group and other can read nothing", so that is what the check now tests.

State that records "where to go back to" must be written only once going forward has actually happened.

- **Run Linux things on Linux.** Git Bash on NTFS cannot represent mode 600, so the mode logic was checked inside a `debian` container. Testing a Linux script on Windows proves the syntax and nothing else.

## 6.0 — Deployment decisions and prerequisites

- **Prove the new way in before closing the old one.** The new user's key login was tested in a second window while the root session stayed open, and only then were passwords and root login switched off. Every lockout on a fresh server comes from doing those two in the other order. The provider's console is the last resort, and the time to find that button is before you need it.
- **A password is what a human can remember; a key is what a computer can't guess.** Roughly 50 bits against 256. Once `PasswordAuthentication no` is set, the thousands of guesses in the journal stop being a risk and become noise.
- **In `sshd_config` the first value wins, not the last.** The drop-in directory is read alphabetically, so the hardening file is named `00-` to sort ahead of anything the provider left there. And what matters is `sshd -T`, the merged effective configuration — not the file you just wrote.
- **`PasswordAuthentication no` alone is not enough.** PAM can still offer an interactive prompt that is a password in everything but name, so `KbdInteractiveAuthentication no` closes the same door from the other side.
- **Match the defence to the workload.** `ufw limit 22/tcp` blocks six connections in 30 seconds, and `release.sh` makes about five: ssh, three scp, ssh. That firewall would have blocked its own deployments, intermittently, looking like a network fault. `fail2ban` reacts to failed *logins* instead, which is the thing actually worth counting.
- **Docker bypasses the firewall.** A published container port is reachable from the internet whatever `ufw status` says, because Docker's rules sit in a chain consulted first. Proved it by accident: an nginx container answered from outside on a port nothing was told to allow. This is why Postgres has no `ports:` — on a server, publishing a port *is* opening it.
- **Diagnose before you change.** `Total failed: 0` looked broken. It had an innocent explanation — the counter resets on every restart, and four restarts had happened — and changing the config first would have meant debugging two problems. Two deliberate failed logins settled it in one minute.
- **Test the mechanism, not the configuration.** `fail2ban-regex` proved the patterns matched history; it could not prove the running jail was reading anything. Only a real failed login, followed by a counter moving, proves the path end to end. Same lesson as restoring a backup rather than admiring the dump file.
- **Swap is not extra RAM.** It exists so a memory spike degrades into slowness instead of the OOM killer picking the largest process, which here would be Postgres. That is why 2 GB is right and 4 GB would be worse: more room to thrash before dying.
- **Test `/etc/fstab` before the reboot that depends on it.** `swapoff` then `swapon -a` exercises the line you just wrote. A malformed `fstab` is discovered at boot, when the only way in is the provider's console.
- **The host's timezone is a label for humans; the app's time comes from its own configuration.** Moments are UTC `timestamptz` and business dates come from `IGymCalendar` reading `Gym:TimeZone`, so `timedatectl set-timezone` changes nothing in the application. It was changed anyway because `backup.sh` names dumps with the host clock — on UTC, the 03:00 Tehran dump carries the previous day's date, and picking the wrong night's backup is a bad way to learn that.
- **`ClockSkew = TimeSpan.Zero` is about steps, not drift.** One process issues and validates the tokens, so a clock that is steadily wrong harms nothing. What zero tolerance removes is the cushion that hides a sudden correction after a long unsynchronised stretch — which is why "NTP service: active" matters more than being right at this instant.
- **DNS has three layers, and the response code names the one that is broken.** `NXDOMAIN` with the TLD's own SOA means no delegation at the registry; `REFUSED` from the delegated nameserver means that server does not hold the zone; `NOERROR` with no answer means the record is missing. Reading the code turned "my domain doesn't work" into one fault at the DNS provider, with evidence good enough for a support ticket.
- **One canonical hostname, because cookies are scoped to a host.** Serving the app on both domains would give staff a separate session per name and sign them out when they typed the other one. The second domain redirects instead — six lines of Caddy config.
- **Compose interpolates variables inside `.env`.** A `$` in the Postgres password becomes part of another variable name, and the database silently receives something other than what the file shows. Generating letters-and-digits secrets avoids a failure whose cause is invisible.
- **`umask 077` before creating a secrets file, not `chmod` after.** The file is then never briefly world-readable, instead of being fixed once it already exists.
- **The `docker` group is root by another name.** A member can mount the host's filesystem into a container. Fine for the deploy user who already has `sudo`; deliberately withheld from the backup account.
- **Trust the kernel's numbers over the provider's label.** The panel said 4096 MB; `free -h` and `df -h` confirmed it, and the memory sizes were already variables in `.env`, so a machine twice the planned size cost one edit instead of a rebuild. Configuration that is a variable is configuration that survives being wrong.
- **The one thing no backup contains is `/opt/gym/.env`.** The nightly dump holds the database; the password and signing key live only in that file. A copy of it, kept apart from the dumps, is part of the backup plan rather than an afterthought.

## 6.5.1 — Lockers for the front desk

- **A group-wide authorization default is a decision nobody makes again.** Every locker endpoint was Owner-only because the whole `MapGroup` carried `RequireAuthorization(Policies.OwnerOnly)` once, written when the assumption was that staff would never browse lockers. The assumption aged; the policy did not, and nothing forced anyone to look at it again. - **The comment that explains a rule is also the thing that outlives it.** The file's own summary said staff "never need to browse the list, because check-in picks a locker itself". That was true and helpful — and it was still sitting there being wrong. When a rule changes, the prose defending it has to change in the same commit, or the next reader trusts it.

- **Tests that assert the old rule are part of the rule.** Four tests said staff get `403` on the locker list. They were not obstacles to route around: they were the previous decision, written down. Rewriting them to assert `200` is how the change gets recorded where it will be noticed.

## 6.5.2 — The "currently inside" board, one row one line

- **A form inside a table cell is a layout decision disguised as a component.** `ServiceChargeBox` was written for the member profile, where a form that expands in place is fine. The same component then went into two tables, and a row grew to three lines. Nothing was wrong with the component; it was right for one of its three homes. Moving the forms into a dialog fixed all three at once — and the cafe, which wants the same slot, now inherits a pattern that scales instead of a column that does not.
- **The row that grows is the design problem; the dialog is just where the form went.** The rule written into BUSINESS_RULES.md is "a row is always one line", not "use a dialog". A rule about behaviour outlives the widget that implements it.
- **`role="status"` is a shared namespace.** The hidden live region added to the charge box claimed the role that each page already used for its own message, and `findByRole("status")` started returning a hidden empty span from the first table row. `aria-live="polite"` announces just as well without claiming the role. Roles are global to the document, so adding one inside a repeated component means adding one per row.
- **A dialog is labelled by its title, so the title is an accessible name too.** Titling the dialog "مبلغ هوازی" while the field inside it carried the same label made `getByLabelText` ambiguous. The fix improved the UI as well: the title now says the action ("افزودن مبلغ هوازی") and the field keeps the noun.
- **The board dropped the status badge for the reason it was asked for.** Check-in refuses a subscription that is not usable today, so a status column here would read "Active" on every row forever. The useful signal is proximity to running out, which is why the row carries a low-sessions and near-expiry mark instead. A badge that never varies is decoration.
- **A progress bar needs a denominator.** An unlimited subscription has none, so `SessionsBar` says "نامحدود" rather than drawing a bar that would be a lie either full or empty. The type says it too: `total` is nullable, so the unlimited case cannot be forgotten.
- **Thresholds are business rules, not magic numbers.** "Three sessions" and "five days" came from the Owner and are written in BUSINESS_RULES.md §7, next to a note that Phase 10's SMS reminders must be configured with the same numbers — otherwise the desk and the member's text message would disagree about what "running out" means.
- **The generated API types widen integers to `number | string`.** The shared component takes the wide type and narrows it once, rather than making every call site remember a `Number(...)`. Normalising at the boundary of a component is the same idea as normalising at the boundary of a system.
- **`Attendance.SubscriptionId` made a hard question trivial.** The board could have re-derived "the subscription in effect today" and occasionally disagreed with the check-in that actually consumed the session. The attendance already names the subscription it used, so there was nothing to derive. When a fact is already recorded, the work is finding it, not computing it.

## 6.5.0 — Panel subdomain and a public page

- **A login form is not a front door.** Anyone typing the gym's domain met the staff login screen, and search engines were free to index it. The fix is not to hide the panel but to stop it being the apex: the gym's name serves the gym's page, and the application gets a host of its own.
- **A subdomain, not a path, and the cookie is the reason.** The refresh cookie is scoped to one host, so on `example.ir/panel` it would be set on the public domain and travel with every request to the public page. On `panel.example.ir` it cannot. The rest — separate rate limits, `noindex` on one host only, a public page that survives the API being down — follows from the same separation.
- **The plan said redirect the second domain to the panel; building it showed that was backwards.** Whoever types the gym's `.com` is a visitor, not a receptionist. Sending them to a staff login form is exactly what this task existed to prevent. The roadmap entry now records the change and why, because a plan that was quietly departed from teaches nobody anything.
- **The public page has no JavaScript and never calls the API, on purpose.** It keeps serving during a release, a migration or a database outage. The cheapest way to make something reliable is to give it nothing to depend on.
- **Ship the code and flip the switch as two separate acts.** The new image, released against the old `.env`, changes nothing a user can see: `PUBLIC_DOMAIN` is unset and `DOMAIN` still names the old host. So a broken build is discovered in a harmless release rather than in the five minutes before the gym opens. The disruptive step is then three lines in a file.
- **`X-Robots-Tag: noindex` is tidiness, not defence.** It asks well-behaved crawlers to stay away. It stops nobody else, and saying so in the comment keeps the next reader from mistaking it for a control.
- **Smoke-test the config, not the diff.** A Caddyfile is not covered by any test suite, so the whole production stack was built and run locally with `DOMAIN=localhost` and all four names exercised with `curl --resolve`. Reading the file proves the file; running it proves the deployment.

## 7.1 — Cafe products and categories

- **Asking the Owner first deleted half the task.** 7.1 was written as "products and stock": a `StockMovement` ledger, a non-negative stock constraint, purchases and adjustments with reasons. One question — what unit is stock in? — got the answer that the gym does not count stock at all and does not want to. The cheapest feature is the one that is never built, and the only way to find it is to ask before writing code, not after.
- **A rule that changes has to change in the source of truth, not just in the code.** BUSINESS_RULES.md §8 still said "stock changes only through the StockMovement ledger". Deleting that paragraph and writing down what replaced it, with the date and who decided, is what stops the next session from re-adding a stock column because the document said so.
- **Permissions are a table, and a phase can rewrite a row of it — twice in one day.** "Products and categories: Owner only" first became two rows (products for both roles, categories Owner-only), and then one row again when the Owner said staff have no restriction in the cafe at all. Splitting first was not wasted: the second change was one policy name, because nothing had been built on the assumption.
- **One policy per endpoint, even when a whole file shares it.** Products and categories still live in two endpoint files, and each names `StaffOrOwner` rather than inheriting a default. The names are what a future reader edits when the rule moves again, and this rule moved twice before the task was finished.
- **A flag's name in the code and its name on screen are allowed to differ.** `IsActive` reads as موجود / ناموجود at the desk, because the gym counts no quantities and this switch is the only thing that says whether something can be bought today. The rule is written down in BUSINESS_RULES.md; the column keeps the name every other entity here uses.
- **A derived answer beats a copied one.** Switching a category off could have written `IsActive = false` onto each of its products. Then switching it back on would have to remember which ones were off before — and it could not. "Sellable" is read as both switches together instead, so the shelf comes back exactly as it was. Same reasoning as occupancy in 6.5.1: the fact that cannot drift is the one nobody stores twice.
- **A filter means what the caller needs, not what the column says.** `GET /products?isActive=true` asks "can this be sold now", which is false for a switched-on product under a switched-off shelf. Naming the concept once, in the query's own documentation and in the response's `IsSellable`, is what stops each screen inventing its own version of the question.
- **Snapshots are what make an editable price safe.** Staff can change a price because an order copies the name and the price when it is rung up, exactly as a subscription copies its plan. Without that copy, editing a price would rewrite history, and the permission could not have been given at all.
- **Deleted, or deactivated — decide by asking what points at the row.** A product is deactivated forever, because orders reference it. A category is a heading with no financial history, so it can be deleted, but only while no product uses it. Same table shape, opposite lifecycle, and the reason is the reference, not the importance.
- **A pre-check and a constraint answer the same question at two different moments.** `DeleteProductCategoryHandler` asks whether the category is empty, and then catches the foreign-key violation for the product that was added a millisecond later. This task added `ForeignKeyConstraintException` alongside the existing `UniqueConstraintException`, so a race answers 409 instead of 500 — Application still knows nothing about Postgres.
- **`numeric(18,2)` money arrived by copying the rule, not the code.** `Product.CheckPrice` is `Plan.CheckPrice` with this feature's own error codes, so the Persian message names the field the user was typing into. Sharing the implementation would have shared the message too.
- **Generated API types are shared ground.** Regenerating `schema.d.ts` pulls in everything the running API exposes, including another branch's half-finished endpoints. Running it mid-way through someone else's task broke the frontend build, and the right move was to revert the generated file and leave the regeneration to the task that actually needs it (7.4).
- **A test that only passes for part of the day is a broken test.** `CurrentlyInsidePage.test.tsx` built an expiry date from `Date.now()` in UTC while the board counts days in the gym's time zone, so it failed between midnight and 03:30 local time. Anchoring the fixture to `gymToday()` — the same clock the code uses — is the fix; "it passes on my machine at 2pm" is not a property worth keeping.

## 6.5.3 — Single-session entry (تک‌جلسه‌ای), the rules and the API

- **The expensive part of a feature is the list of rules it has to be invisible to.** The entity change was one bool and the migration was one afternoon; the work was the five places that order a member's calendar — the queue, the exclusion constraint, the exhausted-promotes-the-queue rule, the freeze shift, and the board's attention thresholds. Each one was a different way for a single visit to rewrite something the member had already paid for.
- **The worst bug in this task would have changed data, not behaviour.** Selling a single visit to a member whose pack had run out of sessions called `CloseExhaustedEarly`, which sets that pack's `EndDate` to yesterday. Nothing errors, nobody is refused, and the member quietly loses the rest of their term. Tests that assert "nothing else moved" are the only ones that catch this class of bug — which is why most of `SingleSessionSubscriptionTests` asserts about the *other* subscription.
- **A flag that a database constraint reads has to live on the row it constrains.** The exclusion constraint is on `subscriptions` and cannot join to `plans`, so `IsSingleSession` is snapshotted at the sale rather than read through `PlanId` the way the plan's *name* is. The same conclusion §4 already reached for price and duration, arrived at from the opposite direction: not "history must not change" but "the constraint cannot see that far".
- **Relaxing an invariant means writing down which one you kept.** The condition went from `WHERE (cancelled_at IS NULL)` to `WHERE (cancelled_at IS NULL AND NOT is_single_session)`. "We made the overlap rule weaker" is not something a reviewer can check; "two memberships still never cover the same date, and that is now the whole of the rule" is.
- **A default parameter is right exactly when the default is the truth.** `PlanKind kind = PlanKind.Membership` left all 45 existing `Plan.Create` call sites alone, not to save typing but because every plan that existed before really was a membership. A required parameter would have made 45 files claim a decision none of them made.
- **A tie-break becomes a business rule the moment money moves.** Once a single visit may overlap a membership, two subscriptions can both be `Active` today and something has to choose which session gets consumed. Picking the single visit (worth nothing tomorrow; the membership's sessions keep) is defensible, but it is a decision about whose money is spent, so it is marked *pending review* rather than buried in an `OrderByDescending`.
- **A column default is a compatibility surface, not a model detail.** I dropped the new columns' defaults, reasoning that a default the model does not declare shows up as a phantom diff later. That reasoning was wrong — EF compares the model to the *snapshot*, never to the live database — and dropping them broke every hand-written `INSERT` in the table tests. Kept both: they fill the existing rows once, and they keep raw SQL written before the column existed working.
- **An enum crosses the wire as text only where you say so, and input is a separate place from output.** `PlanResponse` carried `[JsonConverter(typeof(JsonStringEnumConverter<PlanKind>))]` from the start, so the *reply* read `"SingleSession"`. The command did not, so sending the same word back was a 400 until it did too.
- **A rule that names a screen is a UI requirement, and writing it down does not build it.** §3 said "the Owner creates it once from the plans screen", the API accepted `kind`, the entry screen even told the desk to go there — and the plans form had no box for it. Every test was green because every test checked a piece; nothing walked the path a person would. The gap was found the way the Owner would have found it: by trying to create the plan.
- **"It will not start" has more than one cause, and the first fix is not the last.** The dev database was two migrations behind (the same trap as the dropped `plan_name` in 4.x — green tests say nothing about the database on your machine), and later Docker itself was down after the machine slept, which took the API with it. Read the actual error each time instead of re-applying the last fix.
- **422 is a refused business rule; 400 is input the API could not read.** Asserting `HttpStatusCode.BadRequest` on a check-in refusal was my mistake, and the fix was not a better status assertion but a better test: assert the error code, which is the thing the front desk actually maps to a Persian sentence.

## 6.5.4 — The entry screen

- **The API already knows; asking it beats re-deriving it.** The plan was to work out each person's state in the browser and show one action for it. "Can this member come in today" is `SubscriptionSchedule.InEffectToday` plus `ConsumeSession` plus the exhausted-with-a-queue rule — all of it in Domain, all of it operating on a list of subscriptions. Rebuilding that in React would have been a second copy of two sections of BUSINESS_RULES.md, and the copy would drift. The screen presses check-in and reads the refusal instead.
- **That also made the guarantee stronger.** The worry behind "one primary action" was a member with a usable subscription being charged for a single visit. Deriving state in the browser would have made that a bug waiting in the derivation; reacting to a refusal makes it impossible, because the offer exists only where the API said no.
- **A refusal is not always an error message.** Six error codes mean "needs a subscription" and open a way forward; everything else check-in can answer stays a red alert. The difference is the whole feature: the walk-in case is the one the desk meets all day, and it was previously a dead end.
- **A filter you can reach beats a page you have to find.** The single-session plan is one row that can sit on any page of a paged list. `GET /api/plans?kind=SingleSession` is three lines in the query and the handler, and replaces "fetch page after page and hope".
- **Say which thing is missing.** "The plan does not exist" and "the plan is switched off" have different fixes, and the Owner is the person who does both. The panel asks without an `isActive` filter so it can tell them apart, and shows no button at all rather than one that would fail.
- **Two requests that are not a transaction, and why that is safe here.** Selling the visit and checking in are separate calls. If the second fails, the member has a paid visit for today and the ordinary check-in button finishes the job — the failure is visible and recoverable. The reverse order would not be, which is why the order is the design and not an accident.
- **Generated types are a shared contract, and someone has to regenerate them.** 6.5.3 left `npm run gen:api` to this task on purpose, because the frontend had no use for `kind` and `isSingleSession` until now. Running it earlier — as this session did once, mid-way through 6.5.3 — broke the frontend build with a contract half the codebase had not caught up to yet.

## 7.2 — Cafe orders

- **A column that waits three phases for its first writer.** `Payment.CafeOrderId` and the one-target check constraint have existed since task 4.4, documented as "nothing sets this before Phase 7". Filling it in was a factory method, an enum member and two more `Concat`s in `MemberDebt` — no migration to the payments table, no backfill, no change to how any existing payment reads. Designing the shape once, while the rule was fresh, was worth more than the column cost.
- **"Never edited" is a design, not a missing feature.** There is no endpoint to change a line on an order, because §5 says financial records are corrected with a cancellation and a fresh record. Writing that into the endpoint file's own summary is what stops the next session adding a PUT and calling it an improvement.
- **The snapshot is the whole reason the price is editable.** Staff can change a product's price because an order copies the name and the price at the till. The test that edits a product and re-reads yesterday's order is the one that protects that permission — if it ever fails, the permission has to go, not the test.
- **Two switches, one answer.** A product can be unsellable because it is switched off or because its category is. The till gets `Products.Inactive` either way: the person at the counter needs to know the item cannot be sold, not which flag said so. Where the two *do* differ — the management screen — both flags are on the response.
- **The same invariant, guarded the same way, for the third time.** "Cannot be overpaid" is a sum across rows that no check constraint can express, so the cafe payment handler locks the member row exactly as the subscription and service-charge handlers do. A walk-in order has no member to lock and also cannot be paid later, so the lock is conditional and the comment says why rather than leaving a reader to wonder.
- **A check constraint can police arithmetic.** `line_total = unit_price * quantity` is one line in the configuration and makes a hand-written INSERT with an inconsistent total impossible. The stored total is what the customer was charged; the constraint is what stops it drifting from the two numbers beside it.
- **The only cascade in the schema, and it earns it.** Every other foreign key here is `Restrict`, because financial records must not vanish with the thing they point at. An order line has no meaning and no money without its order, so it cascades — and the comment says the application never deletes an order anyway, so the cascade is about the model being honest rather than about a feature.

## 6.5.4 follow-up — The entry screen, after real use

- **A button that can only be refused should not be offered.** After a single visit the member was inside, but the row still showed "ورود", and pressing it could only get `Attendance.AlreadyCheckedIn`. The API was right; the screen was offering an action it already knew the answer to. The row now shows "داخل باشگاه" instead.
- **Derived on read, never stored.** `MemberResponse.CurrentVisit` is "the attendance with no `CheckedOutAt`", or null, the same test `CheckInHandler` uses. Storing a flag on the member would be a second copy of that fact that check-out, cancel and the nightly auto-close would all have to remember to update.
- **Batch per page, not per row.** Like `Debt`, it is one query for the whole page (`WHERE member_id IN (...)`), not one per member. That keeps the search at a fixed number of queries however many rows it shows.
- **Cache invalidation follows the data, not the feature.** Member lists now carry attendance state, so the attendance mutations invalidate member lists too. Without that, a check-in would succeed and the row would keep showing the old button until the next refetch.
- **Start the form from what was already typed.** The search box already holds a name or a phone, so the registration form starts from it using the same "only digits and phone punctuation" rule the API uses to decide between a phone search and a name search. react-hook-form reads `defaultValues` only when the form mounts, which is fine here because the form appears only after the click.
- **Return what the next action needs, not just a flag.** A yes/no "is inside" was enough to grey out a button, but check-out needs the visit's id and the exit box needs the locker. Returning the open visit itself (`CurrentVisit`) answers the yes/no *and* feeds the next request, without a second call per row.
- **Confirm before, report after, in one place.** The dialog is a small state machine (`confirm → checkedIn | needsSubscription | checkedOut | failed`). Keeping every step in one box means the desk's eyes never leave it, and mounting it with a fresh `key` per press is what resets it to "confirm" — React throws away the old state instead of us resetting it field by field.
- **Guard against the accidental second press.** Nothing is focused when the box opens, and a click outside it does nothing. A held Enter or a stray click is exactly how a confirmation gets skipped, so the dialog refuses both.
- **Depend on the least the component needs.** The box first took a whole search-result `Member`, so only the search screen could open it. Narrowing it to `DeskMember` (id and name) and `DeskVisit` (attendance id and locker) let the profile and the "inside" board use it too, each building those two small objects from the data it already has. A hook (`useDeskDialog`) keeps the "fresh key per press" detail in one place instead of three.
- **A shared label fixes a bug in two places.** The profile's debt card called cafe orders "اشتراک", because its label function only knew two kinds. Moving it to `debtItemLabel` with a `switch` over every kind means TypeScript now complains if a fourth kind is added and not labelled.
- **A valid format is not a valid number.** libphonenumber checks whether a number falls in an assigned operator range, not just its shape, so `0945…` is refused even though it looks right.

## 7.3 — Cancelling a cafe order, and the order history

- **Check again after you take the lock.** The payment handler read the order, saw it was not cancelled, and only then took the member lock. A cancellation finishing in that gap would leave a payment on an order that owes nothing. The fix is to ask the question again *after* the lock: under Postgres's default isolation (read committed), each statement sees everything committed before it started, so the second read sees the cancellation the lock made us wait for. Checking before taking a lock and trusting the answer afterwards is the classic "time of check to time of use" race.
- **Two different guards for two different races.** An order on a member's account is protected by the member lock, the same lock every payment takes. A walk-in order has no member to lock, but it also takes no payments after it is created, so the only race left is two cancels at once. The order's `xmin` version handles that: the second `UPDATE` matches no row, EF Core throws `DbUpdateConcurrencyException`, and because the refunds were written in the same `SaveChanges` inside the same transaction, they are rolled back too.
- **Refunds per payment method.** `PaymentLedger.GetNetPaidByMethod…` groups payments by method in SQL and keeps only the methods still in credit. Voiding a service charge and cancelling an order now share that query instead of each having its own copy.
- **Batch per page, again.** The history reads one page of orders, then makes exactly two more queries for the whole page: member names (`WHERE id IN …`) and net paid per order (`GROUP BY cafe_order_id`). An order with no payments is missing from that dictionary, so it is read with `GetValueOrDefault`, which gives zero.
- **Filter on the business date, not the moment.** The history filters on `OrderedOn` (a `DateOnly` in the gym's time zone), so "the orders of 3 Mehr" needs no time-zone arithmetic. The attendance history had to turn dates into UTC moments because a visit only stores the moment.
- **One handler behind two routes.** `/api/cafe/orders?memberId=` and `/api/members/{id}/cafe-orders` return the same thing. The member route's handler only adds "unknown member is a 404" and then calls the counter's handler, so the query logic lives in one place.
- **A gap found by following the money.** The refunds a cancellation writes needed somewhere to be seen, which exposed that the member's payment history had never included cafe payments at all. Adding a third target meant a third `Any(...)` in the filter and a third branch in the target kind, plus a `switch` in the frontend so TypeScript flags a fourth kind if one is ever added without a label.

## 7.4 — The cafe screens

- **Put the arithmetic where it can be tested without a screen.** The cart is plain functions over a list of lines (`cart.ts`): add, set quantity, remove, total. The till page only calls them. Testing "a second tap raises the quantity" or "3 × 25,000 + 120,000" then needs no rendering, and the rendered tests can stay about what the desk sees.
- **Money is multiplied as whole hundredths, not floats.** `multiplyMoney` and `addMoney` sit beside `subtractMoney` and turn amounts into `bigint` hundredths first. A float can hold 25,000 × 3 correctly, but not every amount the API accepts, and one helper that is always exact beats remembering when a float happens to be safe. The server's total is still the one that counts; the cart only previews it.
- **A value that follows another until somebody touches it.** The amount box starts at the cart's total and keeps following it while items are added. Once somebody types, it keeps what they typed. That is one piece of state holding `null` ("follow the total") or a string ("what was typed"). There is no effect copying one value into another, which is where "the box changed under me" bugs come from.
- **A controlled input that also follows outside changes.** The quantity box has to accept "۱۲" typed one digit at a time and also follow the + and − buttons. Remounting it with a new `key` on every change would lose focus after the first digit. Instead it adjusts its text during render only when the committed number differs from what the box already says (the same "adjust state while rendering" pattern the Jalali date field uses).
- **Put the filter in the URL.** The till's customer (`?member=`) and the history's date range (`?from=&to=`) live in the URL, not only in component state. The member profile can link to the till with the member already chosen. Refreshing or pressing back keeps the filter. The URL holds the ISO dates the API reads; only the boxes speak Jalali.
- **Don't send a request you know will be refused.** A backwards date range is shown next to the box and the query is disabled (`enabled: false`), rather than sent to collect a 400. The same idea as showing only the row actions the API would accept: a cancelled order shows no buttons at all.
- **Fetch every page when the whole list must be on screen.** The till's grid and the category picker need every row, and the API returns at most 100 per page. `fetchAll` keeps asking until it has `totalCount` rows. For a cafe that is one request, but the code does not quietly stop at the hundredth product.

- **The same shape, a second time.** A هوازی charge hangs off its visit, and now a cafe order can too. The backend repeats the pattern rather than inventing one: a nullable `AttendanceId`, a handler check that the visit is open and belongs to that member, a batched `ByAttendanceAsync` for the board, and the same dialog-over-the-row UI. ## 7.4 follow-up — Saying "saved" at the desk

- **A port can only have one listener.** `dotnet run` failed with `address already in use` because an earlier API was still running with nothing attached to it: the window that started it was gone. `Get-NetTCPConnection -LocalPort 7134` shows which process holds a port, and its start time shows whether it is running today's code. `Ctrl+C` stops the API in its own terminal. `Get-Process Gym.Api | Stop-Process` stops one nobody can reach anymore.

The box now ends on a success step (`DialogSuccess`): a green title, what was saved, and a close button. It is the same shape check-in and check-out already used, so the desk learns one pattern.

- **State that outlives the state it started in.** Recording a first هوازی amount turns "no charge" into "a charge" while the dialog is open, because the mutation waits for the refetch before it resolves. The box used to have one dialog per state, so the success step would have been unmounted in the middle of showing. Now there is one dialog for every state, and it picks its content from `open` first.

## 7.5 — Settle a member's debt in one step (تسویه یکجا)

- **Automate the rule, don't change it.** §5 already said "a lump sum is entered against each item". The settlement endpoint does exactly that and nothing more: one ordinary `Payment` per item. No new table and no wallet, so debt, payment status, refunds, voids and cancellations keep working without a single change. Adding a feature by *reusing* the existing record keeps every rule that already reads that record correct.
- **A pure function for the rule that decides whose money is spent.** `SettlementAllocator` lives in the Domain and knows nothing about the database: items and an amount in, shares out. The order "cafe → هوازی → subscription, oldest first" is pinned down by ten fast unit tests instead of integration tests that would each have to build three kinds of debt.
- **"What the desk saw is what gets paid" (optimistic check).** The request carries each ticked item *with the figure the desk was shown*. Under the member lock the handler reads the debt again and refuses with `409 Settlements.DebtChanged` if anything differs. It is the same idea as `xmin` concurrency, done by hand: compare what the client read with what is there now, and refuse rather than guess.
- **One lock that every writer takes.** Paying, voiding a charge and cancelling an order all take the member lock (`LockMemberAsync`), so the settlement only has to take it too. Four settlements pressed at once become one success and three `409`s, and the member is never charged twice (the parallel integration test proves it).
- **All or nothing.** The rows are written in one transaction. If the third payment failed, the first two would roll back too. A half-written settlement would be worse than none, because the desk would think it had failed and take the money again.
- **Keep the success step at one place in the tree.** React keeps a component's state only while it stays at the same position. The debt card first rendered `SettleDebt` in two different branches (owed / not owed), so clearing the debt would have remounted it and wiped the "تسویه ثبت شد" step at the exact moment it appears. Rendering it once, after the branch, fixes that.
- **Store the exception, not the rule.** The form remembers which items were *unticked*, not which were ticked. After a refetch, a new item appears ticked like the rest without any code to reconcile the two lists.
- **Break an import cycle with a file.** `cafe/api.ts` imports `payments/api.ts`, so the settle hook (which refreshes the cafe's cache) lives in `payments/settle.ts` rather than making the two files import each other.

## 7.5 follow-up — Confirming money at the desk

- **Validate first, ask second, send third.** Each money form's `handleSubmit` no longer sends anything. It only stores the checked values (`toConfirm`), which opens `ConfirmPaymentDialog`. The request goes out only from the dialog's "yes". Validation errors still appear the usual way, and nobody is asked "was the money received?" about a form that would have been refused anyway.
- **A guard that names what it guards.** The question shows the amount and the method ("۶۴۰٬۰۰۰ تومان با روش کارت"). A generic "are you sure?" is clicked through out of habit. A concrete figure is something the desk can check against the money in hand.
- **No default is a decision too.** With "نقدی" preselected, a card payment the desk forgot to switch was recorded as cash, and the revenue-by-method report (§12) would inherit the mistake. An empty first option, which the Zod schema refuses (`z.enum(..., { error })`), forces a choice. The empty option is not `disabled`, because a browser skips a disabled first option and would show "کارت" as if it were chosen.
- **One component for one rule.** `PaymentMethodField` holds the empty option and the order (card, bank transfer, cash) for all six forms. The next form that takes money gets the rule by using it, not by remembering it.

So the dialog sits beside the `<form>` in a fragment rather than inside it, and its buttons are `type="button"`. A click on "yes" can never also submit the form.

Without a `method` there, the inferred type lost the field, and the resolver no longer fitted. `useForm<RegisterPaymentValues>` names the full shape, and `DefaultValues<T>` types the partial defaults.

## 11.5 — A password policy after NIST

- **Length beats complexity.** NIST SP 800-63B asks for a long password and a blocklist, and advises *against* "one upper case, one digit, one symbol". People meet such rules the same predictable way (`Ali@12345`), so the rules add typing pain without adding guessing cost. The policy is now 12+ characters, English only, no user name, no keyboard run, not on the list.
- **A blocklist compares cores, not strings.** `Football2024!` is `football` with a disguise. Trimming digits, symbols and spaces from both ends before comparing catches the usual disguises, while equality (not "contains") still lets a passphrase with an ordinary word in it through.
- **Data can ship inside an assembly.** The 100,000-entry list is an `EmbeddedResource` in `Gym.Domain`, read once into a `FrozenSet`. No package, no network call, no password ever leaves the server to be checked, and Domain still references nothing.
- **One rule, two enforcers, one error code.** FluentValidation reports the policy as a field error before anything happens; Identity's `IPasswordValidator` checks it again on every stored password. The Identity error carries the policy's own code (`Auth.PasswordTooCommon`), so the frontend shows the same Persian sentence whichever layer refused.
- **The only moment you see a password is login.** The database holds hashes, so an old weak password cannot be found by a query. At a successful login the server has the real password in hand for a moment; that is where "this no longer meets the policy" is checked and `MustChangePassword` set.
- **Why English only.** ی/ي and ک/ك look identical but are different code points on different keyboards. A Persian password set on one device can fail on another, and nobody could see why.
- **`useWatch` instead of `watch()`.** The React Compiler cannot memoize a component that calls `form.watch()`; `useWatch({ control, name })` subscribes properly and keeps the lint clean.

## 11.6 — A lockout an attacker cannot turn against the gym

- **Every protection can become a weapon.** A lockout stops guessing, and it also lets anyone who knows a user name lock that person out forever. Security features need to be read from the attacker's side too: "what can someone do *with* this rule?"
- **Two doors instead of one (OWASP device cookies).** A browser that logged in successfully gets a secret cookie and its own failure count. Wrong passwords from anywhere else lock only the "unknown devices" door. The attacker can still lock something, but it is a door the gym never uses.
- **Never trust a value you did not issue.** The device secret in the cookie is reused only if the database already knows it. Otherwise a value someone planted (cookie tossing from another subdomain, say) could become a trusted device.
- **Atomic counters in SQL.** `ExecuteUpdateAsync` with `SET failed_attempts = failed_attempts + 1` lets Postgres do the arithmetic on the locked row, so ten parallel wrong passwords count ten times. Reading, adding in C#, and saving would count one.
- **Some operations should have no endpoint at all.** Resetting the Owner from the web would put the whole system one stolen password away. `dotnet Gym.Api.dll admin …` builds the same host and runs one command without starting the web server. SSH access is the authorization.
- **Secrets never go on a command line.** Arguments show up in shell history and in `ps`. `server.sh set-password` reads the password with `read -s` and pipes it on standard input.
- **Rotate secrets on every use.** A review pointed out that a copied device cookie would have stayed valid for 90 days. Now every login and refresh gives the browser a new secret, so a copy dies the next time the real browser is used. The same idea as refresh-token rotation, applied to a second cookie.
- **Read a feature from the attacker's side after writing it.** The tests all passed, and a separate review still found a stolen-cookie path, a 500 on a race, and a shell `read` that silently trimmed spaces from a passphrase. Tests check what you thought of; a reviewer checks what you did not.
- **Two sessions, one folder, is a trap.** Another session was editing the same working tree. A `git worktree` gave this task its own folder and branch, with its own `bin` (no locked DLLs) and its own `node_modules`, and the other session's files were untouched.

## 6.5.5 — The locker map: the desk chooses the locker

- **A rule enforced by the compiler.** "Nobody creates a locker" is not a check in a handler: `Locker.Create` is `internal`, and only `Gym.Domain.Tests` can see it (`InternalsVisibleTo`). Application cannot call it at all. The real 72 come with the migration (`HasData`).
- **Ids from a formula.** `LockerSeed.IdOf(12)` is `…-000000000012`. A migration has to name its rows, and 72 pasted GUIDs are 72 chances for a typo nobody would notice.

- **Say it, do not infer it.** A reserve place has no locker, but so does a visit closed before 6.5.5. `UsesReservePlace` says it outright, so the screen never has to guess from a `null`.
- **A floor plan is data.** `layout.ts` holds zones → groups → cabinets, and a test proves every number from 1 to 72 appears exactly once. The drawing code only walks the data.
- **A left-to-right island in a right-to-left page.** The wall runs 1 → 30 left to right, so each zone is `dir="ltr"` while the rest of the page stays RTL.
- **One component, two modes.** `LockerMap` in `desk` mode opens boxes; in `pick` mode only free lockers are clickable. Moving a visit reuses the same map instead of a second picker.

## 6.5.6 — Custom plans and two fixed prices

- **Settings the Owner edits belong in the database, not in `appsettings`.** `Gym:TimeZone` changes once, with a deployment. A price changes with inflation, from the Owner's own screen. That makes it data: a row with an `xmin` token, an audit trail and an endpoint, not a configuration key.
- **A one-row table.** `price_lists` has a fixed id (`PriceList.TheId`), seeded by `HasData`, and a check constraint `id = '<that id>'`. A second row cannot exist even by hand, so "which price list?" has one answer. The entity has no public constructor: nothing in the app ever creates one.

## 6.5.7 — Sell at the locker: the sale and the check-in in one step

- **One transaction instead of two requests.** The single visit used to be two calls: sell, then check in. If the second failed, the member had paid for a visit with no locker. Now check-in takes an optional `sale` and does both in one database transaction, so they are saved together or not at all.
- **Split a method by who owns the transaction.** `SubscriptionSeller.SellMembershipAsync` opens a transaction, locks the member and commits. Check-in already holds its own transaction and lock, so the pricing and scheduling part moved into `AddMembershipAsync`, which only adds the row. The standalone sale is now just "begin, lock, `Add…`, save".
- **Save inside the transaction, commit at the end.** Check-in calls `SaveChangesAsync` right after the sale, so its own lookup finds the new subscription like any other row. Nothing is committed until the visit is saved as well, and a transaction disposed without a commit rolls both back.
- **Test what did not happen.** The key test takes the locker first, then sells a plan with a check-in on it. It asserts the 409 and also that the member has no subscription at all. An atomicity rule is proved by the row that is missing.
- **FluentValidation: `WithErrorCode` only applies to the rule right before it.** `NotNull().InclusiveBetween(...).WithErrorCode(X)` gives a missing value the default `NotNullValidator` code, not `X`. One `Must(...)` that covers "missing" and "out of range" gives both the same code.
- **`OverridePropertyName` keeps the form simple.** The API reports `sale.durationDays` as `durationDays`, so the same `PlanForm` puts the error under its field, whether it is selling from the profile or from the locker.
- **Minimal APIs run filters even when body binding failed.** The argument is `null` and the status is already 400. `ValidationFilter` took that for a wiring mistake and threw a 500. A test that sends no body caught it.
- **Reuse by extracting the part that differs.** `PlanForm` knows the fields, the price preview and how to show a server error. What happens on submit is passed in as a prop: `assign` on the profile, `checkIn({ sale })` at the locker.
- **Generate types from the code you just wrote.** An API that was already running on :5134 was the old build, so `gen:api` would have read the old document. The new build ran on a spare port for one generation and was stopped afterwards.

## 6.5.9 — A frozen member who comes in is unfrozen

- **One rule, one place, two callers.** The Owner's unfreeze button and a check-in both end a freeze. The queue-shifting logic was inside `UnfreezeSubscriptionHandler` as a database query. - **Load everything, let the Domain choose.** Moving the queue into the Domain meant loading all of the member's subscriptions (tracked) instead of querying only the queued ones. - **A deferred constraint needs the right commit.** Unfreezing moves several rows whose date ranges overlap for a moment, so the overlap check is deferred to commit.
